## Findings

<a id="R1"></a>
### R1 — blocker — Windows workers can execute before their affinity limit is applied

**Location:** `crates/krummi-bench/src/orchestrator/cores.rs:141` (assignment follows at line 142).

**Requirement:** S4/S5, B4/B5 and AC-B3. B4 explicitly includes «los que preparan sus almacenes y los que miden sus cargas» and requires those processes and their descendants to run only on the performance cores when classes distinguish them.

**Problem and failure scenario:** `command.spawn()` starts a runnable worker before `job.assign_process(...)`. On a hybrid Windows machine, the scheduler can run that child on an efficiency core before the parent reaches the assignment. There is no suspension or worker handshake. The worker immediately dispatches preparation (`worker.rs:58`, `worker.rs:571`), which opens and writes its store at lines 574–575. If the parent is delayed long enough, a load can also reach its timed operations (`worker.rs:595`) before assignment. A later successful assignment returns `limited = true`, so the run can report the performance-core line despite having performed earlier work without the limit (`orchestrator.rs:181`). Any descendant created before assignment also escapes the intended job inheritance.

**Evidence type:** verifiable source-level concurrency argument. Ordinary scheduling permits the child to advance while its parent has not completed line 142; the code contains no ordering mechanism to prevent that execution. Microsoft's [process creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) document suspension of the initial thread, and its [Job Objects documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) makes automatic child association apply after the parent joins the job. The ODD's D2 assumption that preparation precedes measurement supplies no scheduling guarantee and does not exempt preparation from B4. This establishes the implementation defect; no claim is made that a particular saved benchmark run encountered this schedule.

**Test gap:** the current affinity test launches PowerShell and inspects its affinity after startup; it does not force the parent to pause between spawn and assignment. Its successful normal execution therefore does not cover this race.

**Suggestion:** establish the limit before the worker can execute, preserving the specified unrestricted fallback, and add a controlled scheduling regression test.

**Status:** open; introduced in the reviewed range.

### R2 — minor — The integration test rejects the permitted unknown-core fallback

**Location:** `crates/krummi-bench/tests/run.rs:381` (accepted variants at lines 382–385).

**Requirement:** S5/S6, B4/B5 and AC-B3. B5 explicitly permits `Núcleos: desconocido` when querying classes or limiting a process fails; B4 requires the run to continue.

**Problem and failure scenario:** if the class query fails, `Workers::classes` returns `None`; if a limit cannot be created or a process cannot be assigned, the placement likewise renders as unknown. A reduced two-engine run can correctly finish with code `0` and `- Núcleos: desconocido`. The integration assertion accepts only the performance-core and unpinned variants, so it fails on that valid report. CI explicitly includes this ignored integration test (`.github/workflows/ci.yml:152`).

**Evidence type:** direct source argument and predicate evaluation. Evaluating the assertion's exact string conditions against `- Núcleos: desconocido` returned `False`. The production fallback paths are in `orchestrator/plan.rs:61`, `orchestrator/cores.rs:77` and `orchestrator.rs:172`. A full .NET integration run under an induced failure was not executed.

**Suggestion:** accept all three specified core-status lines and exercise the fallback with controlled failure injection.

**Status:** open; introduced in the reviewed range.
