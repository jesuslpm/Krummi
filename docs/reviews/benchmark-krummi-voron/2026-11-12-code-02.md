### R1 — original severity: blocker — Verified resolved

Original reference: `docs/reviews/benchmark-krummi-voron/2026-11-12-code.md#R1`.

The original source-level reproduction allowed the engine process to execute between `spawn` and job assignment. The replacement closes that ordering gap: `launcher_main` calls `launcher_job` at `crates/krummi-bench/src/orchestrator/cores.rs:154`; the job has affinity and kill-on-close limits and the launcher joins it at lines 192–198. Only after successful membership does line 172 create the engine. Thus engine preparation, measurement and descendants inherit the job from creation. The launcher itself does no engine preparation or measurement before membership. This satisfies B4's inclusion of «los que preparan sus almacenes y los que miden sus cargas».

Independent evidence:

- The Windows chain unit test `a_limited_process_and_the_ones_it_starts_run_on_its_cores` passed through the real `Pin` and launcher, checking both process masks, unchanged parent affinity, absence of the handshake in worker output and `!pin.failed()`.
- The three `tests/cores.rs` tests passed: launcher/child/grandchild affinity and worker-role propagation; invalid-mask startup emits only `limit 0` and starts no engine; exit code 7 survives launcher shutdown.
- The dependency's `win32job-2.1.0/src/job.rs` creates the job with `CreateJobObjectW(None, ...)`, so its handle is not inheritable. `keep_until_exit` keeps that handle alive until process exit rather than dropping it while the launcher is still in its own kill-on-close job.
- An additional independent reproduction started the real launcher on the lowest allowed CPU, with a Python engine that started a Python descendant; both descendants were waiting for 30 seconds. After reading `limit 1` and both PIDs, the reproduction killed only the launcher. Both already-open process synchronization handles became signaled (`WaitForSingleObject` results `[0, 0]`), and output collection completed within ten seconds. No stores or user data were involved. This verifies the main new cancellation dependency in `orchestrator/child.rs:78`.

Fallback and dependent paths were also inspected: an unsuccessful launcher starts no engine (`cores.rs:160`); the parent consumes its handshake, kills/waits for it, and starts the original command without the limit (`cores.rs:255`). A missing launcher exercises this fallback in the passing unit test `a_process_whose_launcher_cannot_start_runs_without_the_limit`. `Pin::spawn` records the failure, and `orchestrator.rs` derives the report through `Placement::line(false)`, yielding `Núcleos: desconocido`. The original command retains the worker role, arguments and failure-injection variables. The launcher forwards worker output/errors and the worker's exit code. The unchanged interrupt cleanup remains responsible for deleting the disposable work subfolder.

Evidence type: source-level ordering and lifetime argument, supported by independent Windows process tests. The job-inheritance rule is documented in Microsoft's [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) documentation; handle inheritance is specified by [CreateJobObjectW](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-createjobobjectw).
