## Findings

<a id="R1"></a>
### R1 — Major — Included primary-key columns have conflicting ownership contracts

- **Location:** Decisions / IX1 and IX8; Acceptance criteria / AC-IX3 (`docs/prd/krummi/tables/tables-indexes.prd.md:45`, `:52`, `:214`).
- **Follow-up status:** **still open**, independently verified against the unchanged PRD; originally reported as `docs/reviews/tables-indexes/2026-11-18-prd.md#R1`.
- **Problem:** A primary-key column explicitly listed among an index's included columns receives both the borrowed-value and owned-copy contracts, without a precedence rule.
- **Evidence:** IX1 permits «Las columnas de la clave primaria pueden estar en la clave del índice o entre sus incluidas». IX8 says included columns return «sin copia el texto, los bytes, los vectores y el JSON», but primary-key columns return «decodificados en una copia propia de la aplicación, también el texto y los bytes». AC-IX3 explicitly covers «una columna de la clave primaria en la clave del índice y otra entre las incluidas» while requiring «el texto, los bytes y los vectores incluidos sin copia, los de la clave en una copia».
- **Observable readings:** For a table whose primary key is `id: string`, an index on another column that includes `id` can return `id` borrowed from its included payload, or decoded into an application-owned copy because it is a primary-key column. These differ in copying and ownership behavior. IX8 exposes each column once, so returning separate positions cannot satisfy both promises. AC-IX3 has no unambiguous expected result for this supported overlap.
- **Suggestion:** Specify which ownership rule wins for included primary-key columns and align AC-IX3 with it.
