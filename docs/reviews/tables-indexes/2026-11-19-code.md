<a id="R1"></a>
### R1 — Major: Index construction aborts the process on an entry allocation failure

**Location:** `crates/krummi/src/table/index.rs:532`, reached from `:826`; also `crates/krummi/src/table/index_key.rs:44`.

`sorted_entries` builds each entry before passing it to `Sorter::push`. Its included-column payload uses `included.encode(&values)`, whose existing `RowLayout::encode` uses infallible allocation (`row.rs:327–328`). Entry keys similarly use `Vec::with_capacity`. The fallible reservation of the sort's entry vector does not cover these allocations. The new index-building path therefore terminates the host process on allocation failure instead of returning `Error::OutOfMemory` and applying T11.

**Concrete scenario and experimental evidence:** a temporary store contains a committed row with `id = 1`, `n = 42`, and a 2 MiB string payload. Create an index on `n` including the payload. An isolated executable uses a `GlobalAlloc` wrapper around `System`, returning null for allocations/reallocations of at least 1 MiB only after arming immediately before `create_index`. Store creation, row insertion and commit run with the allocator unarmed. The index operation prints:

```text
arming allocator; only allocations >= 1 MiB will fail during create_index
memory allocation of 2097156 bytes failed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
probe_exit_code=-1073740791
```

The operation never returns; the isolated process exits with `0xC0000409`. This simulates the system refusing a valid payload allocation without exhausting the review host's memory. Such refusal is reachable under memory pressure, particularly when a temporary store retains all sorted entries in memory. No corruption or undefined behavior is asserted.

**Requirement:** S1, IX2 and its P13 annotation, with AC-IX14's resource-failure coverage and T11. IX2 explicitly says: «si el sistema no la da, la creación falla con memoria agotada (P13), con T11». The infallible row encoder predates this range; the finding concerns its newly introduced use to allocate index-sort payloads, and the new entry-key allocation.

**Coverage gap:** `ac_ix14_a_temporary_store_sorts_in_memory_only` injects `Op::Alloc` failures into instrumented reservations. It does not exercise these infallible content allocations.

**Suggestion:** make index-entry content allocations fallible and propagate allocation failures through the transaction's failure tracking.

<a id="R2"></a>
### R2 — Major: Index identities and states accept values already known by the catalog

**Location:** `crates/krummi/src/table/index.rs:702` and `:735`; helper `crates/krummi/src/table/catalog.rs:792`.

Creation and dropping use `known_identity(history, value)`, which searches only the current table's schema-history tree. That history excludes the table's own identity (`schema.rs:526–529`) and cannot contain the current identities/states of other tables. The local check between a newly drawn index identity and its state does not close this gap. Consequently, Describe can expose index identifiers and states equal to known catalog values instead of redrawing them.

**Concrete scenario and experimental evidence:** using the public identity-source test hook, create `t(id i64 not null, n i32)` with draws `[10, 20, 21, 30, 40]` (table, columns, schema state, index state). Create the same schema as `u` with `[100, 110, 111, 120, 130]`. For creating `t.ix(n)`, provide `[10, 100, 50, 60]`; for dropping it, provide `[110, 70]`. Observed output:

```text
create: table_t=10 table_u=100 index=10 state=100
drop: table_u_column=110 state=110
```

The transaction commits successfully. Thus the new index identity duplicates `t`'s identity; its creation state duplicates `u`'s identity; and its drop state duplicates a column of `u`. The remaining source values would have been available for correct redraws. This is a deterministic reproduction of a required collision-handling case, not a claim that ordinary random draws collide frequently or that current row data is corrupted.

**Requirement:** S1/S3, IX6, AC-IX11 and design document 11, lines 247–258. IX6 requires values to be redrawn «si coinciden con uno que el almacén conoce». The design explicitly includes values in the store catalog or the table's schema history. Related incomplete column/schema-state collision checks already exist at the base; this finding is limited to the new index-identity/index-state draws.

**Coverage gap:** `ac_ix11_identities_equal_to_known_ones_are_drawn_again` repeats local column/state/index values, but omits the table identity and values belonging to another table.

**Suggestion:** include known catalog values, as well as the table's history and newly drawn values, in every index-identity/state collision check.

<a id="R3"></a>
### R3 — Major: A failed store opening deletes krummi.sort

**Location:** `crates/krummi-pager/src/recovery.rs:111`; subsequent validation in `crates/krummi-tx/src/lib.rs:234–247`.

Recovery removes `krummi.sort` before `Engine::new` reads and validates the transaction metadata page. A store with valid headers/journal but damaged transaction metadata therefore loses its sort files even though `Store::open` ultimately fails. Cleanup on scratch drop must also respect failure of the overall opening (`scratch.rs:708–715`, `:955–962`).

**Concrete scenario and experimental evidence:** create a store and table, commit and close successfully, then create `krummi.sort/run.probe` containing `retain on failed open`. Flip one payload byte at offset `2 * 8192 + 16` of `krummi.data`, making metadata page 2 fail its checksum. Reopen through `Store::open`. It returns `Damaged { page: Some(2) }`; afterward:

```text
sort_exists=false run_exists=false
```

The probe only manipulates its disposable store. The demonstrated deletion affects discardable sorting files, not committed rows or unrelated external files.

**Requirement:** S1, IX2 and AC-IX14: «una apertura que falla no lo borra». The analogous earlier temporary-area cleanup is not reported as a new defect; deletion of `krummi.sort` is introduced by this range.

**Coverage gap:** the failed-opening tests cover failures before this later metadata validation and failure of removal itself; they do not cover an opening rejected after recovery has succeeded.

**Suggestion:** defer sort cleanup until all validations that can reject the opening succeed, including cleanup performed during destruction of a partially opened engine.
