## Open findings

<a id="R3"></a>
### R3 — Major — AC-IX9 contradicts raw validation for invalid definitions that normalize to an existing index

- **Location:** Acceptance criteria / AC-IX9, `docs/prd/krummi/tables/tables-indexes.prd.md:254`–255; Decisions / IX1 (`:46`), IX2 (`:47`), IX3 (`:48`) and IX10 (`:55`).
- **Status:** open; new regression caused by the R1 fix. The original ownership conflict is resolved, as recorded below.
- **Problem:** Removing primary-key columns from included-column definitions creates invalid inputs that compare equal to a valid stored definition after normalization. The existing-name error expectation in AC-IX9 does not account for this case and contradicts the newly explicit raw-input validation rule.
- **Reproduction:** A table has primary key `id: string`, another column `v`, and an existing non-unique index `ix` with key `[v]` and included columns `[]`. Request **Crear si no existe** for `ix` with the same uniqueness and key, but included columns `[id, id]`.
- **Evidence:** IX1 now requires «las reglas de IX3 se comprueban antes, sobre la definición tal como se da». IX3 rejects «una columna repetida en la clave, en las incluidas o en las dos» with **esquema no válido**. Thus the repeated `id` must be rejected before its removal can hide the repetition. However, AC-IX9 expects, for «un nombre que existe con una definición no válida», «en Crear si no existe (esquema distinto)». Under IX2, comparison omits primary-key included columns: both definitions have key `[v]` and included columns `[]`. There is no normalized difference to report as the required first difference, and IX10 assigns esquema distinto to «Crear si no existe con otra definición».
- **Observable readings:** Following IX1/IX3 returns **esquema no válido**, with the repeated column and rule. Following the existing-name/invalid-definition case in AC-IX9 returns **esquema distinto**, requiring a difference that the normalized comparison does not contain. The criterion therefore supplies a conflicting test oracle for this input; this is an observable error-class difference, not an implementation choice.
- **Causal evidence:** At the base revision, included lists `[]` and `[id, id]` remained different for definition comparison. The fix introduces primary-key removal and hence the invalid-but-normalized-equal case. The contradictory interaction is caused by the correction even though the generic error expectation already existed.
- **Suggestion:** Limit AC-IX9's esquema distinto case to different normalized definitions and explicitly cover raw repeated primary-key inclusions that normalize to an equal definition.

Non-primary included values retain the existing borrowing contract.
- **Result:** The ownership defect and its product question are resolved. R3 is a distinct error/acceptance regression from the normalization used by this fix.
