<a id="R2"></a>
### R2 — Blocker: Sampling still reads entire runs containing large values

- Status: **still open**, explicitly pending in the resolutions and ODD T7b; no partial-run implementation was supplied in this range.
- Locations: `crates/krummi/src/table/statistics.rs:482`, `:499`, `:619`; `crates/krummi-tree/src/lib.rs:613`, `:352`.
- **Verifiable technical evidence:** whole-table sampling uses row scans that resolve whole rows; sampled leaf visits likewise call `resolve` before invoking their visitor. `resolve` calls `tx.run(first, count)` for a run, reading/verifying the complete run. Only afterwards does `Gather::add` classify a large field. A valid row with a small estimable field and a multi-MiB blob therefore requires reading the blob when estimating the small field, in read and write sampling. Damage in pages that sampling must skip can also fail this operation. The dependent resolver is unchanged by these fixes.
- Requirement: S1, ST1: «Los **valores grandes** […] no se leen» and «sin verificar la suma de comprobación del tramo entero»; ST14/AC-ST12's page-count verification is still absent. The original and round 2 failure analysis remains applicable.
- Suggestion: implement partial run/row reads and assert which pages sampling actually reads.

<a id="R4"></a>
### R4 — Major: Ordered shortened bounds still lose interval accuracy with long common prefixes

- Status: **still open, partially corrected**. The four round 2 intervals with a 64-byte common prefix now satisfy the allowance, but ordering the shortened bounds does not preserve their position relative to actual values.
- Locations: `crates/krummi/src/table/stats.rs:208`, `:234`–`:263`; `crates/krummi/src/table/estimate.rs:373`–`:377`.
- Failure: `shorten` chooses a prefix greater than the previous *shortened* bound; `fraction` then treats it as an exact upper bound. With a sufficiently long common prefix, many successively longer prefixes remain below every actual value, so intervals containing those values exclude their buckets.
- **Independent experimental evidence:** use the original 10,000-row distribution: 4,000 `A`, 1,000 nulls and 50 occurrences of each suffix `000`–`099`. Analyze, then estimate the same four inclusive suffix ranges. Compare a common prefix of 64 `B`s with 997 `B`s; the latter makes every nonfrequent string exactly 1,000 bytes, below the large-value threshold and explicitly anticipated by AC-ST12. The latter histogram has 91 bounds of lengths 64 through 154, all below every actual suffix value.

  | Inclusive suffix range | Actual rows | Estimate, 64-byte prefix | Estimate, 997-byte prefix |
  |---|---:|---:|---:|
  | `050..099` | 2,500 | 2,425 | 0 |
  | `090..099` | 500 | 425 | 0 |
  | `000..099` | 5,000 | 4,875 | 450 |
  | `100..199` | 0 | 0 | 0 |

- The first and third long-prefix cases exceed the permitted absolute error of 500 rows. Their bounds are present in the table. The updated regression correctly uses 100 suffixes and passes its chosen 64-byte-prefix fixture, but that does not establish the general requirement.
- Requirement: S1, AC-ST1 and ST16; AC-ST12 explicitly includes strings of 1,000 bytes.
- Suggestion: preserve enough information about each bucket's actual position when shortening bounds and estimating intervals.

<a id="R11"></a>
### R11 — Major: Lifecycle epochs do not make retirement and publication consistent

- Status: **still open, partially corrected**. The original sequential zero-row emptying and the build held after sampling now pass, but the new epoch does not establish validity against the sampled snapshot or atomically guard publication.
- Locations: `crates/krummi/src/table/statistics.rs:467`; `crates/krummi/src/table/estimate.rs:97`–`:148`; commit dependency `crates/krummi/src/lib.rs:1591`–`:1593`, `:1604`–`:1606` and `crates/krummi-tx/src/transaction.rs:643`–`:651`.
- **Independent experimental evidence:** commit three rows in `t(id,n)` and index `ix(n,id)`, without statistics. Open read A and its table handle. In another write drop `ix` and `n`, and commit. Only then let A estimate `n = 1` from its old snapshot, and wait for statistics work to become idle. A obtains `Some(origin_rows=3)` column statistics and `Some` prefix statistics. Its snapshot predates all saved statistics, so these are republished memory entries for the removed targets. `build_statistics_until` captures the current epoch when sampling begins, even though A's snapshot predates the removal; publication accepts that epoch without checking the live targets.
- **Additional verifiable concurrency evidence:** `publish` reads the epoch and releases its mutex before acquiring either entry-map mutex. A publication can pass that check, pause, let `retire` increment the epoch and clear both maps, and then insert its invalidated entries. Entries retain no epoch that a later lookup could use to reject them.
- **Resolution evidence assessed:** the resolutions acknowledge that a save can get the turn between an emptying commit and retirement and save a zero-row build, arguing that it still describes the table. This does not satisfy ST6's explicit lifecycle discard. The transaction releases its turn before waiting for durability; retirement runs only after `inner.commit` returns. An old zero-row save can therefore pass both the old epoch and `counter >= emptied` (both counters zero), persist, and survive the later memory retirement. This is a source-established ordering defect; no timed execution of this particular window is claimed.
- Requirement: S1, ST1/ST6/ST8 and AC-ST6: removed targets must leave memory at commit, and invalidated builds must be discarded at publication/save, including zero-row emptying. Old snapshots may keep their own saved statistics; that does not authorize reintroducing removed shared entries.
- Suggestion: coordinate snapshot validity, committed lifecycle changes, publication and saving with an atomic validity protocol.

### R12 — Major: Cancellation still finalizes accumulated statistics

- Status: **still open, partially corrected**. The new check can abandon buffered row processing, but does not cover iterator cancellation or finalization.
- Locations: `crates/krummi/src/table/statistics.rs:172`, `:198`–`:214`, `:482`; `crates/krummi/src/table/stats.rs:131`, `:153`–`:226`.
- **Verifiable technical evidence:** for a table of at most 30,000 rows, `take_while(|_| !cancel())` can observe shutdown between rows and end the iterator before the new check inside `build`'s loop is reached. The loop ends normally and unconditionally calls every accumulated column/prefix gather's `finish`/`finish_combinations`, sorting and constructing the statistics. Cancellation during finalization also has no check, for small or large tables. `renew` discards the completed result only afterwards. This retains the construction portion of the original finding, despite correctly stopping further iteration in several paths.
- No shutdown latency was measured or specific time limit inferred. The passing close test holds `WorkSampled`, after construction, and does not verify cancellation during these operations.
- Requirement: S1, ST10: «cerrar detiene el muestreo en curso del hilo sin publicarlo ni guardarlo»; AC-ST7.
- Suggestion: propagate cancellation out of iteration and abandon gathering/finalization when shutdown is requested.

<a id="R16"></a>
### R16 — Major: Schema and index changes retire statistics that must be preserved

- Status: **new regression** in the R11 correction, `05d3d7f`.
- Locations: `crates/krummi/src/table/catalog.rs:209`, `:914`; `crates/krummi/src/table/index.rs:742`, `:775`; `crates/krummi/src/table/estimate.rs:97`–`:113`.
- Failure: every schema change, and every index creation/removal, sets `emptied`. Commit consequently retires every shared statistic for the table and increments its epoch, invalidating otherwise valid pending builds. Renaming a column, allowing nulls or changing an unrelated index must preserve the unaffected column statistics.
- **Independent experimental evidence:** open read A before analyzing a three-row table with `n` and a two-column index. Analyze on the store; A now sees column and prefix statistics from memory. Rename `n` to `m` in a committed write. A then sees neither column nor prefix statistics, despite the retained column/index identities and unchanged rows; A had no saved copies that could mask the memory loss.
- **Second independent reproduction:** hold store analyze at `WorkSampled`, after it builds the three-row table, rename `n` to `m` and commit, then release analyze. Analyze returns `Ok(())`, but a new read gets `None` for both `m` and the untouched `id` column: the renamed table's otherwise valid build was discarded at publication and save. AC-ST6 explicitly requires this paused rename case to publish, save and be readable under the new name. Existing preservation tests start with already-saved statistics and mask this regression.
- Requirement: S1, ST8, ST17 and AC-ST6: «renombrar una columna las conserva»; «Crear o borrar un índice no cambia las de las columnas».
- Suggestion: retire only invalidated targets and preserve valid statistics/builds across identity-preserving changes.

<a id="R17"></a>
### R17 — Major: Merging queued saves across lifecycle epochs drops the fresh sample

- Status: **new regression** caused by the `Built.epoch` field and save guard added in `05d3d7f`.
- Locations: `crates/krummi/src/table/worker.rs:80`–`:82`; `crates/krummi/src/table/statistics.rs:658`.
- Failure: merging `Save` jobs updates columns and prefixes but retains the queued build's old epoch. A fresh, valid post-emptying sample is therefore attached to an invalid generation and discarded as a whole by `save_statistics`.
- **Independent on-disk reproduction:** analyze a separate 1,000-row table `gate`, add 1,000 rows to make its statistics stale, and hold its background renewal at `WorkSampled`. Estimate one-row table `t`, queuing its epoch-0 save behind the held renewal. Empty/refill `t` and commit, advancing its epoch to 1. Estimate `t` again, building current statistics; the queue still reports one pending save because the requests merged. Release the renewal and wait for idle. Memory reports `Some(origin_counter=3)` for `t`, but after close/reopen its statistics are `None`. There was no injected failure or shutdown during work: the new sample was simply never saved. The queued epoch-0 build remains even though its statistics payload was replaced with the epoch-1 sample.
- Requirement: S1, ST3/ST6 and AC-ST2: the fresh sample's background save must persist unless that sample itself meets a discard condition.
- Suggestion: merge or replace queued saves with generation-aware semantics, retaining the validity of the fresh payload.
