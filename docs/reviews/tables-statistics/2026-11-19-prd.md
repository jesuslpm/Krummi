## Findings

All five findings below remain open. IDs are local to this report.

<a id="R1"></a>
### R1 — blocker — Analyze must publish statistics and also fail without effects

**Location:** Product decisions / ST1, ST7, ST16; Acceptance criteria / AC-ST9 (`tables-statistics.prd.md:50`, `:56`, `:65`, `:253`).

ST7 says store-level analyze constructs statistics, “lo publica en memoria (ST1) y después lo guarda”, and starts waiting for the write turn only after sampling. The validation table includes a timeout acquiring that turn. AC-ST9 nevertheless requires every listed failure to occur “sin efecto”. ST1 retains published statistics, and ST16 exposes them to the application.

Concrete counterexample: a populated table has no statistics; another thread holds the write turn; store-level analyze runs with a zero wait limit. It samples and publishes, then times out. A subsequent statistics read can now return statistics where previously there were none. Another reader can even observe the publication before the timeout, so removing it afterward cannot make the operation have had no observable effect.

**Incompatible readings:** keep the shared publication despite the save failure, as ST7 requires; or prevent any observable publication when analyze fails, as AC-ST9 requires. Both cannot hold as written.

**Suggestion:** specify which effects survive analyze failures after sampling and make AC-ST9 match that contract.

<a id="R2"></a>
### R2 — major — Estimate value-size limits inherited from IX9 are ambiguous

**Location:** Product decisions / ST2, ST12, ST18; Validations and messages (`tables-statistics.prd.md:51`, `:61`, `:67`, `:109`); dependency `tables-indexes.prd.md:54` / IX9.

ST2 adopts “Las reglas de los valores […] (IX9), con una diferencia”, identifying the null-equality exception. IX9 also rejects an encoded prefix with a bound exceeding 2,048 bytes, using **tamaño no válido** and a payload containing the table and index. ST12 and the validation table specify size errors for names, but do not map this prefix-size rule or its index payload to estimates of arbitrary columns. ST18 additionally accepts multi-column equality without resolving whether the cap applies separately or to the combined values.

A concrete input is equality against a 4,096-byte string in an unindexed column: it can be a valid row value under E18, but exceeds IX9's encoded-prefix cap.

**Allowed readings:** inherit only value-domain, normalization and logical-bound rules and accept the long value; or inherit the encoded-size cap and reject it. The latter also lacks a defined error payload when no index is involved, and a combined-size rule for multi-column equality. These choices change public results and are not listed under Left to the implementation.

**Suggestion:** explicitly state which size limits apply to estimates and define any resulting error data and precedence.

### R3 — minor — Starting state omits an existing thread and a row-count mutation path

**Location:** Starting state (`tables-statistics.prd.md:79`–`:83`).

Two assertions disagree with the current source:

- “El único hilo propio del almacén es el que lleva las páginas al archivo de datos”: `crates/krummi-pager/src/journal.rs:591` creates `krummi-journal`, in addition to `krummi-transfer` created at `crates/krummi-pager/src/transfer.rs:259`. Store startup creates both at `crates/krummi-pager/src/scratch.rs:336`; journal close joins its worker at `journal.rs:808`–`:819`.
- “Las escrituras que cambian el número de filas pasan por un mismo punto, salvo el camino rápido de añadir al final”: `empty_table()` directly sets `state.count = 0` at `crates/krummi/src/table/catalog.rs:650`–`:668`, bypassing `apply_rows()` at `crates/krummi/src/table/rows.rs:1479`–`:1507`. The append fast path is therefore not the only exception. This matters when locating every path that must maintain ST4's persistent modification counter.

**Suggestion:** correct the worker inventory and list table emptying as another independent row-count mutation path.

<a id="R5"></a>
### R5 — minor — AC-ST3 cannot observe the truncate increment through staleness

**Location:** Acceptance criteria / AC-ST3 (`tables-statistics.prd.md:206`–`:215`); Product decisions / ST4, ST8, ST16.

AC-ST3 includes “vaciar la tabla” among operations whose exact modification-counter additions are verified with “el contador, observado a través de ST5”. ST8 simultaneously removes all statistics when the table is emptied. There is then no statistic against which ST5 can report staleness, and an estimate samples again rather than exposing staleness relative to the removed origin counter.

The counter behavior is specified, but this observation method cannot establish the truncate increment. ST16 provides a usable alternative: compare origin counters before truncation and after analyzing again, accounting for intervening operations.

**Suggestion:** give the truncate case its own origin-counter assertion using ST16 and a subsequent analyze.
