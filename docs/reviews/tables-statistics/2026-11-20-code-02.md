### R2 — Verified resolved: Sampling page counter includes metadata beyond the first page

- Original ID: [2026-11-19-code.md#R2](2026-11-19-code.md#R2). Previous pending version: [2026-11-20-code.md#R2](2026-11-20-code.md#R2), minor. Fix verified at `3e0641a`, implemented by `aa0b474`.
- Locations: `crates/krummi/src/table/row.rs:508`, `crates/krummi/src/table/rows.rs:730`, `:1069`, `crates/krummi/src/table/statistics.rs:233`; regression test `crates/krummi/tests/table_statistics/build.rs:136`.
- **Source evidence:** `Reader::metadata_len` selects the stored row's layout, including `old.layout` for older versions. `RowLayout::row` validates the header and offset width and bounds `variable_start` by the stored byte length (`row.rs:373`). `run_metadata_pages` accounts for pages `0..=(PAGE_HEADER_SIZE + metadata_len - 1) / PAGE_SIZE`. `build` unions these with selected column ranges and deduplicates them. This includes the page containing the variable end offsets omitted by the previous hook. The added calculation does not traverse large payloads or change the resolver, decoding, persistence or transaction behavior.
- **Independent runtime evidence:** repeated the previous valid-input reproduction with `id i64 PRIMARY KEY`, 600 nullable `ulid` columns, `big bytes NOT NULL` containing 200,000 bytes and `tail string NOT NULL`. Analyzing only `big` now counts **2** pages for one row, with `rows_read=1` and `large_fraction=1`, rather than the previous incorrect count of 1. The supplied public regression test independently passed on disk and in memory: **10** pages for five rows when analyzing `big`, and **15** when analyzing all columns. The earlier narrow-row exclusion test also passed: two pages per run, excluding the large value's intervening payload pages.
- **Boundary verification:** an additional valid fixture at the 1,024-column limit (1,021 nullable `ulid` columns plus `id`, `big`, `tail`) reports three metadata pages. The accounting conservatively covers the entire metadata region, including intermediate pages that a selective analysis may not actually touch. It is not an operating-system page-fault trace. This over-approximation stays before the variable payload and does not invalidate AC-ST12's exclusion check; no exact hardware-access count is claimed. An exploratory 1,603-column fixture was rejected with `InvalidSchema` / `TooManyColumns`; it was replaced by this valid boundary fixture and is not evidence of a product failure.
- **Earlier reproduction independently rechecked:** create and close a disposable on-disk table `t(id i64 PRIMARY KEY, s string NOT NULL, blob bytes NOT NULL)` with `(1, "x", 200,000 bytes)`. Replace the four-byte variable end offset at `first_page * 8192 + 16 + 3` with little-endian `u32::MAX`, preserving its header. Analyze succeeds without an escaping panic; all three columns have `rows_read=1`, with large fractions `id=0`, `s=1`, `blob=1`. Ordinary `get_row` still returns `Damaged`. The package suite also independently passes the middle-of-blob corruption case. The previously corrected bounded-offset and integrity behavior remains intact.
