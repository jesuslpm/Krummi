### R11 — Major: Lifecycle generation can precede the sampled durable snapshot

- Status: **still open, partially corrected**. The callback closes the previously demonstrated writer-release window: retirement now runs after successful staging/publication and before releasing the write turn. Capturing a generation when opening a read also rejects builds from readers opened before retirement. Neither establishes the generation of the actual durable snapshot.
- Locations: `crates/krummi/src/lib.rs:274`, `:1610`; `crates/krummi-tx/src/transaction.rs:648`; `crates/krummi/src/table/estimate.rs:80`, `:151`, `:173`; `crates/krummi/src/table/statistics.rs:483`, `:673`, `:701`. Snapshot dependency: `crates/krummi-pager/src/scratch.rs:477`, `:685`.
- Failure scenario: W1 empties a zero-row table and commits in deferred mode. Retirement advances memory generation immediately, before that commit becomes durable. A new read captures this new generation, but its engine snapshot still precedes W1. A build from that read passes `retired_at <= epoch`; its counter also passes the floor because both remain zero. After W1 becomes durable, the build can be published and saved, despite originating before the emptying.
- **Independent experimental evidence:** a controlled probe created and durably committed an empty `t(id,n)`, paused the journal through the existing engine hook, then emptied `t`, created an `emptying_marker` tree in the same write, and called `commit_deferred`. A new reader had `statistics_epoch = 1` while `tree_exists("emptying_marker")` was false, establishing the snapshot/generation mismatch. A separate thread invoked the public `Store::analyze("t", None)`; waiting for the sample counter to advance proved its source read opened while the journal remained paused. The probe then unpaused the journal and joined analyze. A new read saw the marker and `Some((origin_rows=0, origin_counter=0))` statistics. Closing and reopening the disposable on-disk store still returned statistics. No I/O error was injected, and no timing sleep was required.
- The probe compiled the reviewed facade source from stdin, changing only its `ids`/`table` module declarations to absolute paths and appending the driver. The existing private journal scheduling hook controlled the schedule; sampling, publication, saving and lifecycle changes used the production public APIs. Production source files were not patched.
- **Resolution evidence assessed:** the resolutions explicitly permit a new read with a generation newer than its still-old durable snapshot, arguing that a zero-row build still describes the table. The reproduced persistence confirms that this is an unresolved behavior, not merely a theoretical window. ST6's discard rule depends on the lifecycle of the source snapshot, even when distributions/counters happen to be equal. E3 explicitly permits this read visibility schedule. The “still describes the table” justification therefore does not satisfy the requirement.
- Requirement: S1/ST1/ST6/ST8/AC-ST6: discard «si la tabla se vació después de su instantánea de origen»; on emptying, «entonces no se guardan». This demonstrates invalid statistics persistence, not loss of row data.
- Suggestion: validate builds against their effective source snapshot, including commits pending durability.
