<a id="R1"></a>
### R1 — Blocker: Sampling damage does not invalidate the requesting write

- Location: `crates/krummi/src/table/estimate.rs:634`, `:644`.
- Failure: `sample_built` opens a separate read transaction and propagates its failures with `?`, without recording them through the requesting write's `self.inner.fail`. A write can therefore encounter corruption in `estimate` and still commit earlier changes. Damage in the auxiliary reader does not poison a different transaction; the write's failure mechanism is in `crates/krummi-tx/src/transaction.rs:542`–`:568`.
- **Experimental evidence:** create a disposable on-disk table `t(id i64, n string)` with one sentinel row; close it, flip a byte inside that row in `krummi.data`, and reopen. Start a write, create an unrelated tree `previous-change`, and estimate `n = sentinel` in `t`. Observed: `estimate error Damaged`; `commit after estimate Ok(())`; a new read reports `previous change committed true`. Expected: commit fails with damage and applies nothing.
- Requirement: S1, ST3, T11 and AC-ST8: «en una escritura con daño, esta ya no puede confirmarse».
- Suggestion: transfer operational sampling failures from the auxiliary read to the requesting write's failure state.

<a id="R2"></a>
### R2 — Blocker: Sampling reads and verifies entire runs containing large values

- Location: `crates/krummi/src/table/statistics.rs:406`, `:424`; `crates/krummi-tree/src/lib.rs:613`.
- Failure: small tables use `range_rows`; large tables use `sample_leaves`, which resolves each complete value before invoking the callback. `resolve` calls `tx.run(first, count)` for the whole run (`crates/krummi-tree/src/lib.rs:352`–`:362`). `Gather::add` recognizes a large field only after those bytes have been read. There is no partial row/run reader on either path.
- **Technical evidence:** a valid table with small searchable fields and multi-MiB blobs makes its first estimate read/checksum every blob in the selected rows. Sampling approximately 30,000 rows can read hundreds of GiB instead of only row headers and small fields. This also rejects damage in skipped blob pages where ST1 explicitly permits partial sampling. ODD T7b and L7 expressly record this implementation as pending at the reviewed head.
- Requirement: S1, ST1: «Los valores grandes […] no se leen» and «se muestrea leyendo solo su primera página […] y las páginas de sus columnas que no son grandes, sin verificar la suma de comprobación del tramo entero»; ST14 and AC-ST12 require page-read evidence, which is absent.
- Suggestion: complete the bounded partial run reader and its page-read assertions.

<a id="R3"></a>
### R3 — Major: Private statistics survive emptying and override newer analyzed statistics

- Location: `crates/krummi/src/table/estimate.rs:576`–`:596`; `crates/krummi/src/table/statistics.rs:464`–`:475`.
- Failure: a private cache entry wins unconditionally over saved/shared statistics and is not filtered by the table's emptying marker. Emptying and analyzing do not invalidate or supersede it. The multicolumn column lookup has the same issue at `estimate.rs:531`.
- **Experimental evidence:** in one write, create 1,000 rows with `n=1`, estimate them, empty the table, and refill it with 1,000 rows with `n=2`. After emptying, `column_statistics` still reports `(origin_rows=1000, origin_counter=1000)`. After refilling, equality `n=1` estimates 1,000. Run `write.analyze(None)`: the statistics read and estimate still use that old counter/distribution. After commit, a new reader correctly reports counter 3,000 and estimates zero. Thus this is incorrect cache selection, not unavoidable statistical imprecision.
- Requirement: S1, ST1 (newest visible statistics), ST7, ST8 («vaciar la tabla […] quita todas»), AC-ST6 and AC-ST14.
- Suggestion: apply emptying invalidation and newest-version selection to private entries too.

<a id="R4"></a>
### R4 — Major: Shortened histogram bounds can turn a 2,500-row interval into zero

- Location: `crates/krummi/src/table/estimate.rs:269`–`:290`; shortening in `crates/krummi/src/table/stats.rs:232`.
- Failure: range overlap compares a shortened prefix as an exact upper bound and ignores `bucket.shortened`. Multiple real bounds sharing a prefix collapse below a valid lower bound.
- **Experimental evidence:** analyze 10,000 rows: 4,000 strings `A`, 1,000 nulls, and 50 occurrences of each `B` repeated 64 times followed by `000` through `099`. Query the inclusive interval from that prefix plus `050` to the prefix plus `099`. Actual count is 2,500; observed `Estimate { rows: 0.0, stale: false, joint: true }`. The frequent values contain `A` and suffixes `000`–`008`; all remaining histogram bounds shorten to the same prefix and are incorrectly excluded. This exceeds the allowed 500-row error on a whole-table build.
- Requirement: S1, AC-ST1 (at most 5% of table rows for intervals) and ST16's shortened bounds.
- Suggestion: account for the uncertainty of shortened bounds when evaluating histogram overlap.

<a id="R5"></a>
### R5 — Major: Joint estimates do not retry saving statistics held only in memory

- Location: `crates/krummi/src/table/estimate.rs:421`–`:426`, `:529`–`:547`.
- Failure: the read prefix lookup and every write multicolumn lookup discard `newest`'s `unsaved` result. Unlike single-column `seen_statistics`, they never request another save when fresh statistics exist only in memory.
- **Experimental evidence:** another thread holds a write while `Store::analyze_with_timeout("t", None, Duration::ZERO)` samples a committed table with index `(a,b)` and fails with `Timeout`. Release the writer. A read joint estimate and a write joint estimate both successfully use the fresh memory-only prefix, while `statistics_work()` remains `(false, 0, 0)` before and after both calls. No work is requested; closing loses the unsaved statistics. The same missing path prevents recovery after a retryable save failure.
- Requirement: S1, ST7 and ST9: «la siguiente estimación que use unas que solo están en memoria vuelve a pedir que se guarden»; AC-ST8/AC-ST9.
- Suggestion: request saves for every memory-only group used, including prefixes.

<a id="R6"></a>
### R6 — Major: Save polling loses its FIFO position every 20 milliseconds

- Location: `crates/krummi/src/table/worker.rs:259`–`:269`.
- Failure: each save requests the write turn with a 20 ms timeout. On expiration `Engine::wait_turn` removes its ticket (`crates/krummi-tx/src/lib.rs:755`–`:759`); retrying inserts a new ticket at the end.
- **Technical evidence:** writer A holds the turn, save S queues, then application writer B queues. Let A remain open beyond S's timeout. S leaves and rejoins behind B, so B overtakes S when A releases. Continuous arrivals can indefinitely postpone S and every statistics job behind it. This is a concrete permitted schedule, not a claim that the application FIFO implementation itself changed. ODD L9 records the same unresolved A5.
- Requirement: S1, ST6: «sin límite de espera, al final de la cola» and T4's arrival order.
- Suggestion: support shutdown cancellation while retaining a single FIFO ticket.

<a id="R7"></a>
### R7 — Major: Store analyze silently loses its save after a table rename

- Location: `crates/krummi/src/table/statistics.rs:619`–`:626`.
- Failure: after sampling a table by identity, store analyze only reopens its original name. A rename makes that lookup fail and the build is discarded even though its table still exists. The worker already resolves renamed tables by identity; this path does not.
- **Experimental evidence:** hold `WorkSampled`, run `store.analyze("t", None)` on another thread, rename `t` to `u` and commit, then release the hook. Analyze returns `Ok(())`. Reading `u` before close sees statistics in memory, but after closing/reopening `column_statistics` returns none. No estimate was run to trigger a separate save. ODD L9 also records unresolved A6.
- Requirement: S1, ST6, ST7, ST8 and AC-ST6: «cuando se renombra la tabla, entonces se guardan para ella con su nombre nuevo».
- Suggestion: resolve the sampled table's identity when analyze acquires its write turn.

<a id="R8"></a>
### R8 — Major: Builds from a write's own view scan the entire large table

- Location: `crates/krummi/src/table/statistics.rs:517`–`:519`; `crates/krummi/src/table/estimate.rs:660`–`:669`.
- Failure: write analyze and private estimate fallback use `range_rows` without the `WHOLE` sampling branch used for read transactions. They collect all values while holding the application write turn.
- **Experimental evidence:** insert 60,000 rows into a table in a write and call `write.analyze(None)`. Its `column_statistics(...).rows_read` is 60,000. The same unconditional traversal is used by estimates when the table, required column/index, or post-emptying view is private. Work and collection memory scale with the whole table instead of the sample.
- Requirement: S1, ST1: «Una tabla de hasta 30.000 filas se lee entera; una mayor, por una muestra»; ST3, ST7, AC-ST12/AC-ST14.
- Suggestion: share sample selection between read and write sources.

<a id="R9"></a>
### R9 — Major: Private index-prefix statistics are discarded between estimates

- Location: `crates/krummi/src/table/estimate.rs:49`, `:542`–`:547`, `:671`–`:675`.
- Failure: private storage retains columns only, although private sampling builds index prefixes too. Subsequent joint estimates cannot find their prefix; `WriteTransaction::index_statistics` cannot read it either.
- **Experimental evidence:** create a table with index `(a,b)` in a write, insert a row, and estimate equality on `(a,b)` twice. The sample counter increases by **two**, rather than reusing the first private sample. ODD L7 explicitly records repeated sampling as its chosen implementation deviation.
- Requirement: S1, ST3, ST17 and AC-ST6: «otra estimación de la misma escritura no vuelve a muestrear».
- Suggestion: retain private prefix statistics with the same visibility and invalidation rules as private columns.

<a id="R10"></a>
### R10 — Major: Estimating a table that replaces another object fails with its old type

- Location: `crates/krummi/src/table/estimate.rs:635`–`:648`.
- Failure: the committed-snapshot lookup falls back to private sampling only on `TreeNotFound`. A different object type occupying the same name is also absence of the required table identity, but is propagated as an error.
- **Experimental evidence:** commit a normal tree named `t`; in a new write delete it, create table `t`, and insert a valid row. Estimating that table returns `Err(DifferentTreeType { name: "t", found: Normal, requested: Table, ... })` from the auxiliary committed view. The current write's table is valid and should be sampled privately.
- Requirement: S1, ST3: «Si en esa instantánea la tabla no existe o no es la misma […] lee lo que ve la escritura».
- Suggestion: treat a different committed object type as absence of the requested table identity.

<a id="R11"></a>
### R11 — Major: Shared statistics are not retired or checked against committed lifecycle changes

- Location: `crates/krummi/src/table/estimate.rs:99`–`:121`; `crates/krummi/src/table/catalog.rs:714`–`:720`.
- Failure: `StatsMemory` has insertion/lookups but no retirement on committed drop/empty/schema changes. Publication checks only another memory entry's counter, without checking whether the sampled identity still exists or was emptied. Removed identities accumulate until store close and a stopped old build can publish after its object was removed. Filtering by modification counter alone also cannot identify an emptying that removed zero rows.
- **Experimental evidence:** create and commit an empty table; analyze it on the store (memory statistics have counter zero); empty it again and commit. A new read still gets `Some` statistics: `emptied` remains zero and `newest` accepts the old entry with `counter >= emptied`. Expected: no statistics after emptying. Nonempty cases happen to advance the counter, which masks this in the current test. The lack of retirement is also directly verifiable in the complete `StatsMemory` implementation.
- Requirement: S1, ST1, ST6, ST8, AC-ST6: memory statistics end when their objects disappear or the table is emptied, at commit; late publication must discard them.
- Suggestion: track committed lifecycle invalidation and validate publication against it, including zero-row emptying.

<a id="R12"></a>
### R12 — Major: Closing cannot cancel an active background sample

- Location: `crates/krummi/src/table/worker.rs:107`–`:118`, `:240`–`:250`; `crates/krummi/src/table/statistics.rs:395`–`:449`.
- Failure: stop sets a flag and joins, but `renew` checks that flag only after `build_statistics` returns. Neither row iteration, leaf sampling nor gathering accepts/checks cancellation.
- **Technical evidence:** close while a renewal is still reading its sample. The worker continues every planned read and the full statistics construction before noticing stop and discarding the result. Close waits for that work; with large runs R2 further amplifies the delay. The existing close test stops at `WorkSampled`, after all sampling, and does not exercise cancellation during reads. No wall-clock latency claim was measured.
- Requirement: S1, ST10: «cerrar detiene el muestreo en curso del hilo sin publicarlo ni guardarlo»; AC-ST7.
- Suggestion: observe the stop signal within sampling and gathering, and abandon the partial build.

<a id="R14"></a>
### R14 — Minor: Frequent-combination ties ignore the index's direction and null order

- Location: `crates/krummi/src/table/statistics.rs:143`–`:147`, `:310`–`:318`.
- Failure: prefix combinations are encoded/ordered ascending with nulls first regardless of the actual index definition. Tie selection and returned order therefore use the wrong ordering.
- **Experimental evidence:** two rows `(n,id)=(1,1),(2,2)`, index `(n DESC,id ASC)`, analyze and read index statistics. Returned frequent combinations are `[(1,1), (2,2)]`, both fraction 0.5; the required index order is `[(2,2), (1,1)]`. `Nulls::Last` has the analogous source-level error. ODD L9 records unresolved A2.
- Requirement: ST16, AC-ST13: «a igual fracción, en el orden del índice (N5, con su dirección y sus nulos)».
- Suggestion: use the real index ordering to select and order tied combinations.

<a id="R15"></a>
### R15 — Minor: Validation is interleaved instead of following ST12 precedence

- Location: `crates/krummi/src/table/estimate.rs:715`–`:717`; `crates/krummi/src/table/statistics.rs:607`–`:610`.
- Failure: each multicolumn name is immediately resolved against schema before all name sizes are validated; store analyze opens the table before validating its column name. Write APIs likewise resolve a deleted handle before checking name size.
- **Experimental evidence:** a condition with pairs `[("missing", value), ("", value)]` returns `DifferentSchema`; ST12 requires `InvalidSize` for the empty name first. **Technical evidence:** `analyze("missing", Some(""))` similarly reaches `open_table` before `stats_column`, so it returns `TreeNotFound` instead of the higher-precedence invalid column name. These are defined precedence rules, not product questions.
- Requirement: S1, ST12 and AC-ST9: «después el tamaño no válido de los nombres; después árbol no encontrado […] después esquema distinto».
- Suggestion: validate all name sizes before handle/catalog/schema resolution, then values.
