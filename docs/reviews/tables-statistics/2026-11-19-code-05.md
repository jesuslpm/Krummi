### R11 — Major: Lifecycle invalidation still races with commit publication

- Status: **still open, partially corrected**. Removed-target tracking fixes the sequential old-snapshot column/index reproduction. Moving retirement after `inner.commit()` reopens the writer-release window already identified in round 3.
- Locations: `crates/krummi/src/lib.rs:1592`, `:1595`, `:1607`; `crates/krummi/src/table/estimate.rs:154`; `crates/krummi/src/table/statistics.rs:671`, `:699`; dependency `crates/krummi-tx/src/transaction.rs:644`–`:647`.
- Failure scenario: build statistics from an empty table and pause before publishing. W1 empties the same table and commits; its inner transaction publishes and releases the write turn, but W1 has not yet executed statistics retirement. The old build still has the accepted memory epoch, and its origin counter and the committed emptying counter both equal zero. It can publish and obtain the next write turn to save. W1's eventual retirement clears memory but does not remove those newly persisted statistics.
- **Independent experimental evidence:** a controlled harness built the empty table's statistics through the production builder, then held W1 at the existing `krummi_tx::Point::CommitWait` hook, after writer release. It resumed the exact publication/save continuation used after `Store::analyze`'s `WorkSampled`: `publish`, a fresh write, `save_statistics`, and commit. After releasing W1, a public statistics read returned `Some(origin_rows=0, origin_counter=0)`. Closing and reopening the disposable on-disk store returned the same saved statistics. The invalidated build survived the emptying without any injected I/O failure.
- This harness compiled the reviewed facade source from stdin, changing only its two module declarations to absolute paths and appending the probe, so it could use the existing private builder/save methods and engine hook. Reviewed production logic and repository files were not patched. A preceding public-API timing probe did not reach the window and is not used as evidence of failure or correctness.
- **Resolution evidence assessed:** catalog identity/column/index checks do reject removed targets; the new floors reject counters strictly below an emptying counter. They do not reject this equal-counter zero-row build before retirement, and neither check atomically connects retirement to commit publication. An epoch read after opening a snapshot is likewise not a snapshot generation. The claim that catalog checks cover the post-commit window is therefore refuted.
- Requirement: S1/ST6/ST8/AC-ST6: «si la tabla se vació después de su instantánea de origen» the build is discarded; «cuando se vacía la tabla, entonces no se guardan». This is invalid statistics persistence, not demonstrated row-data loss.
- Suggestion: coordinate lifecycle invalidation with effective commit publication and validate builds against their source snapshot.
