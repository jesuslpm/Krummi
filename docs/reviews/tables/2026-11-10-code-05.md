### R6 — Spill records now preserve fixed-width primary keys within tree limits

- Status: **verified resolved**, preserving [original R6](2026-11-10-code.md#R6) and its subsequent corrections through [round 4](2026-11-10-code-04.md#R6).
- Location: `docs/design/tables/08-execution-plans.md:200`.
- Related contracts: spillable `Sort` and unchanged output columns at lines 101 and 107–113; batches at lines 174–180; fixed-width PK omission at `01-row-format-and-types.md:204–211`; B6 at `docs/prd/krummi/trees.prd.md:46`.

The run retains the unchanged table row in one normal tree and its encoded primary key, followed by computed values, in a second tree under the same eight-byte sequence key. The added PK supplies the fixed-width columns omitted from the raw row, both for merge comparisons and for returning the input columns. The prescribed representation no longer loses the original row identity.

Independently repeated the previous information-loss example: with schema version 1, a `u64` PK and non-null payload `78`, IDs `{1,2}` and `{101,102}` still have identical raw rows `01 00 00 78`, but now produce different auxiliary records. A read-only Python model reconstructed their descending IDs, including `u64` boundary values and an auxiliary `f64`. A separate two-run merge over identical raw rows reconstructed `[256,255,102,101,2,1]` from the paired PK records. These are checks of the documented encoding, not executions of an implemented query engine.

The earlier size counterexamples also remain repaired: a 100 MiB zero-filled payload needs a 104,857,603-byte raw row, below B6's 268,435,456 bytes. The 209,715,202-byte escaped sort key is not stored alongside it. Run keys are eight bytes; the original encoded PK remains at most 2,048 bytes and is stored as a value, so adding a distance does not exceed the tree-key limit. Computed extras in the specified first-version expression model are `f64`; even the conservative bound of one such extra per byte of the entire 1 MiB plan, plus the maximum PK, is only 8,390,656 bytes. Separating the records also preserves exact-limit raw rows without adding bytes to their values.

Checked the reused source invariants directly: public `set` validates keys and values (`crates/krummi/src/lib.rs:869–873`, `:1437–1442`), `MAX_KEY`/`MAX_VALUE` remain 2,048/268,435,456 (`krummi-tree/src/node.rs:31–33`), lower-level writes assert those limits (`krummi-tree/src/lib.rs:696–705`), and off-leaf resolution returns borrowed run bytes (`:310–322`). The correction does not change transaction, partial-write or borrowed-read behavior. Scratch structures remain disposable per query; failure does not commit table data. The lifetime rule at `08:242–244` discards the context on any error, covering a failure between writes to the two trees without publishing a partial run. No new durability or lifetime defect was established.
