<a id="R6"></a>
### R6 — Combined spill records can still exceed the normal tree's value limit

- Severity: **major**. Status: **still open, partially corrected**.
- Location: `docs/design/tables/08-execution-plans.md:200`.
- Related requirements: spillable `Sort` (`08:101`), column ordering (`04-query-tree-and-planner.md:39`), the current row-size design (`01-row-format-and-types.md:285–289`; `02-row-storage.md:30`, `:180`) and B6 (`docs/prd/krummi/trees.prd.md:46`).
- Evidence type: independently checked representation-size argument against existing source preconditions, not an executed future-query failure.

The correction correctly switches to a normal tree with eight-byte big-endian sequence keys. It removes both the original oversized tree-key problem and the previous fixed-tree restrictions on variable/off-leaf values. However, the normal tree's single value contains **the encoded sort key plus the row**. A valid row fitting B6 does not establish that this combined record fits B6.

Consider a table with a small integer PK and one non-null, nonindexed `bytes` column containing 100 MiB of zeros. Request the whole row, ordered by that column. The specified row layout has three header bytes, no null bitmap and no end-offset entries for its one variable column (`01:169–194`): **104,857,603 bytes**. Its tuple sort key contains a type byte, two bytes for each escaped zero, and a terminator (`03-keys-and-indexes.md:151`): **209,715,202 bytes**. The spill value therefore needs at least **314,572,805 bytes**, exceeding B6's **268,435,456** by **46,137,349 bytes**, before any record framing.

The current design explicitly admits rows up to 256 MiB. With the configurable query memory budget set to 512 MiB, one such approximately 300 MiB record fits and another can force a spill, while two records remain below the default 1 GiB spill budget (`08:155–164`). The spill fails because the representation is too large, before that budget is exhausted. The public normal-tree write validates this limit before mutation (`crates/krummi/src/lib.rs:869–873`, `:1441–1442`; `MAX_VALUE` at `crates/krummi-tree/src/node.rs:33`). Direct lower-layer use also violates an asserted precondition (`crates/krummi-tree/src/lib.rs:702–705`). Off-leaf storage does not remove the value limit.

The final maximum table-row size remains assigned to 7.1 (`tables.prd.md:91`; design 2's question 5 at line 309). A sufficiently smaller ceiling could avoid this example, but the delivered design currently admits 256 MiB and provides neither a combined-record size guarantee nor another representation. This finding does not select that product ceiling.

Suggestion: reconcile the complete spill-record representation with B6 over the admitted row and sort-key domain.

### R4 — Corrected zero-copy rules still conflict with dependent descriptions

- Severity: **minor**, reduced from major. Status: **partially resolved; documentary inconsistency remains**.
- Locations: `docs/design/tables/03-keys-and-indexes.md:367–374`, `04-query-tree-and-planner.md:201`; related layout at `02-row-storage.md:180`.
- Requirements: table Output at `docs/prd/krummi/tables.prd.md:115`, AC-N1, D11/T16; Output promises `string`, `bytes` and vector values “sin copiarlos”.
- Evidence type: contradictory design statements, checked against the original concrete byte counterexample.

The substantive fix is verified: document 1 stores variable PK columns raw in the row; the corrected document 3 rule requires an included raw value or row lookup for variable key columns (`03:312–319`); planner covering eligibility now excludes variable key columns without raw storage (`04:168`); corrected Rust/C/C# access descriptions read those values from the row (`04:213–218`; `06-c-interface-and-csharp.md:195–200`). The original logical bytes `41 00 42`, whose tuple is `01 41 00 FF 42 00`, now have a valid zero-copy storage/fetch/accessor path.

Nevertheless, document 3's decided primary-index description still says the row omits all PK columns (`:367–368`), and its covering definition still counts every key/PK column (`:372–374`). Document 2's decided storage table repeats the omission (`:180`). Document 4's batch definition still says PK columns are read from the key (`:201`).

For the original bytes PK with a secondary integer index and no included columns, the corrected planner requires a row fetch, while the remaining covering definition calls the same request index-only. The escaped key cannot supply the logical bytes as a contiguous slice. These statements therefore prescribe different layouts/read paths for the same request. The explicit corrections provide a correct implementation path, so the remaining defect is limited documentary inconsistency, rather than the former major impossibility.

Suggestion: synchronize the remaining layout, covering and batch descriptions with the corrected fixed/variable distinction.
