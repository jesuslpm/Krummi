<a id="R4"></a>
### R4 — Index-only reads still cannot return variable primary keys without copying

- Severity: **major**. Status: **still open, partially corrected**, preserving [original R4](2026-11-10-code.md#R4).
- Location: `docs/design/tables/03-keys-and-indexes.md:312`, secondary-index representation at line 334; dependent covering rule at `docs/design/tables/04-query-tree-and-planner.md:168`.
- Requirements: N1's traversal through indexes (`docs/prd/krummi/tables.prd.md:43`), Output at line 115, AC-N1 and T16. Output requires `string`, `bytes` and vector values “sin copiarlos”.
- Evidence: verifiable representation/access-path argument, with an independently executed byte reproduction of the original counterexample.

The fix correctly stores `string` and `bytes` PK columns in the clustered row (`01-row-format-and-types.md:204–211`). It does not reconcile the paths that omit that row. A secondary index still stores `tuple(index columns) ‖ tuple(pk)` as its key, with only included columns, or an empty value (`03:332–335`). Document 3 still says an index-only scan needs no row read (`03:312–313`); document 4 skips the fetch when the requested columns are in the key or PK (`04:168`).

Consider a table whose PK is `bytes = 41 00 42`, with a secondary index on an integer and no included columns. A scan returning the PK from that index has only `01 41 00 FF 42 00` for the PK. The original `41 00 42` is not a contiguous slice of that representation; the reproduction confirmed its absence. The new raw copy is in the clustered row that this path expressly skips. The path must therefore copy/unescape, return different bytes, or fetch that row contrary to its covering rule. The fix provides storage from which a correct read is possible, but still prescribes a path that cannot meet the contract.

The downstream accessors also continue decoding every PK column from the key while promising zero-copy spans (`04:213–217`, `06-c-interface-and-csharp.md:195–198`). Exceptions for computed values do not cover this stored `bytes` column. This is the remaining original read-contract incompatibility, not a newly expanded review of unrelated query behavior.

Suggestion: reconcile covering eligibility and PK accessors with the new raw-value location and the zero-copy contract.

<a id="R6"></a>
### R6 — Spill runs still violate the reused tree's value constraints

- Severity: **major**. Status: **still open, partially corrected**, preserving [original R6](2026-11-10-code.md#R6).
- Location: `docs/design/tables/08-execution-plans.md:200`.
- Requirements: spillable `Sort` (`08:101`, `:190–200`), ordering of admitted columns (`04-query-tree-and-planner.md:39`), and X1/X2 (`docs/prd/krummi/trees-fixed-size.prd.md:40–41`).
- Evidence: source/contract argument and independent public-API reproduction.

The correction moves the encoded sort key and row into the value of a **fixed-size tree**, keyed by a `u64` run position. It claims large values go off-leaf. However, this tree type requires one constant value length between 0 and 2,048 bytes. X1 explicitly says: “En los árboles de tamaño fijo no hay valores fuera de su hoja (5.3)”.

The original valid input still fails: an orderable `bytes` value of 3,000 bytes produces an encoded sort key of at least 3,002 bytes, before adding the row. Opening a fixed tree for even that lower bound fails in `fixed_kind` (`crates/krummi/src/lib.rs:1453–1457`). The public-API reproduction returned `InvalidSize { what: Value, received: 3002, min: 0, max: 2048, ... }`.

The replacement also cannot hold ordinary variable-length run records below the cap. `set_fixed` checks every value against the exact tree length (`lib.rs:1038–1039`, `:1462–1463`). The reproduction accepted a 16-byte record and rejected a 17-byte record in the same run with minimum and maximum both 16. Moving the sort key out of the tree key removes the original key overflow but transfers the unrepresentable data into a more restrictive value representation. Valid sorts still cannot spill before exhausting the configured spill budget.

Suggestion: specify a run representation supporting both variable-length and oversized records within the actual reused storage constraints.

## Verified resolutions

<a id="R1"></a>
### R1 — Failed-load statistics criterion assumes whole-load atomicity

**Verified resolved.** AC-N8 now permits only load rows that remained committed according to 7.1, with none if the load fails whole (`tables.prd.md:251–253`). The associated design test agrees (`03-keys-and-indexes.md:465–468`). Rechecked the original scenario: batch one commits, sampling opens a read snapshot, and a later batch fails. That snapshot can sample batch one's committed rows without contradicting AC-N8. Whole-load rollback still leaves no committed load rows.

The correction preserves snapshot semantics (`03:417–440`), rather than requiring every subsequent commit to enter an older sample. Existing read transactions delegate to their snapshot (`crates/krummi-tx/src/transaction.rs:40–41`); snapshots open committed durable state (`crates/krummi-pager/src/scratch.rs:386–389`) and choose page versions no newer than their transaction (`:1132–1135`). Commit/abort inspection (`transaction.rs:484–538`) found no requirement to expose uncommitted data or undo an earlier committed batch.

<a id="R3"></a>
### R3 — Proposed vector arithmetic produces NaN for valid finite vectors

**Verified resolved.** Document 5 now converts elements before floating arithmetic, accumulates in `f64`, stores the norm as eight-byte `f64`, and returns `f64` distances (`05-vectors.md:134–175`, `:298–309`, `:323`); document 1's layout agrees at line 89. This repairs both intermediates and stored norm precision.

An independent Rust reproduction gave cosine zero for identical `[1e20_f32]` and `[1e-30_f32]`, and zero for the original cancelling dot product. It also checked identical `f32::MAX` and minimum subnormal vectors, positive finite norms, and finite arithmetic envelopes for 4,096 elements and extreme finite `i8` scales. Even the maximum `f32` norm is about `2.18e40`, and squaring the minimum subnormal in `f64` stays positive. The original NaN mechanism is removed. The updated golden-test specification includes the original cases. This checks the proposed arithmetic, not a future implementation's cross-platform bit identity.

<a id="R5"></a>
### R5 — Maximum-size primary keys generate bounds rejected by the reused trees

**Verified resolved.** Document 3 maps a synthetic `B ‖ FF` bound to `Excluded(B)` at the start and `Included(B)` at the end when `len(B) = 2048` (`03-keys-and-indexes.md:298–303`). No admissible stored key extends that maximum-length `B`, so both substitutions preserve the selected set. The existing API retains included/excluded bounds and validates their sizes (`crates/krummi/src/lib.rs:1468–1506`).

An independent Rust public-API reproduction stored the original 2,048-byte encoded PK together with keys before and after it. The 2,049-byte synthetic bound was rejected; both corrected 2,048-byte bounds succeeded and selected the expected rows, including/excluding the exact PK appropriately.

<a id="R7"></a>
### R7 — Decided row design contradicts the accepted schema and vector rules

**Verified resolved.** The three original contradictions are repaired: dropping a PK/index column fails without effect; allowing nulls on a previously NOT NULL non-PK column creates the new schema version without rewriting old rows (`01-row-format-and-types.md:232–240`); and `bit` dimensions must be multiples of eight (`:92–93`, `:312–314`). These agree with N3/N4 and AC-N2/N6/N7. The row's stored schema version continues to select its layout (`:167–193`, `:226–242`), preserving old-row interpretation when nullability changes. No causal regression was established.

<a id="R8"></a>
### R8 — Differential oracle requires equality for valid tied windows

**Verified resolved.** The corrected oracle requires admissibility and gives generated equality tests a total order by appending the PK (`11-query-contract-reconciliation.md:474–479`). Document 10's rule preserves multiplicity and admits either row from a tie group cut by a window (`10-agent-tooling.md:83–100`). An inline reproduction rechecked two tied rows under `LIMIT 1`: either singleton is admissible, while explicit ordering by the sort value plus PK yields one consistent answer. The original false-positive equality requirement no longer applies.
