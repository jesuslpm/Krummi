<a id="R1"></a>
### R1 — Failed-load statistics criterion assumes whole-load atomicity

- Severity: **major**. Status: **still open**, preserving [2026-11-10-prd.md#R1](2026-11-10-prd.md#R1).
- Location: `docs/prd/krummi/tables.prd.md:251`, Acceptance criteria / AC-N8; related child allocation / 7.1 at line 91 and AC-N3 at line 197.
- Evidence type: verified contradiction between requirements; unchanged from the earlier review.

AC-N8 requires, without qualification: “cuando una carga masiva falla mientras se construyen estadísticas en segundo plano, entonces las que se guardan no cuentan ninguna fila de la carga”. However, 7.1 expressly decides “si una fila con una clave repetida o un valor no válido hace fallar la carga entera sin efecto o solo esa fila” and “si cabe en una sola escritura”. AC-N3 correctly makes complete rollback conditional: “si 7.1 fija que la carga falla entera”.

If 7.1 permits earlier rows/batches to commit before a later failure, a background snapshot taken after such a commit legitimately samples those rows. AC-N8 nevertheless demands excluding every row of that load. `docs/design/tables/03-keys-and-indexes.md:458` assumes the atomic interpretation when explaining that the rows were never committed. Approximate statistics do not resolve the contradiction about which committed state may be sampled.

Suggestion: condition complete exclusion on whole-load atomicity and otherwise follow the committed-row semantics chosen by 7.1.

<a id="R3"></a>
### R3 — Proposed vector arithmetic produces NaN for valid finite vectors

- Severity: **major**. Status: **open**.
- Location: `docs/design/tables/05-vectors.md:129`; norm calculation at line 105 and prescribed `f32` accumulators at line 288.
- Requirements: N4's finite, nonzero cosine vectors; document 5 R1/R4 and its distance formulas.
- Evidence type: source-based causal argument and an executed Rust arithmetic reproduction.

Rejecting nonfinite inputs does not establish the claim that a stored-data distance is never NaN. For identical one-dimensional vectors `[1e20_f32]`, squaring produces infinity, the stored norm becomes infinity, and the prescribed cosine formula computes `1 - inf/inf`, yielding NaN instead of zero. Identical `[1e-30_f32]` vectors underflow to zero squares/norms and compute `0/0`. Both inputs are finite and nonzero, so the stated validation admits them. The query filter `cosine < 0.1` then drops an exact match. Negated dot product of `[1e20, 1e20]` and `[1e20, -1e20]` also produces NaN by adding positive and negative infinity, although its mathematical result is zero.

The coordinator compiled and ran the specified arithmetic in Rust; both cosine comparisons printed `false` and all three results were asserted NaN. Using `total_cmp` gives NaN an ordering but does not repair the distance or the filter. The stored `f32` norm and intermediate precision must be considered together; golden tests that merely mirror the existing operations would pin the wrong behavior.

Suggestion: specify arithmetic and norm storage that cover the admitted domain and add these inputs to the golden distance cases.

<a id="R4"></a>
### R4 — Primary-key-only storage cannot provide the promised zero-copy bytes reads

- Severity: **major**. Status: **open**.
- Location: `docs/design/tables/01-row-format-and-types.md:203`; tuple escaping in `docs/design/tables/03-keys-and-indexes.md:151`.
- Requirements: Output at `docs/prd/krummi/tables.prd.md:115`, AC-N1, D11 and T16 (`docs/prd/krummi/transactions.prd.md:45`).
- Evidence type: verifiable incompatibility between the specified stored representation and read contract.

The design omits all primary key columns from the row and decodes them from the tuple key. Consider a `bytes` primary key with original bytes `41 00 42`. Its only stored value representation is the tuple element `01 41 00 FF 42 00`: the original three bytes do not exist contiguously in that representation. Returning the logical value requires allocating/copying an unescaped buffer; returning a borrowed slice of the encoded element returns different bytes.

The table Output contract explicitly promises “los de `string`, `bytes` y vector, sin copiarlos”, while T16 says “nunca a una copia hecha para esa lectura”. The PRD's copy exception covers scalar types, not `bytes`. This example does not depend on whether 7.1 permits NUL in strings: AC-N1 explicitly covers embedded zero bytes in `bytes` keys. The open internal option to repeat primary keys only if measurements justify it does not settle this correctness constraint.

Suggestion: reconcile primary-key storage with logical zero-copy reads before treating omission as a performance-only choice.

<a id="R5"></a>
### R5 — Maximum-size primary keys generate bounds rejected by the reused trees

- Severity: **major**. Status: **open**.
- Location: `docs/design/tables/03-keys-and-indexes.md:289`, especially the explicit application to full primary keys at line 300.
- Requirements: AC-N1's intervals and keys at the size limit; B5 and the design's 2,048-byte key maximum.
- Evidence type: checked byte lengths and existing range-validation source.

The inclusive-upper transformation and exclusive-lower transformation append `FF` to the encoded value. The document applies these half-open byte bounds to complete primary keys as well as index prefixes. A `bytes` PK containing 2,046 nonzero bytes encodes as one type byte, the payload and one terminator: exactly 2,048 bytes, which the design admits. The transformed bound is 2,049 bytes.

The existing public tree range API validates each bound with `check_key`: `crates/krummi/src/lib.rs:1467`, `:1497`, and `:1438`; `MAX_KEY` is 2,048 at `crates/krummi-tree/src/node.rs:31`. Range removal's lower layer also asserts this bound at `crates/krummi-tree/src/lib.rs:570`. Thus directly using the specified bounds fails size validation (or violates the lower-level precondition) for a valid requested interval. No adaptation for synthetic bounds beyond the tree limit is specified. The byte-length calculation was independently executed; future table operations themselves do not yet exist to run.

Suggestion: specify how these bounds map to the existing included/excluded range API without exceeding its key limit.

<a id="R6"></a>
### R6 — Spill sort keys exceed the reused trees' key limit

- Severity: **major**. Status: **open**.
- Location: `docs/design/tables/08-execution-plans.md:200`, scratch-store sort runs.
- Requirements: document 8's spillable `Sort` at line 101; column ordering in document 4 at line 39 and N4/N5.
- Evidence type: verifiable size conflict between the proposed scratch layout and existing tree invariants.

On memory-reservation failure, the proposed sort moves each run into a normal tree keyed by `sort key ‖ sequence`. A table with a small PK and a nonindexed `bytes` column of 3,000 bytes is valid under the row design and that column is orderable. Its tuple sort key already needs at least 3,002 bytes, before the sequence, whereas the reused trees permit at most 2,048. Even a 2,048-byte sort key stops fitting once the sequence is appended.

Consequently an otherwise valid sort can fit its comparison model in memory yet become unrepresentable when it spills, before exhausting the spill budget. The design provides no oversized-key run representation or comparator outside the tree key, and does not limit sortable values to indexable sizes. These lengths were checked against `crates/krummi-tree/src/node.rs:31` and B5; no implemented query failure is claimed.

Suggestion: define spill runs that support all admitted sort keys without inheriting the persistent tree-key limit.

<a id="R8"></a>
### R8 — Differential oracle requires equality for valid tied windows

- Severity: **minor**. Status: **open**.
- Location: `docs/design/tables/11-query-contract-reconciliation.md:474`, Differential tests.
- Related contract: `docs/design/tables/10-agent-tooling.md:83`, especially lines 97–100.
- Evidence type: concrete counterexample against the existing comparison semantics.

The proposed differential tests require all planner alternatives and the reference to return the same rows, with ties by PK. Document 10 instead defines admissibility: `ORDER BY created LIMIT 1` over two rows with equal `created` may return either row through `Sort` and `Limit`; only `TopK` imposes its own PK tie-break, which is explicitly not part of that logical query.

A generated tied query can therefore produce two correct alternatives with different row multisets. The proposed oracle labels one as wrong even though it meets the stated semantics. Document 11 does not propose changing that semantic rule. This is a test-design inconsistency, not evidence of an implemented query defect.

Suggestion: use document 10's admissibility oracle or generate an explicit total order for equality comparisons.
