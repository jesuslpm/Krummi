<a id="R6"></a>
### R6 — Row-only spill records lose fixed-width primary keys

- Severity: **major**. Status: **still open, partially corrected**.
- Location: `docs/design/tables/08-execution-plans.md:200`.
- Related contract: spillable `Sort` at `08:101`, unchanged output columns at `08:108–113`, batch key/row representation at `08:174–177`, and the row layout at `01-row-format-and-types.md:204–211` and `02-row-storage.md:180`.
- Evidence type: independently verified information-loss argument against the specified representation, supported by an inline byte check; no future-query runtime reproduction.

The correction stores **the row alone**, exactly as the table holds it, under a new sequence-number key. It deliberately omits the encoded sort key and reconstructs sort columns from the stored row. However, fixed-width primary key columns are absent from that row: their only stored representation was the original table-tree key, which the run replaces with its position.

A valid external plan can explicitly sort a `TableScan` returning integer PK `id` and non-key `payload` by `id DESC`. Once enough rows force a spill, the prescribed run contains neither `id` nor an original-key locator. The merge cannot recover its sort column, and `Sort` cannot emit all input columns unchanged. The auxiliary tree covers computed sort keys/projected values such as `Distance`; this plan has neither a computed key nor a `Project`, and `id` is a stored column.

For a concrete representation check, use schema version 1, `id: u64 PRIMARY KEY`, and one `NOT NULL bytes` payload `78`. Document 1's three-byte header plus payload is `01 00 00 78` for every `id`; the PK is omitted. Two-row datasets with IDs `{1,2}` and `{101,102}` require different returned IDs, but sorting each descending produces identical prescribed spill trees: positions 0 and 1, each containing `01 00 00 78`. There is no information from which to reconstruct either dataset's IDs. Retaining an additional key/locator representation would require a rule absent from the specified spill layout.

The preceding 100 MiB counterexample is corrected as to capacity: its row alone is 104,857,603 bytes, below `MAX_VALUE = 268,435,456`; row plus escaped sort key was 314,572,805 bytes. Normal-tree size validation and off-leaf reads remain as previously verified (`crates/krummi/src/lib.rs:869–873`; `krummi-tree/src/lib.rs:310–322`, `:696–705`). Correcting capacity has introduced the information-loss problem within the same pending spill finding.

Suggestion: preserve the original primary key and every required input column in a spill representation whose individual records still respect B6.

- Evidence type: independently checked documentary contradiction using the original escaped-bytes counterexample.

The changed storage table, primary-index/covering paragraphs and batch description now correctly distinguish fixed-width PK columns from `string`/`bytes`. The corrected layout, covering eligibility and Rust/C/C# accessors provide a valid raw-row read path for the original logical PK `41 00 42`; its tuple representation `01 41 00 FF 42 00` cannot supply those logical bytes as a contiguous slice.

Nevertheless, document 2 still states: **“Primary key columns live only in the key. Its off-leaf discussion also says a scan reading only PK columns stays in the leaves. For a `bytes` PK containing zero bytes and a large off-leaf row, the corrected zero-copy accessor must read the raw PK from the row's run; the old paragraph instead omits that copy and the old scan claim excludes the required run read.

These dependent descriptions contradict the same document's newly corrected storage table at line 180. The substantive zero-copy solution remains available, so this retains R4's limited documentary severity rather than restoring its former major severity.

Suggestion: synchronize the remaining primary-key layout and off-leaf scan descriptions with the fixed-width/variable distinction.
