### R1 — major — Contiguous version chunks bypass the configured maximum size

**Location:** `crates/krummi-pager/src/temp.rs:129`, `:150`, `:233`;
`crates/krummi-tx/src/transaction.rs:697`.

**Problem and causal evidence:** A value run must fit in one free range of one temporary-area chunk. If no range
fits, `store_run` grows the area. For a run larger than 1,024 pages, `grow` allocates a chunk of exactly the requested
size. Replacing a value with one requiring just one more page therefore needs another chunk even after all slots
of earlier chunks have become free. Releasing slots only updates free ranges (`temp.rs:223`); chunks remain
allocated and mapped until area removal (`temp.rs:196`). However, `WriteTransaction::memory` counts live scratch
page versions and dirty buffers, not that additional reserved capacity. Successive slightly larger values can
therefore consume substantially more than `max_size`, without long-lived readers or increasing the number of keys.
Temporary stores use the same allocator with heap-backed chunks (`temp.rs:159`).

**Experimental reproduction through the public API:** Open a new disk store with
`StoreOptions { max_size: Some(64 << 20) }`. In ten successive durable writes, open/create the same normal tree and
overwrite key `b"k"` with a value of `(1025 + i) * 8192 - 16` bytes, for `i = 0..10`. Between commits, allow the
background transfer to run (500 ms in the observed reproduction), then read and compare the entire value. Sum the
lengths of the files in `krummi.temp` while the store remains open. All writes and comparisons succeeded:

| Completed writes | `krummi.data` bytes | `krummi.temp` bytes | Configured maximum bytes |
|---|---:|---:|---:|
| 1 | 8,445,952 | 8,527,872 | 67,108,864 |
| 4 | 33,783,808 | 33,767,424 | 67,108,864 |
| 8 | 33,783,808 | 67,534,848 | 67,108,864 |
| 10 | 33,783,808 | 84,467,712 | 67,108,864 |

After four writes, data plus temporary-area capacity is already 67,551,232 bytes, beyond the maximum. After eight,
the temporary area alone exceeds it. An additional deterministic transaction-layer reproduction paused background
transfer, explicitly transferred after each commit, and asserted `scratch_bytes() == 0` each time. Sixteen writes
left 135,462,912 bytes in `krummi.temp`, with 33,718,272 data bytes and the same 67,108,864-byte maximum. Thus pending
transfer does not explain the excess. These files contain the version chunks, not journal files excluded from the
maximum. Continued replacement keeps adding chunks and can exhaust disk or memory despite the configured bound.

The isolated reproduction programs are test temporaries under `target/review-large-values-public.rs` and
`target/review-large-values-max.rs`, compiled against the current Cargo-built libraries and executed successfully.
They use disposable `tempfile::tempdir()` stores and close them after verification.

**Requirement:** The large-values PRD, *Dejado a la implementación*, explicitly requires:

> En modo temporal y en las versiones que se conservan fuera de `krummi.data`, cuánta memoria reserva el motor de
> más para que un valor fuera de su hoja sea contiguo. Esa memoria cuenta para el tamaño máximo (P10, T14)

This is the additional-contiguity-capacity requirement inherited by the execution, with P10/T14 and V8/T11 governing
maximum-size accounting and failures. Existing S8/S9 tests do not exercise increasing run sizes against accumulated
chunk capacity.

**Introduced by this range:** The base allocates individual page slots, which can reuse free slots in any chunk.
The new single-chunk contiguous-run requirement and chunks larger than the previous 8 MiB cap introduce this
repeated growth pattern. This is a demonstrated substantive resource-limit defect, rather than evidence of data
corruption; severity is **major**.

**Suggestion:** Account for and reclaim unused capacity reserved for contiguity before accepting growth, and add a
regression covering repeated slightly larger replacements under a fixed maximum.

**Status:** Open.
