### R1 — major — Contiguous version chunks bypass the configured maximum size

**Verified resolved.** The original increasing-size case, partial retention under an old reader, and retirement
under a newer reader are covered by the three committed transaction regressions, all executed successfully on
disk and in temporary mode:

- `growing_runs_never_pile_up_in_the_temporary_area`;
- `shrinking_runs_under_an_old_read_count_whole_for_the_maximum_size`;
- `shrinking_runs_retired_under_a_newer_read_count_until_freed`.

Source verification supports those results. Exclusive chunks are released with their last holder
(`crates/krummi-pager/src/temp.rs:300–309`). `State::hold` and `release` charge a run's whole allocation while any
entry keeps it (`scratch.rs:790–824`). `retire` preserves that charge when entries move to `retired`, and
`free_retired` releases it only when the last counted holder leaves (`scratch.rs:830–898`). This closes the
previous undercounting path. Single-page accounting and the pre-existing shared-chunk growth policy remain
distinct from the corrected contiguous-allocation retention.

The former rationale for excluding retired runs, rebutted by the previous review, has been withdrawn and
replaced by `098e621`. However, that correction introduces R2 below. R1 keeps its original ID and is closed;
R2 describes the separate false-rejection regression.

## Open findings

<a id="R2"></a>
### R2 — major — A writer's own flush causes a maximum-size failure without readers

**Locations:** `crates/krummi-pager/src/scratch.rs:833`, `:884`;
`crates/krummi-tx/src/transaction.rs:690`.

**Problem and causal evidence:** The latest correction preserves the full charge of every retired multi-page
run, including runs retained solely by the current writer's snapshot. `reserve` calls `writer.flush()` when
the current versions prevent a reservation from fitting (`transaction.rs:669–691`). The writer already has a
registered snapshot (`scratch.rs:292–297`, `:503–509`). Retirement assigns a sequence bound including that
snapshot (`:830–836`), and `free_retired` includes `writer.seq` in its retention bound (`:879–889`). The old
allocation and its charge consequently remain until the write ends. The repeated budget check returns
`MaxSize` even with no read transaction or retained reference anywhere.

**Executed deterministic reproduction:** Open a fresh store with a 24 MiB maximum, pause automatic transfer,
and never open a read transaction. Allocate and commit a 1,040-page value run, then free it and commit in a
separate write. In a third write, allocate the same 1,040 pages again. The reservation forces a transfer but
fails with `MaxSize`; committing that failed transaction also fails with `MaxSize`. Immediately retrying the
identical reservation in a new write reuses the same first page and commits successfully, without growing the
data area. The probe ran successfully in both disk and temporary modes, with identical figures:

| Stage | Data bytes | Counted scratch bytes | Temporary-area capacity bytes |
|---|---:|---:|---:|
| Before the failed reservation | 8,552,448 | 8,552,448 | 8,650,752 |
| After its forced transfer and rejection | 8,552,448 | 8,519,680 | 8,650,752 |
| After ending the failed write | 8,552,448 | 0 | 131,072 |
| After the identical retry commits | 8,552,448 | 8,536,064 | 8,650,752 |

The error reports `needed=25608192`, exceeding `max_size=25165824`. The obsolete run contributes 8,519,680 of
those bytes solely because the writer remains open. Once it ends, the same data and new write fit. This is
neither partial-run fragmentation nor capacity retained by a long reader. Pausing automatic transfer makes
the ordinary pending-transfer state deterministic; the failing operation itself performs the required transfer.

The disposable probe is `target/review-followup-j7.rs`, compiled with `rustc --edition=2024` against the
current Cargo-built `krummi-tx` and `tempfile` libraries. It uses a disposable `tempfile::tempdir()` disk store
and an independent temporary store. Its assertions check the error class, failed commit, successful retry,
same-page reuse and successful close.

**Violated requirement:** J7, `docs/prd/krummi/journal.prd.md:37`, explicitly states:

> una escritura nunca falla por tamaño máximo a causa de versiones que ninguna lectura necesita: antes se trasladan.

The large-values annotation to J7 adds contiguous retained values; it does not override that guarantee. T8
(`transactions.prd.md:37`) ends a writer's returned references at its next modification, and this reproduction
does not obtain any such reference. The implementation's freedom to reserve additional contiguous capacity
does not authorize retaining an unnecessary allocation through a mutating operation and rejecting its write.
This is inherited by the large-values execution, including S8/S9's maximum-size and transaction behavior.

**Introduction and severity:** Introduced by `098e6217529556acce930f367e711b8e9be476a3`, whose retirement
change keeps the run charged where the previous implementation released its charge after transfer. The
resolution record acknowledges that a write's own flush can now cause failure, but no PRD override authorizes
that regression. **Major:** an otherwise fitting write is spuriously rejected and its transaction invalidated;
retrying in another transaction recovers. No corruption or durability failure is claimed.

**Coverage gap:** The new regressions exercise readers that actually retain runs. Existing
`ac_j18_the_journal_stays_bounded_and_outside_the_maximum_size` uses individual pages
(`crates/krummi-tx/tests/journal.rs:208–242`), whose retirement charge still drops immediately, so it passes
without testing this run-specific regression.

**Suggestion:** Release allocations no live reader or valid reference needs before rejecting the reservation, while preserving whole-allocation charges for genuinely retained runs.

**Status:** Open.
