### R1 — major — Retained partial runs still bypass the configured maximum size

**Locations:** `crates/krummi-pager/src/temp.rs:191`, `:298`;
`crates/krummi-pager/src/scratch.rs:607`, `:782`, `:807`, `:1050`;
`crates/krummi-tx/src/transaction.rs:697`.

**What the fix resolves:** Recompiled and reran the original report's public-API and deterministic transaction
reproductions against the current libraries. Increasing runs without a retained reader now leave only 131,072
bytes in the temporary area after each transfer, instead of accumulating a chunk per write. Exclusive chunks
are released when their last holder disappears, as claimed.

**Remaining failure and causal evidence:** A run's pages share one `Arc<Slot>` owning its entire contiguous
allocation (`scratch.rs:1050–1054`). Reusing a freed run for a slightly smaller run supersedes every page except
its final page. `collect_garbage` discards the superseded per-page entries and subtracts their page sizes from
`state.bytes` (`scratch.rs:782–808`), but the surviving tail entry still owns the entire old allocation. An open
snapshot from before the first insertion prevents transferring these newer versions (`scratch.rs:600–608`).
It does not need the superseded versions, so garbage collection still removes their entries. Repeating the
operation leaves one tail entry retaining each earlier full run.

The new release logic (`temp.rs:298–307`) consequently never runs for those chunks while the reader remains
open. They are still in `versions`, so the new `free_retired` call (`scratch.rs:644`) cannot reclaim them.
`WriteTransaction::memory` continues to charge `scratch_bytes()` plus dirty pages (`transaction.rs:697–699`),
which undercounts those physically retained allocations. This rebuts the resolution's assertion that each
chunk's full capacity always belongs to a live version already counted by the maximum-size accounting.

**Public-API reproduction, executed successfully:**

1. Open a fresh disk store with `StoreOptions { max_size: Some(64 << 20) }` and retain a read transaction opened
   before creating any tree or value.
2. For page counts descending from 1,040 through 1,025, insert key `b"k"` in the same normal tree with a value
   of `count * 8192 - 16` bytes and commit. Before each insertion after the first, remove that key and commit
   the removal in a separate write, making its pages reusable by the next write.
3. After every insertion, open a fresh read and compare the complete current value. Sum the sizes of files in
   `krummi.temp` while the initial read remains open. Every write and comparison succeeds; no maximum-size
   error occurs. This reproduction uses no internal hooks, file interference or timing assumptions.

| Completed insertions | Current run pages | `krummi.data` bytes | `krummi.temp` bytes | Configured maximum bytes |
|---|---:|---:|---:|---:|
| 1 | 1,040 | 8,568,832 | 8,650,752 | 67,108,864 |
| 7 | 1,034 | 8,568,832 | 59,596,800 | 67,108,864 |
| 8 | 1,033 | 8,568,832 | 68,059,136 | 67,108,864 |
| 16 | 1,025 | 8,568,832 | 135,462,912 | 67,108,864 |

At seven insertions, data plus temporary capacity already exceeds the maximum; at eight, temporary capacity
alone exceeds it. At sixteen, the combined capacity is 144,031,744 bytes, despite a single key with an
approximately 8 MiB current value and a 64 MiB maximum.

**Independent deterministic confirmation:** At the transaction layer, pause automatic transfer, retain a read
opened before the first run, and alternate committed frees with committed allocations of the same descending
sizes. Explicitly request a transfer after each allocation. Every run reuses first page `4`; data stays at
8,552,448 bytes and `scratch_bytes()` stays at 8,536,064 bytes, while `area_bytes()` grows to 135,462,912 bytes.
On disk this exactly matches the file lengths. The same probe in temporary mode produces the same allocation
and accounting figures without any temporary files. Dropping the initial reader and transferring reduces
`area_bytes()` to 131,072 and `scratch_bytes()` to zero in both modes. Thus the discrepancy is whole-allocation
retention, not journal capacity or a transfer scheduling delay.

The reproduction sources and binaries are disposable verification artifacts under `target/`:
`review-large-values-public-partial-02.rs`, `review-large-values-partial-02.rs`, and
`review-large-values-partial-memory-02.rs`. Each uses a disposable store and closes it after verification.

**Requirement:** The authoritative large-values PRD, *Dejado a la implementación*, states:

> En modo temporal y en las versiones que se conservan fuera de `krummi.data`, cuánta memoria reserva el motor de
> más para que un valor fuera de su hoja sea contiguo. Esa memoria cuenta para el tamaño máximo (P10, T14)

This is R1's existing P10/T14 requirement, inherited by S9 and the maximum-size behavior of the execution.
Long readers may cause a maximum-size failure; they do not exempt retained contiguous capacity from that limit.
The new regression (`crates/krummi-tx/tests/runs.rs:440–452`) increases sizes and drains all scratch versions
after every write, so it does not exercise partial run retention.

**Severity and lineage:** **Major**, unchanged. This is experimentally demonstrated resource-limit failure on
ordinary supported operations, including temporary-mode memory retention; no data corruption is claimed.
It remains part of original `docs/reviews/trees-large-values/2026-10-27-code.md#R1`, introduced by the feature's
whole-run contiguous allocation, and is not a newly introduced follow-up regression.

**Suggestion:** Charge each retained contiguous allocation's full capacity until its last holder releases it,
and cover shrinking reuse under a retained reader in both storage modes.

**Status:** Still open; original scenario verified fixed, overall finding unresolved.
