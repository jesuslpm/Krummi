## Findings

<a id="R1"></a>
### R1 — Major: migration by integer division can change previously stored values

- Location: **Flujo**, lines 64–69; TU3/TU5.
- Evidence: “Una aplicación que pase de nanosegundos a microsegundos divide sus valores entre 1.000.”
- Problem: the instruction does not distinguish original application inputs from values already normalized by Krummi. Those are observably different migration sources when the original input has a submicrosecond remainder.
- Allowed readings: dividing a previously read/normalized value preserves the stored instant; dividing the original integer input can change it. For example, an old `timestamp` input of 1,500 ns is stored as 2 µs, whereas integer division of that original input gives 1 µs. An old column default with that input therefore differs from a default migrated by the stated division and can fail opening with **esquema distinto**.
- Source evidence: `crates/krummi/src/table/value.rs:422` normalizes timestamp inputs; `value.rs:473` rounds with ties toward the greater value. `crates/krummi/src/table/schema.rs:283` normalizes defaults, and `schema.rs:687` compares the normalized defaults when opening an existing table.
- The same paragraph also overstates the failure of unchanged nanosecond defaults: “dentro, al abrir con ese esquema una tabla que ya existe da esquema distinto”. A zero default remains zero in both units and does not cause this difference.
- Suggestion: distinguish exact conversion of normalized values from conversion of original inputs with a remainder, explain preservation of previously stored values, and qualify the default-mismatch statement.
- Status: open.

<a id="R3"></a>
### R3 — Minor: AC-TU6 mixes incompatible types in its duplicate-key setup

- Location: **Criterios de aceptación / AC-TU6**, lines 146–150.
- Evidence: the criterion lists hours, timestamps, and durations, then says “cuando se piden en su forma de texto y cuando son la clave de una **clave duplicada** en una tabla con clave `timestamp`”.
- Problem: read literally, both checks apply to all six examples. A `time` or `duration` value cannot produce a duplicate timestamp key: N4 and the PRD's own validation table require a type-mismatch failure first. `crates/krummi/src/table/value.rs:175`–177 matches each temporal value only to its corresponding column type. TU6 explains the intended text output, but the acceptance setup needs a type-correct mapping.
- Suggestion: explicitly delimit the duplicate-key examples and their corresponding key types.
- Status: open.
