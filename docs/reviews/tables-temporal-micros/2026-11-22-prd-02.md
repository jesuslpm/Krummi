### R1 — Major: migration by integer division can change previously stored values — verified resolved

- Original finding: [2026-11-22-prd.md#R1](2026-11-22-prd.md#R1).
- Location: **Flujo**, `tables-temporal-micros.prd.md:64–79`; TU3/TU5, schema E5/E6.
- The fix separates “**Un valor leído de Krummi antes de este cambio**” from “**Un valor original de la aplicación**”. It requires the latter to use the previous nearest-microsecond rounding with ties toward the greater value, and explicitly preserves zero in the unchanged-default warning: “salvo cuando es el mismo en las dos unidades, como el 0.”
- Prior reproduction rechecked: an input of 1,500 ns normalizes to 2,000 ns and stores 2 µs; truncating the original input gives 1 µs. The corrected guidance converts the original input to 2 µs or divides the normalized read of 2,000 ns exactly. The new default therefore has the same stored value, whereas the truncated default differs.
- Source evidence: `crates/krummi/src/table/value.rs:415–431,473–480` rounds and validates temporal inputs; `schema.rs:280–288` normalizes defaults; `schema.rs:687–693,726–731` compares the normalized defaults. `schema.rs:1201–1213,1241–1242` stores defaults using the row layout.
- Opening-path evidence: `crates/krummi/src/table/catalog.rs:431–439` checks the supplied schema and compatibility before joining an existing table or emptying it. The corrected default therefore follows the existing compatibility rule without introducing a new conversion at open time.
- Regression check: negative inputs and ties (−1,500 ns, −500 ns), positive ties, zero and exact normalized read conversion were checked against the source arithmetic. The fix changes migration guidance, without adding engine-side conversion, changing domains or relaxing TU5 byte preservation.
