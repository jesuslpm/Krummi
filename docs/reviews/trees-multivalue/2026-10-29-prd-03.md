### R3 — The new A10 annotation overgeneralizes the conditional-change rule — verified resolved

- Original severity: **minor**.
- Earlier finding: [2026-10-29-prd-02.md#R3](2026-10-29-prd-02.md#R3), arising from the original report's R1 fix.
- Section / IDs: dated annotation to *Decisiones de producto / A10*, `docs/prd/krummi/trees-keys.prd.md:75`; matching *Anotaciones a otros PRD*, `docs/prd/krummi/trees-multivalue.prd.md:335–337`.
- Claimed disposition: `fixed`, in the resolutions' round 2 fixes. Both reviewed hashes match that claim's artifact versions.
- Verified correction: A10's annotation now enumerates “Añadir, Quitar valor, Quitar clave y los dos Quitar intervalo” instead of applying the conditional-change rule to all modifying operations. It explicitly preserves catalog operations and opening modes, and says “vaciar un árbol multivalor es siempre un cambio, como dice A2”. The target's matching summary likewise preserves those rules. Both agree with M9 (`trees-multivalue.prd.md:48`), A2 and A10 (`trees-keys.prd.md:37`, `:45`).
- Reproduction, empty tree: begin with an existing empty multivalue tree and successfully request Vaciar. Both corrected passages explicitly classify it as a change. The former reading that it is a no-op because no key/value was added or removed is no longer supported.
- Reproduction, rename: rename an existing tree to another name without changing its key/value set. The corrected passages preserve A10, so this remains a change; renaming to the same name remains a no-op. The condition for the five named add/remove operations cannot now be applied to these catalog operations.
- Source corroboration of inherited behavior: `crates/krummi/src/lib.rs:363` dispatches the emptying opening modes to `empty`; `:644–658` unconditionally frees/recreates the root and marks the state dirty, including for an empty tree. `finish` at `:676–690` persists dirty catalog entries. `rename_tree` at `:406–433` returns early for the same name and updates the catalog for another name.
- Result: **verified resolved**, without introducing a new product rule or requiring a product decision.

## Dependent invariants and scoped gap sweep

The correction preserves the distinction between ending references/scans and producing actual changes:

- A10, M9 and R6/R7 (`trees-scan.prd.md:46–47`) end references/scans for potentially modifying operations even when they change nothing or fail. Existing APIs express this through mutable transaction borrows; read operations retain shared borrows (`crates/krummi/src/lib.rs:343–344`, `:494`, `:504`, `:516–529`). The corrected annotation does not condition reference invalidation on a runtime change.
- Successful creation, emptying, deletion of an existing tree and renaming to another name retain A10's change rules. Opening an existing tree with Abrir o crear, deleting a missing tree and renaming to the same name retain their no-op rules. Validation errors remain distinct from T11 failures.
- T10's no-change path and its E11 durability qualification remain intact: `crates/krummi-tx/src/transaction.rs:359–372` checks a recorded failure first; otherwise a transaction without dirty pages/runs performs no change commit and, in durable mode, waits for previously observed commits. R3 does not waive failure handling, durability waits or snapshot/page ownership requirements.
- M9 and AC-M17 (`trees-multivalue.prd.md:303–307`) still classify duplicate additions and missing/empty removals as no-ops; AC-M9 (`:248–254`) retains invalidation requirements after operations that fail without effect.
- The focused methodological/gap sweep found no new competing observable interpretation for empty cases, opening modes, catalog operations, duplicate/missing values, validation failures, outputs or reference/scan lifetimes. No implementation detail or new scope requirement was introduced.

The source corroborates inherited normal-tree behavior. It does not establish runtime correctness of the future multivalue implementation.
