### R2 — original severity: minor — Verified resolved

- Original finding: [2026-10-29-code.md#R2](2026-10-29-code.md#R2), accepted measurement counts could
  index past the allocated keys.
- Reviewed fix: `dc317ece34a0911a5981e43366beeda41ea049ab`, retained at the reviewed head.
- Source: `crates/krummi/examples/multi_timing.rs:346–365`, with callers at `:180–206` and consumers
  starting at `:415` and `:577`.
- Requirement: tooling supporting M15 / S19–S20; the additional `--values` option caused the original failure.
- Technical evidence: for a positive supported set size `n`, the effective count is now
  `floor(count / n) * n` before values, owners and keys are generated. Every owner's index is consequently
  smaller than `effective_count / n`, the allocated key count. This arithmetic cannot overflow because its
  result is at most the input count. The caller skips `n > count`, so measured set-size loads are nonempty.
  Output, scans, baseline comparisons and rate/page denominators use the effective `data.values.len()`.
- Independent reproduction: the original command, with an existing disposable-store parent, passed:
  `cargo run --locked -p krummi --example multi_timing -- --values 11 --loads n10 --pairs 2048:1024 --folder target`.
  Exit 0; header: `## Load n10: 10 values, keys with values: 1`. Both multi-value and composite rows completed.
- Boundary checks: the built example was run with `--pairs 2048:1024 --folder target` for the cases below.
  Every invocation exited 0, its expected headers were asserted, and its internal add/contains/scan/remove
