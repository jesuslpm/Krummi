## Findings

<a id="R1"></a>
### R1 — blocker — Public handle supertraits expose normal operations on multi-value trees

- Location: `crates/krummi/src/lib.rs:283–294`, with the multi-value conversions at lines 302–305 and 314–317.
- Status: open; introduced by this range.
- Requirement: S9 / AC-M9, M4. The PRD requires: “Usar una operación de un tipo con la apertura de un árbol de
  otro tipo no compila”. This also protects the persisted multi-value representation and subtree ownership.
- Problem: the private `sealed` module prevents applications from naming its traits, but does not prevent an
  application with a public `WriteHandle` or `ReadHandle` generic bound from calling the inherited public
  `as_tree()` method. It returns the normal-tree handle contained in a multi-value handle. Normal operations
  consequently compile and run on a tree whose catalog kind is still `MultiValue`.
- Failure scenario: create a multi-value tree, add `(k, v)`, obtain its normal handle through the generic bound,
  and call `set(k, "not-a-multi-blob")`. Both `set` and `commit` succeed. After closing and reopening the store,
  `value_count(k)` reports `Damaged`. The normal `set` writes arbitrary value bytes without the multi-value blob
  encoding, and `multi::entry` rejects those bytes when decoding. Replacing an existing subtree entry through
  this route also bypasses multi-value subtree freeing.
- Evidence: experimentally reproduced from an external Rust application linked against the reviewed library,
  using safe code only. Both temporary-store and on-disk probes compiled with exit 0. The on-disk probe printed
  `reopened value_count kind: Damaged` after a successful commit, close and reopen. A read-handle probe likewise
  compiled and returned the internal blob through normal `get`: `Ok(Some([0, 1, 0, 1, 0, 118]))`.

The on-disk reproduction was compiled from stdin with `rustc --edition=2024`, linking the workspace's `krummi`
and `tempfile` libraries via `--extern` and `-L dependency=target/debug/deps`; its executable was placed under
`target/`. The complete application was:

```rust
use krummi::{OpenMode, Store, StoreOptions, WriteHandle, WriteTree};

fn normal<'a, 's>(tree: &'a impl WriteHandle) -> &'a WriteTree<'s>
where
    'a: 's,
{
    tree.as_tree()
}

fn main() {
    let folder = tempfile::tempdir().unwrap();
    let store = Store::open(folder.path(), &StoreOptions::default()).unwrap();
    let mut tx = store.write().unwrap();
    let tree = tx.open_multi_tree_with("index", OpenMode::CreateNew).unwrap();
    tx.add(&tree, b"k", b"v").unwrap();
    tx.set(normal(&tree), b"k", b"not-a-multi-blob").unwrap();
    tx.commit().unwrap();
    store.close().unwrap();

    let store = Store::open(folder.path(), &StoreOptions::default()).unwrap();
    let tx = store.read().unwrap();
    let tree = tx.open_multi_tree("index").unwrap();
    println!("reopened value_count kind: {:?}",
        tx.value_count(&tree, b"k").unwrap_err().kind());
}
```

The existing compile-fail test `multi_tree_handle_takes_no_normal_tree_operations.rs` exercises direct use of the
wrapper, but never accesses the normal handle through a public generic bound, so it passes despite this defect.

Suggestion: keep conversion to normal handles inaccessible through public bounds and add an external compile-fail regression for both handle traits.

<a id="R2"></a>
### R2 — minor — Accepted measurement counts can index past the allocated keys

- Location: `crates/krummi/examples/multi_timing.rs:348`, leading to the panic at line 358.
- Status: open; introduced by this range.
- Requirement: M15 / S19–S20 measurement tooling; this affects the additional documented `--values` option,
  rather than the recorded one-million-value default runs.
- Problem: `--values` accepts every positive count, but `data(SetSize(n), count)` allocates `count / n` keys and
  produces owners for all `count` values using `j / n`. If the count is not divisible by the set size, the last
  owner's index equals the number of allocated keys. Updating `counts[k]` then panics before measurement starts.
- Failure scenario: request 11 values in sets of 10. One key is allocated, while value 11 is assigned owner 1;
  indexing `counts[1]` fails because its length is 1. Default loads can hit the same problem with other positive
  counts accepted by the parser.
- Evidence: the coordinator ran
  `cargo run --locked -p krummi --example multi_timing -- --values 11 --loads n10 --pairs 2048:1024`.
  Cargo exited 1; the example exited 101 with:

```text
panicked at crates\krummi\examples\multi_timing.rs:358:15:
index out of bounds: the len is 1 but the index is 1
```

Suggestion: validate divisibility for the selected set-size loads, or explicitly define and implement a partial final set.
