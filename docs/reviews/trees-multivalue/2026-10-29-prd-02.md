### R3 — The new A10 annotation overgeneralizes the conditional-change rule

- Severity: **minor**.
- Section / IDs: dated annotation to *Decisiones de producto / A10*, `docs/prd/krummi/trees-keys.prd.md:75`; introduced by the R1 fix.
- Problem: the annotation applies the conditional T10 rule to all multivalue operations that can modify, whereas M9 makes that rule conditional only for its named add/remove operations and explicitly preserves Vaciar as a change. The target already settles the behavior; this is an inaccurate summary in the earlier PRD, not an unresolved product decision.
- Evidence: the new annotation says “las operaciones de los árboles multivalor que pueden modificar” and “son cambios para T10 solo cuando añaden o quitan algo”. M9 explicitly says “Vaciar un árbol multivalor es un cambio, como dice A2.” (`docs/prd/krummi/trees-multivalue.prd.md:48`). A2 says “Es un cambio, aunque el árbol ya estuviera vacío o se acabe de crear en la misma transacción.” (`docs/prd/krummi/trees-keys.prd.md:37`); the unchanged A10 also lists emptying and renaming to another name as changes (`:45`).
- Reproduction / readings: start with an existing empty multivalue tree and request Vaciar. The annotation's broad wording permits calling this a no-op because it adds/removes no entries; M9/A2 require a change. Similarly, renaming to another name changes no key/value set but remains a change under A10. Reading the linked M9 recovers the intended rule, which limits this finding to clarity. The existing implementation confirms the inherited Vaciar behavior: `crates/krummi/src/lib.rs:644` frees/recreates the root and marks the state dirty at `:657` even for an empty tree. This was a source/requirement reproduction, not a runtime multivalue test.
- Suggestion: scope the conditional T10 summary to M9's named add/remove operations and preserve A10's catalog-operation rules explicitly.
- Status: **open**, new regression; original R1 and R2 are resolved below.

### R2 — Unsupported deletion-path rationale — verified resolved

Earlier finding: [2026-10-29-prd.md#R2](2026-10-29-prd.md#R2). Disposition claimed: `fixed`.

M14 now says “un motor de formato `7` no conoce el tipo multivalor y toma la entrada de un árbol multivalor en el catálogo por dañada” (`trees-multivalue.prd.md:53`). The unsupported permanent-leak scenario is removed.

The original source-path reproduction confirms the replacement rationale: `Entry::decode` rejects unknown kinds at `crates/krummi-tree/src/catalog.rs:60`, and `decode_in` maps that to damage at `:72`. Listing decodes every entry (`:100`); opening calls `find`, which reads the catalog (`crates/krummi/src/lib.rs:737`); deletion looks up the entry before freeing anything (`:394`); renaming looks up source and destination before deleting the destination (`:409`, `:415`, `:424`). Thus catalog rejection precedes the alleged partial-free path.

This is the counterfactual incompatibility rationale if the old format were retained. An actual engine opening a store with a different header version returns `DifferentFormat` before catalog access (`crates/krummi-pager/src/pager.rs:816`). D7, B12 and M14 still require this early rejection, format `8`, no migration, and rejection of format `7` even when empty. No regression was found in those requirements.
