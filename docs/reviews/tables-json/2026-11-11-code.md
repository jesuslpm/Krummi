### R1 — major — One exact numeric term cannot cover rounded f64 equality

**Location:** docs/design/tables/14-json-indexes.md:229. Supporting locations: that document's lines 150–153, 208–220 and 238–240; docs/design/tables/13-json-column-storage.md:114, :292 and :704; docs/design/tables/11-query-contract-reconciliation.md:400.

**Problem and failure scenario:** insert two rows whose payloads are {"n":0.1} and {"n":0.10000000000000001}, then evaluate Eq(JsonAs(f64, payload, ["n"]), $p) with the f64 parameter 0.1. Document 13 explicitly permits correctly rounded f64 conversion. Both numbers therefore satisfy the predicate, but document 14 stores them under different exact decimal value terms. Its numeric-extraction rule selects one term's posting list and rechecks it. A single exact term cannot contain both rows; the recheck cannot recover a row excluded from the candidates. The indexed result differs from the full scan.

**Evidence type:** reproducible numeric counterexample plus a causal argument over the written candidate-selection rules, not an engine reproduction. The coordinator executed this in-memory model with Python, without writing files:

    from decimal import Decimal
    docs = {1: "0.1", 2: "0.10000000000000001"}
    param = 0.1
    scan = [k for k, v in docs.items() if float(v) == param]
    term = Decimal(str(param))
    candidates = [k for k, v in docs.items() if Decimal(v) == term]
    result = [k for k in candidates if float(docs[k]) == param]
    print(scan, candidates, result)

Observed output: [1, 2] [1] [1]. A separate check confirmed unequal Decimal values and identical binary64 bits, 3fb999999999999a. The shortest-round-trip parameter spelling follows the earlier query contract. Selecting any other single exact decimal term still cannot include both distinct decimal values. Document 13:790–795 already acknowledges this loss of distinctions through f64.

The related wording also needs reconciliation: document 13:292 and document 14:103 promise "never a rounded value", while document 13:114 and :704 explicitly allow correctly rounded f64. Those statements cannot all define the same extraction contract.

**Violated requirement:** document 14 X3, its explicit candidate-completeness invariant at lines 238–240 and the proposed no-false-negatives test at lines 369–370. There is no future PRD acceptance ID or S# to map yet. Severity is major because the proposed access rule is substantively incorrect, while this documentation-only range introduces no running implementation or operational data loss.

**Suggestion:** make the conversion contract consistent and leave JsonAs(f64) as a residual filter until candidate selection can conservatively include every rounding-equivalent value.

**Status:** open.

### R2 — minor — The conformance corpus requires accepting forbidden duplicate names

**Location:** docs/design/tables/13-json-column-storage.md:777. Supporting locations: :657, :769–771, :783–789 and :822–828.

**Problem and failure scenario:** the conformance layer requires every JSONTestSuite y_ file to be accepted. However, the suite's y_object_duplicated_key.json contains {"a":"b","a":"c"}, and y_object_duplicated_key_and_value.json contains {"a":"b","a":"b"}. Krummi's decided policy rejects both. Applying the stated corpus expectation would fail a correct reader or encourage accepting values the product forbids. The exceptions mentioned at lines 788–789 apply to the separately described differential layer; they do not qualify the blanket corpus rule.

**Evidence type:** direct contradiction between the new test specification and its required fixtures. The coordinator fetched the primary [suite instructions](https://raw.githubusercontent.com/nst/JSONTestSuite/master/README.md), [duplicate-key fixture](https://raw.githubusercontent.com/nst/JSONTestSuite/master/test_parsing/y_object_duplicated_key.json) and [duplicate-key-and-value fixture](https://raw.githubusercontent.com/nst/JSONTestSuite/master/test_parsing/y_object_duplicated_key_and_value.json). **Violated requirement:** the decided duplicate-name rejection policy, stored-form rule 5 and the document's proposed rejection tests. This is a limited test-plan contradiction, not a demonstrated parser defect.

**Suggestion:** define pinned Krummi-specific expectations for corpus cases that conflict with its stricter duplicate, depth or number rules, as already planned for differential testing.
