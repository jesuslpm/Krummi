### R1 — minor — Dictionary prefix scans omit hashed string terms

- **Location:** `docs/design/tables/14-json-indexes.md:280–284`, introduced in `d7bf6b8` and still present at head.
- **Problem:** the new section says every value term of a path begins with `V ‖ path ‖ kind`, that its values
  are contiguous, and that string prefixes/ranges can use the dictionary as designed. The existing *Long terms*
  rule at `:159–160` instead replaces an entire long term with `H ‖ xxh3-64`, outside that prefix.
- **Concrete scenario:** row 1 contains `{"a":"A…A"}` with 3,000 `A` characters; row 2 contains `{"a":"Ab"}`.
  Both satisfy a prefix `A` on path `a`. Row 1's term exceeds the 2,048-byte key limit and is hashed; row 2's
  term can retain its `V ‖ path(a) ‖ string` prefix. Scanning the proposed dictionary prefix finds only row 2.
  Rechecking candidates cannot recover omitted row 1. The same problem can arise from a long encoded path.
- **Evidence:** verifiable technical argument from the two conflicting rules, independently reproduced with
  a Python in-memory dictionary model. The model used an arbitrary eight-byte hash payload: the actual hash
  cannot change the decisive `H` versus `V` prefix separation. Output:

  ```text
  dictionary prefix: full scan [1, 2] V-prefix scan [2] (long-term H key omitted)
  ```

- **Requirement:** design 14 X3 (`:87–88`) and candidate completeness (`:245–247`). No future PRD criterion
  or ODD S# exists yet.
- **Impact boundary:** this is an incorrect completeness claim in an explicitly open design proposal.
  Line `:296` keeps ranges without an index list, so the counterexample does not demonstrate an active engine
  query defect. No implementation of the deferred feature is requested by this finding.
- **Suggestion:** qualify the claim for unhashed terms and record that enabling these scans requires conservative
  handling of hashed terms or a full-scan fallback.

This report's R1 is a new local finding; it is distinct from R1 in the earlier code reports.

## Other reviewed behavior

- Exact integer extraction in any numeric notation agrees with exact numeric term normalization, including
  range boundaries. Decimal rounding matches E8's ties away from zero and checks precision after rounding.
  Excluding rounded decimal extraction from single-term candidates prevents the earlier f64 completeness defect
  from recurring for decimals. Existing AND/OR fallback and recheck rules remain conservative.
- Temporal extraction specifies offsets, microsecond rounding, domain checks after rounding, and NULL for invalid
  strings. These agree with the relevant E8 contract. Expression indexes use the extracted typed value and the
  existing chronological key encoding. Query parameters deliberately retain design 11's stricter serialized form.
- No additional temporal inverted-index defect was demonstrated: the rules do not specify translating a typed
  timestamp parameter into one JSON string term. The phrase “equality with a term” does not establish such a
  mapping, and a predicate without a usable list falls back to filtering. A future implementation must preserve
  candidate completeness when adding that mapping.
