### R1 — previously minor — Verified resolved

Original finding: [2026-11-11-code-03.md#R1](2026-11-11-code-03.md#R1), “Dictionary prefix scans omit hashed
string terms.” This ID preserves the code-03 finding; it is distinct from the older numeric R1 verified closed
in [code-02](2026-11-11-code-02.md). The earlier reports and their resolutions were consulted for lineage.

**Reviewed fix:** `e352bcaf21b031f6f33869e7d9afccf563923eaf`, present at the reviewed head.

**Source evidence:** `docs/design/tables/14-json-indexes.md:288–296` now explicitly identifies the lost hashed
term, repeats the original 3,000-character-string counterexample, and qualifies the preceding scan claims:
they are complete only over unhashed terms. Enabling them requires either visiting and rechecking relevant
hashed terms with retained path/value-prefix information, or giving no list and falling back to a full scan
for any path that may hold hashed values. An oversized encoded path explicitly falls back too.

**Independent reproduction:** a Python in-memory dictionary model repeated the original scenario, with row 1
holding 3,000 `A` bytes and row 2 holding `Ab` at path `a`. It reproduced the omitted row and verified the
explicitly permitted full-scan remedy:

```text
original R1: full scan [1, 2] V-prefix scan [2]
corrected original R1: no list -> full scan [1, 2]
```

Twenty prefix/range cases covering long values and a 3,000-byte path passed with that fallback, including
prefixes longer than the value and narrow ranges. Two additional AND/OR composition cases confirmed that a
listless predicate is handled conservatively: AND can retain the other child's list for rechecking, while OR
falls back. Two modeled term-size cases at 2,048 and 2,049 bytes confirmed the key-limit boundary used by the
counterexample. These are models of the design, not engine tests: the length-field widths and eight-byte
digest payload were placeholders; the decisive properties are the disjoint `H`/`V` prefixes and fallback.

**Dependent invariants and regression assessment:** X3 and candidate completeness remain at document 14
`:87–88` and `:245–247`. Hashed matches still require rechecking (`:159–160`, `:219–227`, `:243`), and the
AND/OR rules remain unchanged (`:209–217`). Lines `:276` and `:305` explicitly keep ranges without an index
list until detailed design. The proposed `H ‖ path ‖ kind ‖ value prefix ‖ hash` representation is an option
for that later design, not a change to current term encoding or equality lookup. This verification does not
approve a concrete truncated-prefix range algorithm: none is specified or enabled here.

The underlying byte-prefix/range logic (`crates/krummi-tree/src/range.rs:22–65`) and the 2,048-byte limit
(`crates/krummi-tree/src/node.rs:31`; `crates/krummi/src/table/key.rs:17`) support the failure argument and
fallback requirement. No code changes are needed for this clarification of a deferred proposal. JSON storage,
typed extraction, exact numeric term normalization and transactional index maintenance are unaffected.

**Requirement:** design 14 X3 and its candidate-completeness invariant. The original design-document defect is
resolved; this does not claim that future JSON indexes have been implemented or tested through a public API.
