### R1 — previously major — Verified resolved

Original finding: [2026-11-11-code.md#R1](2026-11-11-code.md#R1), “One exact numeric term cannot cover rounded f64 equality.”

**Reviewed fix:** `e36a9b7e7ceda3162119fc5c55c0a01aba686e13`, present at the reviewed head.

**Source evidence:** `docs/design/tables/13-json-column-storage.md:114` and `:289–296` now distinguish exact
integer/decimal extraction from correctly rounded `f64`. Document 14's expression extraction at `:102–107` agrees.
The inverted-index candidate rule at `docs/design/tables/14-json-indexes.md:209–217` explicitly gives no posting
list for `Eq(JsonAs(f64, ...), value)`, and the query table at `:233–234` matches it. The proposed regression
case at `:373–374` requires both rounding-equivalent documents to be returned.

**Independent reproduction:** repeated the original report's Decimal/binary64 counterexample with Python in
memory. The exact decimal values differ, while both binary64 bit patterns are `3fb999999999999a`:

```text
original R1: scan [1, 2] old [1] corrected [1, 2] bits 3fb999999999999a
```

The corrected result uses the specified fallback: no usable list means evaluate the predicate over the scan,
not an empty candidate set. This independently confirms the resolution's model; it is not an engine test.

**Dependent rules and regression verification:** `AND` intersects only usable lists and leaves `f64` to the
recheck; an `OR` with a listless child gives no list. These rules apply inside `JsonAny` as well. Exactness rule
2(d), `:223–225`, prevents treating numeric extraction as a proven exact term match; the complete quantifier is
rechecked, preserving same-element correlation. An in-memory set model checked 578 combinations of conservative
child candidates for `AND`/`OR`, with no lost matching rows. Mixed string/f64 `JsonAny` examples included a row
whose string and numeric matches occur in different elements:

```text
JsonAny and candidates [1, 3, 5] result [1]
JsonAny or candidates [1, 2, 3, 4, 5] result [1, 2, 3, 5]
```

Additional numeric pairs confirmed the same need for fallback beyond the original decimal example: adjacent
integers at `2**53`, and positive/negative underflow to zero. Document 11's value contract at `:400–401` already
allows correctly rounded floats, subnormals and underflow, with signed-zero normalization. The existing ordinary
typed-value normalization (`crates/krummi/src/table/value.rs:394–395`, `:424–439`) and key encoding
(`crates/krummi/src/table/key.rs:264–272`, `:392–403`; design 3's type table) were inspected. They do not introduce
a dependency requiring exact-decimal inverted terms for rounded `f64`. The fix does not alter stored JSON text,
exact structural numeric equality, term normalization, or transactional maintenance.

**Requirement:** document 14 X3 and its candidate-completeness invariant at `:243–245`. There is no future PRD
acceptance ID or ODD S# yet. This verification closes the design defect, without claiming future JSON support is
implemented or tested.
