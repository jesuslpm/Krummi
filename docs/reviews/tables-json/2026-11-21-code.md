### R1 — minor — Sampling rate targets are described as hard limits

- **Location:** `docs/design/tables/15-query-profile-and-tuning.md:755`; supporting locations: the same document at lines 222–223, 338 and 353–363, and `docs/design/tables/15-query-profile-and-tuning.html:659`.
- **Problem:** the new Costs text promises “never more than `R` rows per second per (shape, plan) nor `B` overall”, although the specified producer draws using a delayed probability snapshot and the consumer adjusts expected rates rather than enforcing a hard quota.
- **Concrete scenario:** set `R = 10` and run a newly seen shape at 10,000 executions/s. Capture explicitly assigns an entry absent from the snapshot `p = 1` for its first 100 ms tick, retaining about 1,000 executions before any update. This already exceeds the claimed ten-row limit. Even the idealized first-second calculation in Sampling gives about 79 retained executions for those same parameters. The global controller uses the previous second's demand and smoothing, so it likewise does not prove an instantaneous `B` bound. The companion chart clips its result with `Math.min(p[1], B)`, concealing that distinction.
- **Evidence type:** verifiable technical argument and internal contradiction in the changed design, not a reproduction of implemented profiling behavior; the document explicitly remains a proposal. This is a documentation issue, not a demonstrated JSON engine defect.
- **Requirement:** internal consistency and accuracy of the design included in the requested range; no JSON S#/AC applies.
- **Suggestion:** describe expected-rate targets and startup/transient overshoot, and label the chart's clipping as an idealization or model the delayed controller.
- **Status:** open.
