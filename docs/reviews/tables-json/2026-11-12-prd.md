## Findings

### R1 — Define the copy contract for decoded JSON strings

<a id="R1"></a>

- **Severity:** major.
- **Section / IDs:** Split into child PRDs / 7.5, annotation of 2026-11-12, typed extraction; Output; inherited D11, T16 and AC20.
- **Location:** `docs/prd/krummi/tables.prd.md:181–192`, `:281–283`; `docs/prd/krummi/krummi.prd.md:477–480`.
- **Problem:** typed extraction promises the logical string value, but does not define an exception or alternative public contract for strings that must be unescaped. The inherited no-copy requirement still covers string reads. The design's proposed copying accessor therefore needs a product-level clarification before it can become the implementation contract.

**Evidence.** The annotation requires “la lectura de un valor del JSON como un tipo de Krummi” and “un texto, de una cadena” (`tables.prd.md:181–182`). Root AC20 requires that a returned reference point to engine memory “y no a una copia hecha para esa lectura” (`krummi.prd.md:477–480`); T16 states the same constraint (`transactions.prd.md:45`). The current column-value exception continues to list `string` and JSON among values returned “sin copiarlos” (`tables.prd.md:281–283`), and neither the JSON annotation nor Left to the implementation settles the extraction case.

Consider the stored JSON text `{"x":"a\nb"}`. Stored form v1, explicitly incorporated at `tables.prd.md:142`, requires the newline to remain escaped in the text (`13-json-column-storage.md:698–700`). The decoded string has bytes `61 0a 62`; those bytes do not occur contiguously in that stored text. Returning the escaped spelling changes the requested string value. Returning an ordinary decoded string requires materializing it or defining a different view contract. The existing Krummi string value is `String(Cow<'a, str>)` (`crates/krummi/src/table/value.rs:297`).

The design already sketches `Cow<'txn, str>` for this accessor (`13-json-column-storage.md:632`) and limits its no-copy test to whole-document reads and escape-free strings (`:819`). Those technical proposals do not themselves declare an exception to the inherited product guarantee. A read-only Python byte check confirmed that the decoded string is not a contiguous subslice of this normalized document; this was a representation check, not an engine test.

**Observable readings.** One implementation returns an owned decoded string when escapes require it, following the design's `Cow` sketch. Another preserves the prohibition on copying through a lazy decoding view. These expose different result shapes, ownership and lifetimes; the PRD does not select or expressly delegate that choice. This is not a claim that every possible no-copy API is impossible.

**Suggestion:** explicitly settle the copy/view contract for typed JSON string extraction, preserve the whole-document no-copy guarantee, and assign its acceptance check to 7.5.

**Status:** open.

## Open product question

**Q1 (R1):** May typed extraction of an escaped JSON string return an owned decoded string, or must it retain a no-copy view? An owned result fits the design's proposed accessor but needs an explicit exception to D11/AC20; a view retains that guarantee but needs a defined decoding and lifetime contract. Whole-document text reads remain no-copy in either case. No choice is made by this review.

Questions about future JSON index families explicitly deferred in design document 14 remain with their owning future PRDs; this review does not reopen them or require an immediate answer.
