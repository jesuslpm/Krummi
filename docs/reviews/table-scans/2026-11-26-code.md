### R1 — Unbounded text and bytes filters discard all matching rows

**Severity:** blocker. **Status:** open.

**Location:** `crates/krummi/src/table/filter.rs:237` (rank selection, lines 237–239); rejection at `filter.rs:339`–341.

**Failure scenario:** a table contains a row with `id = 1`, a non-null `String` or `Bytes` column `x`, and a non-null vector. A nearest-neighbor query using this valid filter returns no rows instead of that row:

```rust
FilterCondition::Range {
    column: "x",
    lower: Bound::Unbounded,
    upper: Bound::Unbounded,
}
```

**Evidence: experimental reproduction and a source-level causal argument.** `Test::map` maps an unbounded limit without invoking the supplied function (`filter.rs:74`–84). With both limits unbounded, mapping to ranks therefore succeeds without checking the column type, producing `Some(Test::Range(Unbounded, Unbounded))` even for text and bytes. `Filter::meets` takes that fast path, but `element_rank` returns `None` for those types (`key.rs:638`); `is_some_and` rejects every non-null row. A secondary index does not avoid the problem because candidate rows still pass through the same predicate (`nearest.rs:315`). Both exact and index-based vector searches use this filter evaluator.

The coordinator compiled a standalone public-API test harness from stdin, linked to the head-built `target/debug/deps/libkrummi-c5ab749b3eed5235.rlib`, and ran `target/table-scan-review.exe --nocapture`. Each case opened a temporary store with columns `id: I64`, nullable `x`, and `v: Vector(F32, 1)`; inserted one row with a non-null `x` and vector `[1.0]`, plus one row with null `x` and the same vector; optionally created secondary index `by_x`; and called `nearest_exact` with `k = 10`. Equality on the non-null value was the control query.

| Column / value | Secondary index | Equality results | Unbounded range results | Expected range results |
|---|---|---:|---:|---:|
| String / `"alpha"` | No | 1 | 0 | 1 |
| String / `"alpha"` | Yes | 1 | 0 | 1 |
| Bytes / `[1, 2]` | No | 1 | 0 | 1 |
| Bytes / `[1, 2]` | Yes | 1 | 0 | 1 |
| I64 / `7` | No | 1 | 1 | 1 |

The harness finished with **1 passed, 4 failed**, all four failures asserting `0 == 1` for the range result count. No repository test source was edited.

**Introduced by this range:** the base's `Filter::meets` encodes the non-null row value and evaluates both unbounded limits as `true`; it has no rank dispatch. This baseline behavior was verified against source, rather than by rebuilding the base.

**Violated requirements:** S4's equivalent filter results and S6: “Los recorridos deben devolver exactamente las mismas filas, en el mismo orden, y las mismas comprobaciones de daño.” This also violates VI7/AC-VI13. The existing public SQL-filter test covers two unbounded limits only on `i64`; the added filter matrix covers fixed-width types, leaving this fallback case untested.

**Suggestion:** select the rank path by supported column type even when the condition contains no values, and add public-API regression coverage for fully unbounded text/bytes ranges with and without a secondary index.
