## Findings

<a id="R1"></a>
### R1 — major — Directive changes do not reach cached plans

- Location: `docs/design/tables/15-query-profile-and-tuning.md:476` (forcing and expiry, lines 476–486).
- Problem: installing a plan directive only changes the input to the next planning operation. No change to cache
  lookup, invalidation or revalidation is specified when a directive is installed, withdrawn or expires.
- Concrete scenario: a statistics rebuild replaces cached plan P with Q under the same catalog state. Q is more
  expensive, so the consumer records a directive to restore P. Subsequent calls keep the same parameters and
  statistics, pass ordinary revalidation and continue running cached Q. Planning need not occur again, so the
  automatic correction never takes effect. Conversely, if a forced plan becomes cached, dropping its failed
  directive or expiring its TTL does not by itself stop future calls from reusing that plan.
- Evidence type: verifiable technical argument against the documented cache contract. Design 4, lines 190–194,
  reuses a cached plan while estimates remain within the revalidation band. Design 11, lines 311–323, keys the cache
  by normalized shape, types, table identity and schema/index tokens; a same-key replan replaces the entry for later
  lookups. It includes no directive generation. The new text at design 15, lines 477–479, acts only at “next planning”,
  whereas lines 481–486 promise withdrawal and renewed planner choice. A stable hot shape can retain its cache entry
  indefinitely without eviction or catalog changes.
- Violated contract: H30, M2, and the new *Forcing* / *Trial and expiry* behavior. A related omission in earlier
  estimate feedback is not counted separately; this finding concerns the newly added plan-forcing lifecycle.
- Suggestion: specify how directive transitions change subsequent cache lookups while preserving running cursors.
- Status: open.

<a id="R2"></a>
### R2 — major — The first flush can permanently exclude a regressed plan

- Location: `docs/design/tables/15-query-profile-and-tuning.md:470` (detection, lines 470–473).
- Problem: eligibility requires both a plan new since the last flush and enough executions in that interval.
  The design does not retain a pending comparison when the first interval has insufficient evidence.
- Concrete scenario: P has adequate history at 10 pages per execution. Q first appears just before a flush,
  executes 29 times at 100 pages per execution and fails the proposed 30-execution threshold. In the following
  interval Q executes 1,000 times. It now has ample evidence but is no longer new since the last flush, so it is
  excluded. If Q remains the shape's plan, no later flush detects its sustained 10× regression.
- Evidence type: direct evaluation of the two eligibility conditions at lines 470–473. The cost statement at
  line 823 likewise limits comparisons to shapes that ran a new plan. Neither specifies reconsidering a candidate
  that missed the threshold. The scenario also applies to a frequent shape that changes plans near a boundary.
- Violated contract: H30 and automatic regression detection in *Plan regressions*; no S#/AC exists for this proposal.
- Suggestion: keep comparisons pending until sufficient evidence arrives or an explicit discard condition applies.
- Status: open.

<a id="R3"></a>
### R3 — major — Different parameter mixes can validate a uniformly worse forced plan

- Location: `docs/design/tables/15-query-profile-and-tuning.md:481` (trial, lines 481–484; detection, lines 470–474).
- Problem: exact means and percentiles from different parameter populations do not establish which plan is better.
  Both detection and trial compare separate historical windows without controlling their parameter mix.
- Concrete scenario: two index access paths P and Q have these logical-page costs for one shape:

  | Parameter set | P | Q |
  |---|---:|---:|
  | A | 10 | 1 |
  | B | 100 | 50 |

  Q is better for both sets. P's historical window contains 100 executions of A, giving mean and p95 of 10.
  Q's first window contains 100 executions of B, giving mean and p95 of 50. The specified detector declares a 5×
  regression and forces P. During trial, the workload returns to 100 executions of A: P's mean of 10 is below Q's
  historical 50, so P passes trial and stays forced. Q would have cost only 1 page per execution on that same load.
  Subsequent A-only windows continue to pass the historical comparison while paying 10× the alternative's cost.
- Evidence type: arithmetic counterexample to the specified decision rules. Aggregates are keyed by `(shape, plan)`
  at lines 281–283, not by comparable parameter populations. Lines 470–474 compare the new interval with an earlier
  window; lines 481–484 compare subsequent forced windows with the regressed plan's observations. Including all
  executions in each mean does not remove this confounding. Stage 1 adds automatic forcing before sampled executions
  exist (lines 685–689), so sampling cannot be assumed as an unstated safeguard.
- Violated contract: H30, R4, and the trial's claimed protection against retaining a plan that merely redistributes
  cost, also used as the mitigation at line 839. This finding concerns the new automatic intervention; earlier tuner
  comparisons are outside scope. No runtime failure is claimed because the proposal has no implementation.
- Suggestion: require comparable evidence between plans before forcing and confirming an improvement.
- Status: open.
