## Critical-path and test assessment

- `take_free_page` removes a free slot under the area's lock without growing the area. `SlotMut` exclusively owns its bytes; immutable snapshots and the transfer access published versions. Its private inner slot and mutable borrow prevent shared mutation through the safe API. A held slot keeps its chunk alive.
- `stage` consumes each page buffer, seals a slot before exposing it as `Slot`, and prepares the journal before publishing. Error/unwind paths retain ordinary owner-based slot release. Page order, change flags, and diff bases stay aligned. `seal_page` and in-place `seal_run` produce the same header/checksum for the same full payload.
- Maximum-size accounting continues to include transaction pages through `dirty` and `run_pages`; reserving an existing slot does not add area growth. The fallback retains the existing payload path. Payloads successfully copied during staging can be recycled; unstaged payloads dropped after a failed stage are the known performance limitation recorded in L16, without a demonstrated data-correctness defect.
- New tests cover stored-byte equivalence with slots enabled/disabled, publication from the same address, zeroing reused slots, no-slot fallback, allocation failure, reader isolation, abort/reuse, and preservation of spare payloads.
- Coverage limitations, not additional demonstrated defects: existing panic tests (`crates/krummi-tx/tests/commit.rs:63` and `:215`) traverse the slot path after initial commits leave free slots, but do not explicitly assert that precondition. The run-commit error test (`crates/krummi-tx/tests/runs.rs:846`) can fail after staging slot pages while growing for a run. There is no explicit regression test forcing both `PageBuf::Slot` and `PageBuf::Payload` in a partially failed stage and asserting both returns. Dedicated concurrent slot-mutation and forced-slot crash probes described in L16 were not retained as tests; their reported outcomes are historical claims, not independently executed checks here. Real allocator failure at the new spare-vector reservation is not injectable by the existing fault hooks.
