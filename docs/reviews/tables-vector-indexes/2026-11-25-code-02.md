(`:713`, `:869`, `:909-925`), after the relevant target identity checks. Dropping a preceding column therefore

<a id="R2"></a>
### R2 — Verified resolved: the complete supported primary-key domain is indexable

Original: [R2](2026-11-25-code.md#R2), blocker. Fix: `52fe70482badac8577805c6b297e06c858068518`.

`vector_worker.rs:461-542` limits inline keys to 2,039 bytes. Longer keys use numeric references, exact
prefix buckets and full-key comparisons. Posting/locator keys remain below the tree limit; number and
lookup-map writes occur in the same worker transaction (`:1426-1458`). Search resolves the complete primary
key before pending exclusion and candidate ordering (`nearest.rs:629-647`). Generation cleanup includes
the new long posting/locator tags (`vector_worker.rs:1123-1140`); whole-tree destruction remains shared with
ordinary index/table cleanup (`catalog.rs:796-800`, `vector_index.rs:435-437`).

Both reviewers' runs of `codex::r2_long_primary_keys_are_indexed` passed the original worker-panic case and
subsequent update/delete/search checks. An additional external public-API probe was independently run by
the delegated reviewer and coordinator on separate disposable on-disk stores:

- Construct 256 distinct encoded composite keys of exactly 2,048 bytes sharing their first 2,047 bytes:
  string component `"a".repeat(2043)` and `u16` component `256..512`.
- Build over 10,000 short-key vectors plus those keys; compare exhaustive indexed and exact results,
  asserting identical keys and distance bits, not merely a live worker or successful build.
- Exercise pending update/delete/null/new long key; abort foreground mutations and a rebuild request;
  rebuild with pending changes; durable close/reopen; reinsert and rebuild again; query an older snapshot;
  drop/recreate the index; empty/drop the table.
- Both runs passed; final used pages returned to the pre-table baseline of **5**.

The ODD L25 dismissal of `R3-long-bucket-growth` is supported: admitted keys are self-delimiting for a fixed
schema, so a shared 2,047-byte prefix permits at most 256 full-key variants at the 2,048-byte maximum.
The largest bucket is `256 * (8 + 4 + 2048) = 527,360` bytes, below the 256 MiB value limit. The composite-key
probe exercises this bound. Removed-key maps do persist until index/tree destruction, as the resolution
explicitly documents; this is not an unbounded single bucket or evidence that the dismissal is false.

Evidence covers S1, inherited E18 and affected VI3/VI4/VI9/VI10/VI12/VI13 behavior. Transaction fault tests
also passed, but no fault was injected specifically between individual long-key allocation-map writes.

### R3 — Verified resolved: automatic reconstruction counts non-null vectors

Original: [R3](2026-11-25-code.md#R3), major. Fix: `7f7a39c61be92dad1444329bf0dc434a21822c43`;
dependent optimization: `08a238f9bf084b66d189ba5fe38503c66e27eda0`.

`vector_worker.rs:1021-1050` derives the current non-null-vector population from active entries, subtracts
entries shadowed by pending keys and adds pending rows with vectors. Rebuild eligibility/list selection use
that population (`:1185-1208`), not total table rows. Untrainable reconstruction is cancelled even when the
sample result is memoized (`:595-607`). The optimization defers this count until an indicator warrants it;
it does not restore total-row eligibility.

Reviewer and coordinator reran `codex::r3_rows_without_a_vector_start_no_rebuild`: after the deletion leaves
1,000 vectors among 13,000 rows, the index stays `Ready`, not idle in `ReadyRebuilding`, with trained-row
ratio `Some(0.1)`. Full vector/rebuild tests passed. This verifies S1, VI9/VI11 and AC-VI16:
«solo se reconstruye un índice listo de una tabla con al menos 10.000 filas con vector».
