## Open finding

R6 is new in this report; R1–R5 retain their original identities below.

<a id="R6"></a>
### R6 — Major: deferred index creation can lose its only effective worker activation

**Location:** `crates/krummi/src/table/catalog.rs:327-331,632-633` (removed `resume_once` calls), together with
startup at `crates/krummi/src/lib.rs:198`. Dependent unchanged code:
`lib.rs:1643-1654`, `table/vector_worker.rs:283-298,369-387`.

**Failure scenario:** create the first vector index using a deferred transaction. The already-running worker can
consume its activation before that transaction is durable, read a catalog without the new index, and go back to
sleep. Making the transaction durable and subsequently opening its table no longer activate it. The index stays
`Training` despite having 10,000 valid vectors, until another activation or reopening.

**Independent public-API reproduction:**

1. Open a fresh persistent store and wait for initial vector work to become idle.
2. Create `t(id: i64 NOT NULL, v: vector<f32,1>)`, primary key `id`; insert 10,000 rows with
   `id = 0..9999`, `v = [(id % 100) as f32]`; commit durably.
3. In a new transaction create the first L2 index, `near(v)`. In the same transaction create an ordinary tree
   `other` and store an incompressible 8 MiB value at key `key`, widening the normal journal-flush window.
   Commit with `commit_deferred()`.
4. Call `make_durable()`, open `t` in a new read and fetch index information, then `wait_vector_idle()`.
   Sleep 20 ms and fetch information again. No journal fault or journal pause is injected.
5. Observe `Training`, `pending=0`, a live worker and zero worker batches. Explicitly activating the worker with
   the test hook `pause_vector_work(false)` immediately allows it to finish: `Ready`, empty `check_vector_index`.

The coordinator and delegated reviewer each ran the same program against both revisions, with separate fresh
stores. Both independently observed:

```text
HEAD: round 0..9: first=Training, after=Training, pending=0, alive=true, batches=0
HEAD: every explicit wake rescued=Ready
HEAD: stalled=10/10
BASE: round 0..9: after=Ready
BASE: stalled=0/10
```

Both executables exit zero because the diagnostic program counts stalls and verifies the explicit-wake recovery;
exit zero is **not** a passing candidate verdict. Without the extra value write, the reviewer also reproduced
2/10 stalls at HEAD versus 0/10 at the base. The extra write is a valid ordinary transaction, not fault injection.

**Causal evidence:** `commit_deferred` expressly permits reads to lag until durability (`lib.rs:1643-1647`) and
calls `vectors.kick` immediately after its deferred commit (`:1652-1654`). `run` clears `kicked` before the scan
(`vector_worker.rs:283-285`); an empty target list yields `Ok(false)` and returns it to its indefinite condition
wait (`:288-298,371-387`). There is no durability-completion activation in this path. The base's first subsequent
table opening called `resume_once`, providing a second activation after the index became visible; this range
removes that fallback. Thus the early notification itself predates the range, but the demonstrated previously
working deferred-create → durable → table-open sequence regresses in the correction. Merely opening the store
earlier is not a substitute for activating work once its definition becomes visible.

**Requirement:** S1, VI4 and AC-VI15, including «con la fila 10.000, el índice entrena». The VI15 durable-only
insertion-performance decision does not exempt deferred transactions from functional index maintenance.

**Impact/severity:** major liveness and performance defect, not demonstrated data loss. Source rows remain
available through exact search. Waiting longer cannot itself wake a worker sleeping without `kicked`; ordinary
later vector mutations may hide the defect by supplying another activation.

**Suggestion:** guarantee activation after relevant committed changes become visible to worker snapshots while
preserving the requested startup behavior.
