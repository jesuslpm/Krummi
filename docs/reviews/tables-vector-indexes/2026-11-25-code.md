### R1 — Blocker: a concurrent unrelated column drop silently removes valid vector entries

**Location:** `crates/krummi/src/table/vector_worker.rs:398-403`, `824-878`; insufficient validation at
`1127-1129`. Related schema change: `crates/krummi/src/table/schema.rs:698`.

**Failure:** a worker target retains a vector column's positional index across a schema change. Removing a preceding
column shifts that position without changing the vector index's identity or instance. A later reconciliation reads
the wrong position, treats the vector as absent, removes the posting and clears the pending marker. A committed
non-null vector is then represented by neither the index nor its pending log, so indexed searches silently miss it.

**Observed reproduction (public API, temporary store):**

1. Create table `b(id: i64, n: i64?, v: vector<f32,1>?)`, primary key `id`, with 10,000 rows:
   `id = 0..9999`, `n = 0`, `v = [id as f32]`. Create L2 index `near(v)`; wait until ready.
2. Pause vector work, hold `VectorPoint::Sampled`, and create the same populated/indexed table named `a`.
   Resume and wait for its training to reach the hold. This keeps the already enumerated target for `b` stale
   without holding the application's write turn.
3. In one committed write, drop `b.n` and update row 42's vector to `[-100.0]`.
4. Release the hold and wait for vector work to become idle. Force the indexed path with the existing test hook
   (`set_vector_search_threshold(Some(0))`), rerank all candidates and probe all lists; query `[-100.0]`, k = 1.

Coordinator and reviewer both observed:

```text
state: Ready, pending: 0
check_vector_index: ["g1: row [21, 42] has no entry"]
exact:   id 42, distance 0.0
indexed: id 0,  distance 100.0
```

The small probe uses hooks to expose the indexed path at 10,000 rows. With more than the default 20,000 passing
rows the same stale-position race affects the ordinary indexed path; the schema/reconciliation bug is unchanged.
The exhaustive probe/rerank eliminates normal ANN approximation as an explanation.

**Causal evidence:** `Target.place` is captured at `355-358`; `step` refreshes roots/counts but clones that old
position at `398-403`. Identity/instance checks do not validate the schema. The write passes the old position to
`row_vector` at `831`, reconciles the absent value, then removes pending at `878`.

**Requirement:** S1, VI3, VI5, AC-VI2/AC-VI5; specifically:
«El índice nunca deja de reflejar una fila confirmada: o la refleja, o la fila está en el registro de pendientes.»

**Suggestion:** resolve the indexed column by identity in each current snapshot/write, or reject work prepared for
a different schema before clearing any pending entry.

### R2 — Blocker: valid primary keys panic the store's only vector worker

**Location:** `crates/krummi/src/table/vector_worker.rs:441-444`, `1252-1256`;
also locator encoding at `447-450`.

**Failure:** posting keys concatenate a nine-byte tag/generation/list prefix with the full primary key.
Tables already admit encoded primary keys up to 2,048 bytes
(`crates/krummi/src/table/key.rs:24`), which is also the internal tree's maximum. Valid user keys can therefore
exceed that internal limit after prefixing. `krummi_tree::set` reaches the assertion at
`crates/krummi-tree/src/lib.rs:1087-1089` and panics instead of returning a recoverable batch error.

**Observed reproduction (public API, temporary store):** create 10,000 rows with a one-dimensional f32 vector
and a string primary key. Use short keys for 9,999 rows and `"a".repeat(2040)` for the last row. That last key
encodes to 2,042 bytes and is successfully inserted and committed. Create its L2 vector index and resume work.

Both runs observed:

```text
thread 'krummi-vectors' panicked at .../krummi-tree/src/lib.rs:1087:5:
a key has 1 to 2048 bytes
alive=false
state: Building, lists: None, pending: 0
```

The posting key is 2,051 bytes. The foreground write accepted valid data, but the index cannot finish building;
the one shared vector-worker thread exits, affecting other indexes as well. The source rows are not lost:
searches without a ready generation remain exact. This does not make the failed maintenance acceptable.
Existing long-key data cannot be repaired merely by reopening and retrying the same construction.

**Evidence:** repeated public-API reproduction plus the unconditional internal-key assertion. Both prefix encodings
are new in this range; the inherited primary-key limit is not new.

**Requirement:** S1, VI4/VI13 and inherited E18. A valid table key must not terminate asynchronous maintenance;
worker failures must follow the specified rollback/retry behavior.

**Suggestion:** use an internal representation that accommodates the complete supported primary-key domain
without exceeding the underlying tree's key limit.

<a id="R3"></a>
### R3 — Major: null-vector rows can leave automatic reconstruction permanently active

**Location:** `crates/krummi/src/table/vector_worker.rs:1047-1062`, `503-514`.

**Failure:** automatic-rebuild eligibility and list-count change use `target.rows`, the total table row count,
rather than the number of non-null vectors. After a reduction below 10,000 vectors, null rows can keep the total
above 10,000 and incorrectly trigger reconstruction. Training counts the real vectors, cancels and records
`untrainable`. The next pass starts reconstruction again, but the memoized early return skips cancellation.
The worker becomes idle while the public state remains `ReadyRebuilding`; further requests are no-ops in that state.

**Observed reproduction:** start with 10,000 non-null vectors and 12,000 null-vector rows; build a ready index with
10 lists. Delete vector-bearing keys `0..9000`, commit and wait for `wait_vector_idle()`. There are now only
1,000 vectors but 13,000 table rows. Both runs produced:

```text
before: Ready,           lists: Some(10), pending: 0, rows_against_trained: Some(1.0)
after:  ReadyRebuilding, lists: Some(10), pending: 0, rows_against_trained: Some(0.1)
```

**Causal evidence:** the total count drives `lists_for(target.rows)` at `1052` and the minimum gate at `1061`.
The failed sample is memoized at `513`; on the next training attempt `503-504` returns before the cancellation
at `514`. No foreground changes remain to invalidate the memo.

**Requirement:** S1, VI9/VI11, AC-VI16:
«solo se reconstruye un índice listo de una tabla con al menos 10.000 filas con vector».

**Suggestion:** base eligibility/list changes consistently on non-null-vector counts and ensure the memoized
untrainable path cannot leave a reconstruction active.

### R4 — Major: the broad-filter comparison does not satisfy matched-recall measurement

**Location:** `odd/tasks/tables-vector-indexes-report.md:102-110`, particularly `106`.

**Failure:** the closing report compares a broad-filter Krummi result at recall@10 **0.9425** with a PostgreSQL
result at recall **1.0**, and uses their 27.6 ms versus 354 ms p95 values as the VI15 comparison.
These are not the same quality of result, and Krummi's chosen point is below 0.95. This does not fulfill the
explicit matched-recall comparison for the broad-filter case even though the separate unfiltered threshold passes.

**Verifiable artifact evidence:** the committed table states these unequal recall values itself. VI15 requires:
«Compara, en un hilo (...) el p95 de Krummi y de pgvector con la misma recall@10 de al menos 0,95, sin filtro y con
un filtro que deja pasar pocas filas y otro que deja pasar muchas».

The lab already sweeps filtered probes at `crates/krummi-ann-lab/src/engine.rs:415-424`; this is not a missing
probe-sweep implementation. Supplementary ignored `work/ann/motor.md` contains a broad-filter point at 50 probes,
recall 0.9600 and p95 31.49 ms, but that still does not by itself provide the required matched-quality comparison
against PostgreSQL's reported exact result. The closing report also says no PostgreSQL plan was observed:
its assertion that a scan was exact should not substitute for recorded execution-plan evidence.

**Requirement:** S3, VI15, AC-VI11's comparison/reporting component. This is a demonstrated measurement/report gap,
not evidence that the unfiltered 0.95/20 ms engine threshold failed.

**Suggestion:** report corresponding measured points at a common recall of at least 0.95 and record the actual
PostgreSQL query plan used for the filtered comparison.

<a id="R5"></a>
### R5 — Minor: the new motor command silently ignores an explicit dataset selection

**Location:** `crates/krummi-ann-lab/src/main.rs:65-80`;
`crates/krummi-ann-lab/src/engine.rs:148`, `352`, `465`.

**Failure:** the shared CLI accepts `--conjunto sift` or `glove` with `motor`, but the engine measurements always
load `Set::Cohere`. With multiple prepared datasets, the requested dataset is silently replaced; without Cohere,
the command fails for an unrelated missing Cohere file instead of rejecting the unsupported option.

**Observed non-destructive reproduction:** in a newly created empty disposable folder:

```text
cargo run --locked --offline --quiet -p krummi-ann-lab -- motor --carpeta <empty-temp> --conjunto sift --paso buscar --filas 1
No se pudo leer o escribir <empty-temp>/data/cohere-base.fvecs: No such file or directory (os error 2)
exit code: 1
```

**Evidence:** the parser accepts the flag; the selected step demonstrably tries Cohere. Source inspection confirms
the same hardcoded dataset in loading/search/threshold steps. No destructive `cargar` execution was needed.

**Requirement:** CLI option correctness and review-code's explicit-option check; no additional dataset support is
required by VI15, which intentionally prescribes Cohere. This is limited to lab validation/help and does not prove
that the recorded VI15 dataset was wrong or that engine search results are wrong.

**Suggestion:** reject non-Cohere dataset selections for this Cohere-only command and document its applicable options.

## Open product questions — not defects

   commits. The closing report measures durable at 0.928× (passes) and deferred at 1.118× (above 1.10×), then treats
   deferred as informational. User confirmation is needed before claiming that this interpretation closes the gate.
2. VI12 says the worker resumes when the store opens, while the implementation and closing report deliberately
   defer it until a transaction opens a table with a vector index, to preserve inherited opening/cache behavior.
   Confirm whether that lazy-resumption interpretation is accepted, or reconcile the PRD and inherited requirement.
   The documented implementation default is not evidence of user approval.
