## Findings

All five findings remain open.

<a id="R1"></a>
### R1 — blocker — Persistent index writes are classified as unchanged transactions

**Section / IDs:** Product decisions / VI3, VI9; Validations and messages. Target lines 73, 79 and 141.

**Evidence:** VI3 says, “Los lotes no cambian filas, así que no son cambios para T10”. VI9 says a rebuild request “vale cuando se confirma, sobrevive al cierre”. The validations state, “Las búsquedas, la información y reconstruir no son cambios para T10”.

T10 concerns transaction changes, including persistent metadata and pages, rather than only row modifications. Its current journal rule E11 explicitly says an unchanged commit “En ningún caso escribe en el diario” (`docs/prd/krummi/journal/journal-group-commit.prd.md:51`). The implementation takes the unchanged path when there are no dirty pages or new runs (`crates/krummi-tx/src/transaction.rs:630`); it only waits for previously observed commits when necessary. The cited statistics precedent classifies saving statistics inside a write as a change for T10 (`docs/prd/krummi/tables/tables-statistics.prd.md:56`, ST7).

Worker batches must persist changes to postings, generations, build progress and pending rows. Such batches cannot simultaneously be unchanged transactions under T10. Likewise, the request-only transaction needs a consistent contract for its persistent rebuild request. No exception to the unchanged-commit contract is declared. Treating metadata writes as changes violates the draft's classification; following its unchanged classification cannot provide the required transactional persistence.

**Suggestion:** distinguish absence of row modifications from persistent transaction changes, and align VI3 and rebuild requests with T10.

<a id="R2"></a>
### R2 — blocker — The k-result guarantee includes rows whose vectors cannot be returned

**Section / IDs:** Product decisions / VI1, VI6; Acceptance criteria / AC-VI13. Target lines 71, 76 and 244–247.

**Evidence:** VI1 states, “Una fila con el vector nulo no está en el índice y nunca es un resultado”. VI6 states, “Sin filtro, todas las filas pasan” and “devuelve k filas siempre que al menos k cumplan el filtro”.

A ready index may belong to a table with many rows, while a relational filter selects ten rows, one with a null vector. With k = 10, all ten satisfy the relational filter, but only nine may be returned under VI1. Probing every list cannot satisfy the promised cardinality. An even simpler permitted case is updating every vector to null without deleting the rows: no filter and k = 1 require a result under VI6 and forbid every result under VI1. Updating rows is distinct from emptying the table, so VI10 does not resolve this case.

The eligible population must also be explicit for the exact/approximate threshold: counting relational matches including null vectors versus counting only searchable vectors can produce a different public search-mode flag. AC-VI13 does not establish this boundary.

**Suggestion:** reconcile the cardinality guarantee with null-vector exclusion and explicitly define the population used for the threshold.

<a id="R3"></a>
### R3 — major — Dropping a missing index is both a no-op and an error

**Section / IDs:** Product decisions / VI1; Validations and messages. Target lines 71 and 130.

**Evidence:** VI1 says, “Sigue las reglas de 7.2” for “borrar (IX4)”. IX4 says, “Si la tabla no tiene un índice con ese nombre, no hace nada” (`docs/prd/krummi/tables/tables-indexes.prd.md:49`). However, target line 130 includes “Borrar” in the missing-vector-index cases that return “Esquema distinto”. Existing `drop_index` returns success when the index name is absent (`crates/krummi/src/table/index.rs:812`).

**Observable readings:** follow IX4 and succeed without changes, or follow the validation table and return a schema-mismatch error. No override of IX4 is declared, so either implementation contradicts a stated rule.

**Suggestion:** select one behavior and align the decision, validation and acceptance contract.

<a id="R4"></a>
### R4 — major — Index indicators have no defined output when unavailable or undefined

**Section / IDs:** Product decisions / VI9, VI11; Output; Acceptance criteria / AC-VI17. Target lines 79, 81, 153 and 260–262.

**Evidence:** VI11 specifies “el número de listas de la generación que usan las búsquedas, o ninguno si no hay”, but also requires “los indicadores de VI9 de esa generación” without an absence rule. AC-VI17 requires their values “también sin generación lista”. VI9 includes “el tamaño de la lista mayor frente a la media”.

During initial training there is no searchable generation from which to obtain the indicators. Another reachable case is deleting every row individually and allowing maintenance to drain the index: VI10 resets the state for explicit table emptying, but does not reset a ready generation when its last row is individually deleted. All lists can then be empty, making largest-list size divided by mean list size 0/0. Design document 12's *SQ8 quantizer and drift* section lists these counters but provides no output convention for these cases.

**Observable readings:** return absent/not-applicable indicators, substitute numeric conventions, or preserve earlier values. Those choices change public information and the interpretation of the rebuild conditions. Choosing field/type names in *Left to the implementation* does not settle what these values mean.

**Suggestion:** define unavailable indicators and zero-denominator cases, with corresponding output examples and acceptance cases.

<a id="R5"></a>
### R5 — minor — The starting state overlooks existing background threads

**Section / ID:** Starting state / Background work. Target line 97.

**Evidence:** the draft says, “El almacén tiene un hilo, el de las estadísticas de 7.3” and “no hay otro trabajo en segundo plano”. Besides the statistics worker, the engine starts `krummi-journal` (`crates/krummi-pager/src/journal.rs:591`) and `krummi-transfer` (`crates/krummi-pager/src/transfer.rs:259`). The statistics worker is confirmed in `crates/krummi/src/table/worker.rs:102`.

The intended comparison may be limited to table maintenance that takes the write turn, but the current claim describes the whole store and is false against source.

**Suggestion:** scope this starting-state statement to background table maintenance that acquires the write turn.
