**Lineage:** [original R1](2026-11-04-code.md#R1), [round 2 R1](2026-11-04-code-02.md#R1), and [round 3 R1](2026-11-04-code-03.md#R1). Reviewed correction: `384e13edab1b47f6f41c18030f93caaf3edd6022`; documentation/test-comment refinement: `c148cdfadce56a64bad8bbe43cb5602a0ac8f62e`.

D10 defines the reader's completion observation immediately after checksum verification, as already assessed in round 3.

**Source verification:** `crates/krummi-bench/src/worker.rs:911–912` finishes all write batches before calling `finish`. At `:1011–1014`, that function stores `FINISHING` with `SeqCst`, executes a `SeqCst` fence, and then samples the end. This removes the release-store/store-buffer window established in round 3 on the supported x86-64 platforms. The optimized Windows x64 harness assembly independently shows `xchgb`, a locked `orl` fence, and then the call to `Instant::now`, in that order. This is evidence about the compiled harness, not an assertion that every processor must execute the reader at a particular instant. The [Rust fence documentation](https://doc.rust-lang.org/std/sync/atomic/fn.fence.html) was consulted alongside source and generated code.

The reader's extracted `record` (`worker.rs:1019–1025`) preserves the existing decision: count `WRITING`, timestamp boundary phases, stop at `ENDED`. `ReaderTally::reads_in` (`:971–973`) filters those boundary timestamps against the same writer interval. In Voron, `crates/krummi-bench/voron/Loads.cs:435–437` now performs `Interlocked.Exchange(ref phase, Finishing)` before sampling `we`. The [.NET memory-model specification](https://github.com/dotnet/runtime/blob/main/docs/design/specs/Memory-model.md#order-of-memory-operations) explicitly gives `Interlocked` operations full-fence semantics, supporting the analogous correction.
