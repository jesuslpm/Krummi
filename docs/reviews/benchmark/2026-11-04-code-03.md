<a id="R1"></a>
### R1 — minor — W12 can still count reads after the writer's measured end

**Locations:** `crates/krummi-bench/src/worker.rs:912–913`, `:996–999`; analogous publication and counting in `crates/krummi-bench/voron/Loads.cs:434–435`, `:457–467`. The unconditional count bypasses timestamp filtering at `worker.rs:973–974` and `Loads.cs:473–474`.

**Problem and concrete failure scenario:** on a supported multiprocessor machine, the writer issues its `FINISHING` release store and samples its end while another processor can still observe the older `WRITING` value. A reader whose completion observation is after that sampled end increments `inside` without recording a timestamp. Aggregation counts it unconditionally, divided by an interval that has already ended. Publishing `ENDED` afterwards does not retract that increment.

The new fix correctly addresses the previously reproduced writer scheduling gaps: reads in `NOT_STARTED` and `FINISHING` now receive timestamps and readers continue until `ENDED`. An adapted extraction of the production counting code counted exactly 2,010 expected in-interval reads among 3,011 reads under controlled phase-publication delays. The remaining problem is publication ordering across processors, not the earlier objection about descheduling between checksum completion and recording. It persists under D10's clarified definition of completion as the reader recording the read.

**Evidence — independent concurrent protocol reproduction:** a minimal Rust harness preserved the production writer sequence (`WRITING` release store, mock work, `FINISHING` release store, `Instant::now`, `ENDED` release store) and the reader's acquire-load decision. Two barriers isolated every round and its reset. Immediately before the reader's phase load, instrumentation sampled `Instant::now` and executed a sequentially consistent fence. An observed `WRITING` with that preceding timestamp greater than the writer's end therefore demonstrates an after-end observation. The reader fence strengthens the observation and is not a weakening of production synchronization.

On Windows x64, `rustc 1.99.0`, optimized harnesses compiled with `rustc --edition 2024 -O` produced:

```text
Release FINISHING, reader instrumentation fence:
over_100ns=92, over_1000ns=47
clock/phase stress: rounds=1000000, WRITING_observations_proven_after_end=15194, maximum_lateness_ns=318700

Control: only FINISHING changes from Release to SeqCst, same reader instrumentation:
over_100ns=0, over_1000ns=0
clock/phase stress: rounds=1000000, WRITING_observations_proven_after_end=0, maximum_lateness_ns=0
```

The sources are disposable artifacts `target/review-benchmark-round3/ordering_reader_fence.rs` and `ordering_both_fences.rs`, with SHA-256 `e141f4d362dea16e167a397ea6467d9df0e240226e3d50915956ad22e59b89a9` and `b90acad2c71f4d46b443b916e84af7b3d8f9c611b67dcc9f9c1c03ca2a5de8c3`, respectively. Additional runs without the reader fence reproduced the issue; adding a writer fence before the release store, modeling already-flushed preceding work, also did not eliminate it.

This isolates the actual clock/phase protocol with a mock writer, rather than running a storage workload. The counts are rounds exhibiting at least one invalid observation, not the percentage of incorrect operations in a real benchmark. No contribution to historical benchmark results or threshold outcomes has been quantified, and the control is evidence about this experiment rather than a complete proposed fix.

**Source support:** [Rust's ordering specification](https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html) describes release ordering for operations preceding the store; it does not establish the needed visibility before a subsequent clock sample. [Microsoft's `Volatile` documentation](https://learn.microsoft.com/en-us/dotnet/api/system.threading.volatile?view=net-10.0) likewise explicitly permits a later reader to observe the older value. Voron has the same unfiltered counting assumption. Its analogous issue is supported by source and ordering semantics, but no C# interleaving reproduction or end-to-end incidence is claimed here. The independently reproduced Rust path alone establishes that R1 remains open.

**Requirement:** K8/W12, incorporated by the specs: “El tiempo es el del escritor, de su primera operación a su última confirmación; cuenta cada lectura individual que termina en ese tiempo.”

**Severity:** reduced from major to **minor** because the previously demonstrated large scheduling gaps are fixed; the residual boundary-counting error is demonstrated, but material impact on complete benchmark results is not established. It remains R1 because it is the same interval/counting invariant, not a separate new finding.

**Suggestion:** ensure finishing publication and the end timestamp exclude stale `WRITING` observations across processors, and cover that ordering with a concurrent regression test.
