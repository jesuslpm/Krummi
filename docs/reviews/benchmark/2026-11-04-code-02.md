<a id="R1"></a>
### R1 — major — W12 counting still differs from the writer's measured interval

**Locations:** `crates/krummi-bench/src/worker.rs:911–915`, `:962–966`; `crates/krummi-bench/voron/Loads.cs:427–431`, `:449–459`. Metric consumers: `worker.rs:928–935` and `src/measure.rs:15`.

**Problem and concrete failure scenarios:** the timestamp and the phase publication remain separate operations. If the writer is descheduled after taking its start but before publishing `WRITING`, readers complete reads inside the recorded interval without counting them. If it is descheduled after publishing `DONE` but before recording its end, readers stop while the denominator continues growing. Both Rust and Voron have these gaps. The latter gap affects W13's denominator as well as W12's. Conversely, a reader can complete its value checksum before the writer starts, be descheduled before loading the phase, then resume during `WRITING` and count that pre-start read.

The resolution acknowledges undercounting windows but calls them adjacent instructions. Adjacency does not bound a scheduling pause. Undercounting also violates the requirement and can alter the ratio and threshold decision; applying similar code to each engine does not make their scheduling delays equal. D10's added explanation is an implementation decision, not an override of K8/W12.

**Evidence:** independently checked source/interleaving argument, plus a controlled mock reproduction using the production `read_until` function and constants extracted without changes. The temporary harness took the writer interval's start, allowed 1,000 reads while publication of `WRITING` was delayed, then 10 during `WRITING`, and one at `DONE`, before recording the interval's end. Channels forced the writer scheduling gaps. It observed:

```text
production read_until: counted=10, completed_inside_recorded_interval=1011, elapsed_ns=209700
```

This is a reader-counting reproduction with mock storage and controlled scheduling, not an end-to-end engine measurement. The unchanged extracted production fragment had SHA-256 `61e349b8f17d1a05e4860519852c92d8e381f6a82a0fb284d69d564d4af53661`. The original review had source evidence only; the new phase-driven unit test passes but does not relate phase transitions to writer timestamps. The analogous Voron defect is established by its matching control flow; a forced C# interleaving was not run. No contribution to the historical benchmark numbers is quantified here.

**Requirement:** K8 and workload W12, incorporated by the specs: “El tiempo es el del escritor, de su primera operación a su última confirmación; cuenta cada lectura individual que termina en ese tiempo.”

**Suggestion:** make counting and the denominator use the same verifiable interval, with controlled tests for scheduling pauses at both boundaries.

<a id="R3"></a>
### R3 — minor — Finalization interruption can still leave the report when removal fails

**Locations:** `crates/krummi-bench/src/orchestrator.rs:92–94`; callers at `:65–78`, report creation at `:265–275`.

**Problem and concrete failure scenario:** after the report has been written and closed, the command removes the work subfolder before calling `settle`. On Windows a report viewer or scanner can open that visible report without sharing deletion. If Ctrl+C arrives during finalization, `settle` attempts one deletion, ignores its failure and returns `Interrupted`. The command prints `Banco interrumpido.` and returns `1`, but leaves the report. Even a temporary lock leaves it permanently because there is no subsequent retry.

The new check fixes the original success-code behavior during cleanup. It does not complete the required report rollback. The added unit test exercises only successful deletion. The existing work-subfolder cleanup already retries transient Windows file retention; the new report cleanup does not.

**Evidence:** independent Windows reproduction using the production `settle` function extracted without changes, an owned disposable report, and a read handle opened with `OpenOptionsExt::share_mode(3)` (read/write sharing, without delete sharing). Passing an interrupted successful result produced:

```text
production settle: result=Err(Interrupted), report_remains=true
```

The test then closed the read handle and successfully deleted its report and temporary directory. This verifies the actual filesystem failure and helper result, not a full command run with a real console signal. The production flag-to-helper and helper-to-message/exit-code paths were checked separately in source. No external scanner's frequency is asserted. A preexisting report remains protected: failed `create_new` produces an error result, which `settle` does not delete.

**Requirement:** S9 / AC-K9 and the Ctrl+C row: “Igual que un fallo: termina los procesos de los motores, borra su subcarpeta y no escribe informe”, with `Banco interrumpido.` and exit code `1`.

**Suggestion:** handle transient report-removal failures and verify rollback rather than silently treating a failed deletion as completed cleanup.

<a id="R5"></a>
### R5 — minor — The report-folder probe can leave a file after initial validation fails

**Locations:** `crates/krummi-bench/src/cli.rs:138–141`; subsequent prerequisite check at `crates/krummi-bench/src/orchestrator.rs:115–116`.

**Problem and concrete failure scenario:** the R2 fix creates a probe, closes it, ignores its deletion error and unconditionally returns success. On Windows, another reader can open the new probe without sharing deletion between the close and removal. The probe remains even after that temporary reader releases it. If the following RavenDB validation fails, the command exits before running the benchmark but has left `.krummi-bench-<pid>-<nanos>.tmp` in the report folder. There is no later cleanup owner for that path. The unique-name refinement avoids collisions with leaked probes but does not remove them.

**Evidence:** independent Windows reproduction using extracted `can_create_in`, with one explicit scheduling hook after `drop(file)` opening the probe with `share_mode(3)`. The remaining helper code was unchanged. It produced:

```text
can_create_in with controlled scanner interleaving: result=Ok(()), leaked_probes=1
```

The added handle was released when the helper returned; the file still existed and was then removed by the harness. This experimentally establishes the cleanup failure and unconditional success under the modeled interleaving. It is not a full CLI/antivirus reproduction and does not use a denied-delete ACL. The later RavenDB failure and lack of probe cleanup follow directly from the checked caller. The added unit test checks only that deletion succeeds in an ordinary writable folder.

This is a limited-impact regression introduced by `6afd038`, still present after `14730a4`; it is distinct from R2's corrected inability to detect denied file creation.

**Requirement:** S9 / AC-K9 and the ordered initial-validation rules, which say “La orden no hace nada.” when a prerequisite fails. The probe's cleanup promise and its new test also require leaving the checked folder as it was.

**Suggestion:** make probe cleanup part of the validation outcome and cover a transient deletion failure without leaving an unowned probe.
