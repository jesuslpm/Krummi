## Findings

<a id="R1"></a>
### R1 — major — Exhausting one scan end leaves the other able to fail and invalidate a write

**Location:** `crates/krummi-tree/src/range.rs:362`, the `Ok(None)` branch of `guard`.

**Status:** verified still open; original finding `docs/reviews/trees-scan/2026-10-26-code.md#R1`. No fix commit is present in the requested range.

**Problem and failure scenario:** normal exhaustion marks only the selected end finished. After a one-entry scan returns its entry and then `None` from the front, first using the back still descends and allocates its path. If that allocation fails, the completed scan returns `Some(Err(OutOfMemory))` and poisons its write transaction. A previously valid commit is rejected and pending changes are not applied. The same failure occurs with the directions reversed. This unnecessarily rejects pending work; it does not lose already committed data.

**Evidence: fresh experimental reproduction and source argument.** The coordinator compiled a public-API probe from stdin against the checked libraries into `target/review_exhaustion_round2.exe`. For each direction it created a pending tree, stored one entry, consumed that entry and `None`, reset fault counters, injected failure of the next allocation, and first used the opposite end. Assertions verified the returned error, commit rejection and absence of the pending tree in a new read. Both cases reproduced:

```text
front=true: exhausted end; opposite end errors OutOfMemory; commit rejected; pending tree absent
front=false: exhausted end; opposite end errors OutOfMemory; commit rejected; pending tree absent
```

The essential front-first sequence, after creating `pending` and storing its entry, was:

```rust
let mut scan = write.range(&tree, ..).unwrap();
assert!(scan.next().unwrap().is_ok());
assert!(scan.next().is_none());
testing::reset();
testing::inject(Op::Alloc, 0, Action::Fail(std::io::ErrorKind::OutOfMemory));
assert_eq!(scan.next_back().unwrap().unwrap_err().kind(), ErrorKind::OutOfMemory);
testing::reset();
drop(scan);
assert_eq!(write.commit().unwrap_err().kind(), ErrorKind::OutOfMemory);
assert!(!store.read().unwrap().tree_exists("pending").unwrap());
```

The reset immediately before injection is required: fault indices count from the last reset. An initial setup trial without that reset did not trigger the intended allocation failure; the corrected probe above reproduced it in both directions.

The source chain is `guard` leaving the other end active, its seek reserving a path before detecting crossing (`range.rs:204,221`), `reserve` propagating through `PageSource::fail` (`krummi-tree/src/lib.rs:110`), and write failure recording / commit rejection (`krummi-tx/src/transaction.rs:234,264`). The scan API is new in this range.

**Requirement:** R1 / AC-R1 / S1: "cada entrada sale una sola vez, y el recorrido termina cuando los dos extremos se encuentran" and "y después ninguna más por ningún extremo". Existing exhaustion and OOM tests do not combine normal exhaustion with first use of the opposite end under allocation failure.

**Suggestion:** finish both ends on normal exhaustion and add fault-injection coverage for both directions.

### R2 — minor — The short-scan benchmark does not always measure 100 entries per scan

**Location:** `crates/krummi/examples/scan_timing.rs:64`, with consumption at lines 67–69.

**Status:** verified still open; original finding `docs/reviews/trees-scan/2026-10-26-code.md#R2`. No fix commit is present in the requested range.

**Problem and failure scenario:** starts are sampled from all keys, including positions with fewer than 100 entries remaining. `take(SCAN_LEN)` imposes a maximum, not an exact length. With the default million keys and committed seeds, two starts have sorted positions 999,981 and 999,989, returning 19 and 11 entries. The workload reads 999,830 entries instead of 1,000,000. This is a limited measurement discrepancy, not a demonstrated engine performance regression.

**Evidence: fresh deterministic reproduction and source argument.** The coordinator compiled a probe from stdin into `target/review_workload_round2.exe`, importing the actual `timing::keys` and `timing::shuffled` helpers. It sorted the million keys, found each of the first 10,000 selected starts and summed `min(100, entries - rank)`:

```text
rank=999981, returned=19
rank=999989, returned=11
total=999830
```

The closing report at `odd/tasks/trees-scan-report.md:104` records the same total. No logged user correction changes the fixed-length workload.

**Requirement:** R11 / AC-R15 / S15: "10.000 recorridos hacia delante de 100 entradas desde claves límite al azar".

**Suggestion:** select starts with 100 entries available, assert every scan's length, and rerun that measurement on Windows and Linux.
