### R1 — verified resolved — Exhausting one scan end leaves the other able to fail and invalidate a write

- Original severity: **major**; [original finding](2026-10-26-code-02.md#R1).
- Fix: `f2bb44dc62ff9cc01c7a1e5181f58d63e39e582c`; test strengthened in `3dea0434c8e2791936d803e85bbdf8ce6bd6c129`.
- Source evidence: `crates/krummi-tree/src/range.rs:362` now calls `stop()` on normal exhaustion. `stop` at line 193 marks both ends finished, so the early return in `guard` at line 352 prevents further page reads or reservations. Every normal exhaustion exit in `step_front` and `step_back` represents an empty remaining interval: an exhausted path, a monotonic bound, or crossing the other end's last returned key. Stopping both ends does not discard pending valid entries. The error branch still stops both ends and preserves T11 failure handling.
- Requirement: S1 / AC-R1 / R1, including "y después ninguna más por ningún extremo".
- Fresh experimental evidence: the committed regression test `crates/krummi/tests/tree_memory.rs:465` passes for both directions and asserts zero reservations after exhaustion. Its fault helper resets counters before injection. A separate public-API probe compiled from stdin into `target/review_scan_followup.exe` passed all eight combinations of disk/temporary store, front/back first, and exhausted/nonexhausted control. After consuming the entry and `None`, an armed next-allocation failure remains untriggered: the opposite end returns `None`, its allocation count is zero, repeated calls at both ends stay empty, and the write commits its original value. Disk cases also verify that value after close and reopen. In the control, without first consuming `None`, the opposite end makes exactly one reservation and returns `OutOfMemory`; commit is rejected and the pending tree is absent, including after disk reopen. Thus the probe confirms both the fix and the fault injection's effectiveness.
