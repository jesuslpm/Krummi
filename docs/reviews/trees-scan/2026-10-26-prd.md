## Findings

No **blocker** or **major** findings were identified. The four findings below are **minor**. In particular, R1 is an acceptance-evidence omission, not a detected format incompatibility or an ambiguous product decision.

<a id="R1"></a>
### R1 — AC-R14 does not demonstrate the full compatibility promised by R10

- **Severity:** minor.
- **Section / IDs:** Acceptance criteria / AC-R14; Product decisions / R10.
- **Location:** `docs/prd/krummi/trees-scan.prd.md:251`, with the governing promise at line 50.
- **Problem:** R10 promises that a 5.1 engine can both read and modify a store after 5.2 has deleted ranges. AC-R14 describes opening a 5.1 fixture with 5.2, deleting ranges, reopening and reading the remaining entries. It does not explicitly exercise the 5.1 engine against the resulting store or perform modifications with it.
- **Evidence:** R10 states: “un motor de 5.1 las lee y las modifica sin riesgo”. AC-R14 ends with “porque las páginas cumplen las comprobaciones de consistencia de 5.1”, but the described observations do not establish the complete promise. Current consistency checks reside in `crates/krummi-tree/src/lib.rs:125` and `crates/krummi-tree/src/node.rs:78`; passing a future version of those checks alone would not prove that the old reader and writer remain compatible.
- **Impact:** the described acceptance exercise could pass without demonstrating the backward read/write compatibility that justifies retaining format version 6. The requirement itself is clear.
- **Suggestion:** extend AC-R14 to reopen, read and modify with the 5.1 engine a store whose ranges were deleted by 5.2.

<a id="R3"></a>
### R3 — Starting state omits the internal traversal used by Listar

- **Severity:** minor.
- **Section / IDs:** Starting state / Internal traversal.
- **Location:** `docs/prd/krummi/trees-scan.prd.md:60`.
- **Problem:** the claim about the library's only existing whole-tree traversal uses is too broad.
- **Evidence:** “La biblioteca solo recorre internamente un árbol entero, de principio a fin, para liberar sus páginas y en las pruebas.” The catalog is also a B+ tree (`crates/krummi-tree/src/catalog.rs:1`). `catalog::list` traverses its leaves at `crates/krummi-tree/src/catalog.rs:91`, calling the whole-subtree traversal implemented at `crates/krummi-tree/src/lib.rs:206`. The public list operation calls it from `crates/krummi/src/lib.rs:246`.
- **Impact:** the starting-state and reuse description misses an existing production traversal; the separate claim that normal application trees have no public range/prefix traversal remains correct.
- **Suggestion:** include catalog listing among the current uses, or explicitly restrict the claim to normal application trees.

<a id="R4"></a>
### R4 — R3 overstates the difference from Rust's range behavior

- **Severity:** minor.
- **Section / IDs:** Product decisions / R3.
- **Location:** `docs/prd/krummi/trees-scan.prd.md:43`.
- **Problem:** the comparison says Rust panics in the cases described, which include equal bounds with only one excluded endpoint. Rust already permits that empty range.
- **Evidence:** R3 says “diferencia con `BTreeMap::range`, que en estos casos detiene el programa” and includes “los dos tienen la misma clave y alguno está excluido”. Rust documents a panic for reversed bounds, or equal bounds when both endpoints are excluded. [Official `BTreeMap::range` documentation](https://doc.rust-lang.org/std/collections/struct.BTreeMap.html#method.range).
- **Impact:** the reference comparison is inaccurate; Krummi's intended empty-range behavior is nevertheless specified unambiguously.
- **Suggestion:** narrow the comparison to Rust's actual panic conditions while preserving Krummi's chosen behavior.
