## Findings

<a id="R1"></a>
### R1 — major — Exhausting one scan end leaves the other able to fail and invalidate a write

**Location:** `crates/krummi-tree/src/range.rs:362` (`guard`, the `Ok(None)` arm).

**Problem:** normal exhaustion sets only the selected end's `finished` flag. The other end remains active. If it has never been used, consuming it starts a new descent and reserves a path even though the scan has already returned `None`. That reservation can produce a new error instead of termination. In a write, it also records a T11 failure and prevents an otherwise valid commit.

**Concrete failure scenario:** create a tree with one pending entry, consume the entry and then `None` from the front, and let the next allocation fail. `next_back()` returns `Some(Err(OutOfMemory))`; committing the write then fails with `OutOfMemory`, and its pending tree is absent in a new read. Starting from the back and then calling `next()` has the same result. No committed data is lost; the defect unnecessarily rejects pending work after a completed scan.

**Evidence type:** experimental reproduction, supported by source inspection. The delegated reviewer compiled a standalone probe from stdin against the checkout's built libraries into `target/review_scan_end.exe`, using the existing `krummi_pager::testing` allocation hook. Both directions reproduced:

```text
first direction=front, exhausted=None, other=OutOfMemory, commit=OutOfMemory, pending tree absent
first direction=back, exhausted=None, other=OutOfMemory, commit=OutOfMemory, pending tree absent
```

The essential public-API sequence was:

```rust
let store = Store::open_temporary(&StoreOptions::default()).unwrap();
let mut write = store.write().unwrap();
let tree = write.open_tree_with("pending", TreeKind::Normal, OpenMode::CreateNew).unwrap();
write.set(&tree, b"a", b"pending").unwrap();
let mut scan = write.range(&tree, ..).unwrap();
assert!(scan.next().unwrap().is_ok());
assert!(scan.next().is_none());
testing::inject(Op::Alloc, 0, Action::Fail(std::io::ErrorKind::OutOfMemory));
let error = scan.next_back().unwrap().unwrap_err();
testing::reset();
assert_eq!(error.kind(), ErrorKind::OutOfMemory);
drop(scan);
assert_eq!(write.commit().unwrap_err().kind(), ErrorKind::OutOfMemory);
assert!(!store.read().unwrap().tree_exists("pending").unwrap());
```

The causal chain is `guard` leaving the opposite end active, `step_back` / `step_front` calling the unstarted end's seek, and the seek reserving a new path (`range.rs:204`, `range.rs:221`). `krummi-tree/src/lib.rs:110` propagates reservation errors through `PageSource::fail`; `krummi-tx/src/transaction.rs:234` records the write failure, and `transaction.rs:264` rejects its commit. These paths and the new exhaustion branch were checked by the coordinator. The scan API does not exist at the base, so this is introduced by the range.

**Requirement:** R1 / AC-R1 / S1: "cada entrada sale una sola vez, y el recorrido termina cuando los dos extremos se encuentran" and "y después ninguna más por ningún extremo". The existing normal and OOM tests do not combine complete exhaustion of one end with failure on first use of the opposite end.

**Suggestion:** stop both ends on normal exhaustion and cover both directions with a post-exhaustion fault-injection regression test.

**Status:** open.

<a id="R2"></a>
### R2 — minor — The short-scan benchmark does not always measure 100 entries per scan

**Location:** `crates/krummi/examples/scan_timing.rs:64` (random starts and consumption at lines 67–69).

**Problem:** starts are sampled from all keys, including keys with fewer than 100 remaining entries. `take(SCAN_LEN)` caps a scan at 100 entries but does not ensure it returns 100. The experiment therefore differs slightly from the specified fixed-length workload.

**Concrete failure scenario:** with the default 1,000,000 entries and the committed seeds, two of the 10,000 starts have sorted ranks 999,981 and 999,989, leaving only 19 and 11 entries. The workload reads 999,830 entries instead of 1,000,000. This is a limited measurement discrepancy, not evidence of an engine correctness or performance regression. The closing report honestly records the smaller total, but that does not change the requirement.

**Evidence type:** deterministic reproduction and source argument. The delegated reviewer compiled a probe from stdin into `target/review_scan_workload.exe`, using the actual `timing::keys` and `timing::shuffled` helpers, sorting the keys and summing `min(100, entries - rank)` for the selected starts. It found the two short scans and the total above. The coordinator checked the sampling/consumption code and the matching total in `odd/tasks/trees-scan-report.md:104` and execution log L10. No recorded correction authorizes shorter scans.

**Requirement:** R11 / AC-R15 / S15: "10.000 recorridos hacia delante de 100 entradas desde claves límite al azar".

**Suggestion:** sample starts with at least 100 remaining entries for the required workload, assert each returned count, and rerun that measurement on Windows and Linux.

**Status:** open.
