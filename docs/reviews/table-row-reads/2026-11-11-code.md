### R1 — major — Reading compound keys repeatedly decodes their prefixes

**Location:** `crates/krummi/src/table/key.rs:118`, specifically the prefix loop at lines 120–122; called by `crates/krummi/src/table/rows.rs:501–502`. Full-row iteration at `rows.rs:701–702` and update processing at `rows.rs:929–937` expose the regression.

**Problem and failure scenario:** create a valid table whose primary key contains multiple fixed-width columns, insert a row, and either read every column or issue an identical update. Every `key_value(types, key, k)` starts again at the beginning of the key and calls `skip_element` for all preceding components. Reading all n key columns therefore decodes n(n+1)/2 components, in addition to the initial key validation. An identical update enumerates the old values twice, first to merge the supplied values and then to compare the result. The base decoded the key once in `Reader::decode` and subsequently indexed materialized values. The change introduces quadratic work in the number of key columns for these public operations.

This affects admitted schemas, rather than malformed input: E4 allows up to 1,024 live columns and composite primary keys; 256 or 1,024 `Bool` key columns encode into 256 or 1,024 bytes, below E18's 2,048-byte key limit. These exact schemas were successfully created and exercised in the reproduction.

**Evidence type: source argument and experimental reproduction.** A temporary Rust harness used `Store::open_temporary`, `Schema`, `insert_row`, `get_row`, `TableRow::value` and `update_row`. Each schema had one row, all primary-key columns were non-null `Bool` with value `true`, and updates supplied the identical complete row. Each read accessed every column and passed its value through `black_box`. Schema construction and insertion were outside the timed loops. Five batches were measured per operation, reporting median nanoseconds per operation; each batch used 10,000 iterations below 256 columns and 100 iterations at 256 and 1,024 columns.

The base library was built with `rustc --edition=2024 -O --crate-type rlib` from exact base source bytes exported with `git show` into `target/review-table-row-reads/base-src`. The head library was built with `cargo build --locked --offline --release -p krummi`. Both used the same release dependencies for pager, tree and transactions, whose source does not change in this range. Separate optimized executables ran the same public harness against base and head. The following final measurements were taken sequentially after the workspace test suite had finished:

Harness and executables are verification temporaries under `target/review-table-row-reads/`. To repeat while those artifacts remain: run `public_base.exe` followed by `public_head.exe` in that directory. The harness is `public_scaling.rs`; only the baseline build selects `--cfg base` and links the exported baseline library. An additional optimized comparison of `decode_key` plus value clones against `is_key` plus all `key_value` calls independently confirmed the prefix-decoding cost. These measurements establish this regression; they are not the complete comparative benchmark or evidence about W26/W28 thresholds.

**Requirement/principle:** the run is a performance optimization (S1), while `CLAUDE.md` requires efficient algorithms by design. E4 and E18 establish that the affected schemas are supported. This does not establish a failure of the fixed W26/W28 workloads; it demonstrates a substantive performance regression in supported public operations introduced by the implementation.

**Suggestion:** reuse component boundaries or decoded key values from validation so that accessing successive primary-key columns does not repeatedly decode their prefixes.

**Status:** open. No fix was supplied or verified in this review.
