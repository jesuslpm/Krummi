## Findings

### R1 — Major — Update patch adds quadratic work for wide compound primary keys

**Location:** `crates/krummi/src/table/rows.rs:509`; repeated traversal at lines 512 and 522.

**Problem and reachable failure scenario:** `Reader::patch` filters each supplied column with `self.key_columns.contains(i)`. Every primary-key column must be supplied, so even the key columns that this filter discards search the same list. With `k` key columns, filtering the mandatory keys alone performs `k(k+1)/2` index comparisons per traversal. A changed fixed-width value runs the traversal twice. This introduces quadratic work into updates and upserts; the base's merge uses linear passes and its existing `key_starts` avoids repeatedly decoding key prefixes.

A supported table can have a nullable string first, 1,022 `bool NOT NULL` columns in its primary key, and a nullable `i64` last. This is exactly 1,024 columns (`schema.rs:26`, E4); each bool key element takes one byte (`key.rs`, `encode_element`), so its 1,022-byte key is below E18's 2,048-byte limit. Updating that integer requires all 1,022 key values and performs 522,753 comparisons per traversal just to discard those keys. Repeating the traversal to write the integer more than doubles that count. The result remains correct, but supported wide-key writes become substantially slower, contrary to the performance purpose of this change.

**Evidence type:** source-level causal argument plus a public-API optimized-build reproduction. The temporary probe in the appendix uses a single temporary store and transaction for each width. It compares the patch with the retained full-merge path by supplying an additional unchanged `v = Null` at schema position zero. That variable column makes `patch` return `None` before walking the keys; the remaining algorithm is the base's decode/merge/encode path. Both inputs produce the same row. The control pays the extra validation of that column and still outperforms the patch for wide keys.

Final diagnostic run, after the workspace test process completed: 100 warm-up pairs, 4,000 updates per timing, median of three rounds with alternating path order. Each timed update changes `n`; the probe asserts the final integer and every bool key value.

| Key columns | Patch, ns/update | Full merge control, ns/update | Patch/control |
|---:|---:|---:|---:|
| 8 | 724 | 957 | 0.76 |
| 64 | 4,245 | 5,094 | 0.83 |
| 256 | 27,472 | 26,558 | 1.03 |
| 512 | 82,622 | 52,128 | 1.58 |
| 1,022 | 260,562 | 112,105 | 2.32 |

An earlier run also showed the effect for identical, key-only updates: at 1,022 key columns, 173,514 versus 104,849 ns/update (1.65×). An initial changed-value run measured 2.39× at that width. These are diagnostic comparisons between paths in HEAD, **not measurements of separately built base and head binaries**, and do not establish a W28 threshold failure. CPU affinity and the benchmark power plan were not controlled; the deterministic quadratic traversal establishes the mechanism independently of absolute timings.

**Requirement:** S6's update optimization and `CLAUDE.md`'s performance-by-design principle. E4/E18 establish that the scenario is supported; they do not themselves promise a complexity bound. This is a demonstrated performance regression for wide keys, without demonstrated data loss.

**Suggestion:** determine primary-key membership in constant time per supplied column and cover wide compound-key update/upsert behavior.

**Status:** open.

```rust
use krummi::{Column, Schema, Store, StoreOptions, TableMode};
use krummi::table::value::{ColumnType, Value};
use std::hint::black_box;
use std::time::Instant;

fn main() {
    for k in [8, 64, 256, 512, 1022] {
        let store = Store::open_temporary(&StoreOptions::default()).unwrap();
        let names: Vec<String> = (0..k).map(|i| format!("k{i}")).collect();
        let key_names: Vec<&str> = names.iter().map(String::as_str).collect();
        let mut columns = vec![Column::new("v", ColumnType::String)];
        columns.extend(names.iter().map(|n| Column::new(n, ColumnType::Bool).not_null()));
        columns.push(Column::new("n", ColumnType::I64));
        let schema = Schema::new(columns, &key_names);
        let mut tx = store.write().unwrap();
        let table = tx.open_table_with("t", TableMode::CreateNew(&schema)).unwrap();
        let mut given: Vec<(&str, Value<'_>)> = names.iter()
            .map(|n| (n.as_str(), Value::Bool(false))).collect();
        given.push(("n", Value::I64(0)));
        tx.insert_row(&table, &given).unwrap();
        let mut fallback = vec![("v", Value::Null)];
        fallback.extend(given.iter().cloned());
        for _ in 0..100 {
            assert!(tx.update_row(&table, &given).unwrap());
            assert!(tx.update_row(&table, &fallback).unwrap());
        }
        let iters = 4000;
        let mut patch = Vec::new();
        let mut merge = Vec::new();
        for round in 0..3 {
            for which in if round % 2 == 0 { [false, true] } else { [true, false] } {
                let input = if which { &mut fallback } else { &mut given };
                let start = Instant::now();
                for i in 0..iters {
                    input.last_mut().unwrap().1 = Value::I64(i as i64);
                    black_box(tx.update_row(&table, black_box(&*input)).unwrap());
                }
                let ns = start.elapsed().as_nanos() as f64 / iters as f64;
                if which { merge.push(ns); } else { patch.push(ns); }
            }
        }
        patch.sort_by(f64::total_cmp);
        merge.sort_by(f64::total_cmp);
        println!("keys={k}: patch={:.0} ns, full_merge={:.0} ns, patch/merge={:.2}",
            patch[1], merge[1], patch[1] / merge[1]);
        let keys: Vec<Value<'_>> = (0..k).map(|_| Value::Bool(false)).collect();
        let stored = tx.get_row(&table, &keys).unwrap().unwrap();
        assert_eq!(stored.i64(k + 1), Some((iters - 1) as i64));
        for i in 1..=k { assert_eq!(stored.bool(i), Some(false)); }
    }
}
```
