### R2 — original severity: major — Verified resolved

Original: [2026-11-11-code-03.md#R2](2026-11-11-code-03.md#R2), raw text reads panicking for malformed text in older schema versions. Claimed fix: `2bc4fe4fab23a54426d6ff852f6a8bd02d57caf5`, verified at the head above.

**Source evidence:** `TableRow::typed` now maps the current column through `old.places[position]` and reads its raw bytes through the historical layout (`rows.rs:950–967`). It no longer decodes a `Value::String` before `text_bytes` can return those bytes (`rows.rs:1010`). `text` still checks UTF-8 and panics on malformed text. A column absent from that version still takes the existing default/null path. `version_layout` constructs the mapping by column identity (`rows.rs:655`), so a dropped preceding column cannot redirect the accessor to a different stored value.

**Independent reproduction:** reused the original `review_text_bytes_of_an_older_malformed_row` source from the retained harness against a fresh copy of head source. It passes in debug and release, returning `b"row\xFF"` after the schema rename. The committed regression test also passes in both builds.

The committed new test covers a read transaction, whereas the resolution describes both transaction types. Independent temporary test `review_older_malformed_text_in_both_transactions_and_mapped_columns` closes that verification gap: in both read and write transactions, it reads by key and scans forward, backward and with `next_row`, verifies raw bytes, catches the expected `text`/`value` panics, and verifies that raw bytes remain readable afterwards. A second scenario drops the preceding column, adds a text default and reuses the dropped name for a new nullable text column; it verifies the shifted historical mapping, borrowed default and null. The write transaction then inserts another row and commits successfully. Both scenarios pass in debug and release.

This verifies L2, verbatim: «Un texto que no es UTF-8 leído como texto termina siempre con un pánico; leído como sus bytes, se devuelve tal cual.» It also checks AC-L1 and the relevant N3 schema-evolution behavior. The resolution's functional evidence is confirmed, with broader independent coverage.

### R3 — original severity: major — Verified resolved

Original: [2026-11-11-code-03.md#R3](2026-11-11-code-03.md#R3), row lookups scanning retained readers. Claimed fix: `bb496a144ec526ac1190791be29bf23451c56ca5`, verified at the head above. R4 concerns its added test, not persistence of the original performance defect.

**Source evidence:** `Readers::keep` now follows hash digits through an append-only trie (`rows.rs:736–765`) instead of traversing unrelated readers. Multiplication modulo 2^64 by the odd constant is bijective. Each descent consumes another four bits; distinct keys must diverge within the 16 digits. A lookup therefore visits at most 17 nodes including the root, independently of table count. Read-side opening, lookup and scan creation use this same structure (`catalog.rs:260`, `rows.rs:1134`, `ranges.rs:242`); write-side lookup and scans use it with retained reader addresses (`rows.rs:1209`, `ranges.rs:273`).

**Independent optimized reproduction:** reused the retained original `review_reader_lookup_scaling` source against head, opening valid one-row tables outside timing and measuring public `get_row` with `black_box`. Each entry is the median of five batches of 50,000 reads. Ran the optimized harness after other checks and compilation completed, with one test thread.

| Tables in snapshot | First table, ns/read | Last table, ns/read |
|---|---:|---:|
| 1 | 161 | 188 |
| 100 | 168 | 182 |
| 1,000 | 199 | 208 |

For one table both measurements address the same handle; the difference illustrates timing variation. At 1,000 tables, the prior report measured 204/4,066 ns; this run measures 199/208 ns. The linear penalty is removed, corroborating the resolution rather than establishing a particular comparative benchmark threshold.

The committed 300-table test passes. Independent temporary test `review_concurrent_first_reader_publications` additionally runs eight workers opening and reading 128 tables in different orders within one shared read transaction, repeated with eight fresh snapshots. Opening happens inside the workers so first publication can race. Every table has its own column name and payload; workers check keyed and lending reads and retain rows until all their table openings finish, then recheck those rows. It passes in debug and release.

## Dependent invariants and regression assessment

- **Stable readers and concurrency:** each trie node is a `Box` published once through `OnceLock`; published nodes are never replaced or moved. A losing insertion retains its constructed `Arc`, rereads the same slot and consumes a digit only when descending. A matching key returns the published reader. The source argument and concurrent reproduction found no reader mix-up or invalidation.
- **Write schema changes:** retained `Arc<Reader>` values keep their addresses unique while used as write-side keys (`rows.rs:769–772`). A schema change creates a new reader; mutable transaction operations continue to end previous row borrows. Public schema/version and transaction tests pass.
- **Historical values and lifetimes:** historical layouts retain their own null bits, fixed slots and variable offsets. `Row::column_bytes` returns a reference tied to the transaction's stored bytes, independently of the layout's lifetime. Defaults and owned rows retain their established paths; the typed-accessor, added-default and value-lifetime integration tests pass.
- **Damage and replacement:** structural row validation still precedes returned rows. The update/upsert replacement validator remains separate from typed accessors and still runs after a prior read; malformed-row and damage tests pass. Neither fix changes row/key encoding, page writes or the store format.

No additional functional, concurrency or storage-safety defect was demonstrated in the requested scope. These checks are not exhaustive corruption or concurrency model checking.
