<a id="R2"></a>
### R2 — major — Raw text reads panic for malformed text in older schema versions

**Location:** `crates/krummi/src/table/rows.rs:939` and `crates/krummi/src/table/rows.rs:984`.

**Problem and failure scenario:** store a row with a string, alter that string to contain `FF` while keeping its page integrity valid, then rename another column. Renaming advances the schema without rewriting the row. `get_row` correctly returns the older row, but `row.text_bytes(2)` panics instead of returning its raw bytes. This path is shared by reads and scans in both transaction types.

**Evidence — reproduced in debug and release, supported by source tracing:** the temporary test `review_text_bytes_of_an_older_malformed_row` reuses `bad_text_store()`, whose committed row has `s = b"row\xFF"`. It renames `n` to `number`, commits, reads row `BAD`, verifies its key, and asserts that `text_bytes(2)` returns `b"row\xFF"`. Both builds fail at `row.rs:518` with `a malformed row: a column that does not decode`.

`TableRow::typed` reads raw storage only for `old: None` (`rows.rs:939–944`). An older row falls through to `self.value(position)` at line 946. `Reader::stored_value` selects the older layout and calls `Row::read` (`rows.rs:605–613`), which decodes a `Value::String` and validates UTF-8 (`row.rs:672–674`) before the bytes accessor can see it. The existing AC-L1 test exercises only the current schema version, so its success misses this case.

**Violated requirement:** L2, verbatim: «Un texto que no es UTF-8 leído como texto termina siempre con un pánico; leído como sus bytes, se devuelve tal cual.» Also AC-L1, and N3's supported reading of older rows. This is a substantive requirement gap; no transaction corruption is alleged.

**Suggestion:** obtain raw text bytes through the older layout and mapped column position, and extend AC-L1 coverage to older rows.

<a id="R3"></a>
### R3 — major — Every row lookup scans the transaction's retained table readers

**Location:** `crates/krummi/src/table/rows.rs:734`, called at `crates/krummi/src/table/rows.rs:1106`.

**Problem and failure scenario:** an application opens many small tables in one read snapshot and repeatedly reads a row from a later-opened table. Every `get_row` calls `Readers::keep`, which starts at `head` and follows the entire prefix of readers (`rows.rs:734–738`), although the table handle already contains its reader. With T tables, reading the last table incurs O(T) additional work per lookup; visiting all tables incurs O(T²) lookup work. The base used `table.reader` directly. Write-side reads and starting a range also perform this search (`rows.rs:1181`, `ranges.rs:242`, `ranges.rs:273`).

**Evidence — isolated optimized reproduction and source argument:** `review_reader_lookup_scaling` creates 1, 100 and 1,000 valid single-column tables, each with one row, commits, and opens all handles in order. It measures repeated public `get_row` calls to the first and last handles in the same snapshot, consuming the returned row through `black_box`. Table creation and opening are outside timing; each result is the median of five batches of 50,000 reads. This run was executed after the workspace tests and compilation finished.

| Tables in snapshot | First table, ns/read | Last table, ns/read |
|---|---:|---:|
| 1 | 152 | 152 |
| 100 | 163 | 292 |
| 1,000 | 204 | 4,066 |

The last table is about 20 times slower than the first with 1,000 tables, corroborating the list traversal. Both use identical valid schemas and one-row trees; this does not require malformed data or schema changes. This is a supported scenario: inherited B11 imposes no artificial small limit on the number of trees/tables. The benchmark's one-table workloads cannot detect this regression. The measurements establish the lookup cost, not failure of a particular K7 threshold.

**Violated objective/principle:** S1's read-performance objective and `CLAUDE.md`'s requirement to choose efficient algorithms from the outset. Retaining readers for stable borrowing does not require a linear search on every subsequent read.

**Suggestion:** retain direct or indexed access to the transaction-held reader so that each operation avoids scanning unrelated tables.
