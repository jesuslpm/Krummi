## Findings

All seven findings remain open. Locations without another path refer to the reviewed Spanish PRD.

<a id="R1"></a>
### R1 — blocker — AC-CU13 requires committing after a fatal store-read error

**Section / IDs:** Acceptance criteria / AC-CU13; CU18.

**Evidence:** Lines 328–329 require a write to commit after a query fails for “cada causa de CU18 salvo el daño”. CU18, line 41, includes “Un daño o un fallo de entrada y salida al leer el almacén sigue T11 y T12”. T11 in `docs/prd/krummi/transactions/transactions.prd.md:40` explicitly makes an I/O failure while reading inside a write transaction prevent its commit. The existing transaction contract is also documented in `crates/krummi-tx/src/transaction.rs:597`.

Consequently, the store-read I/O case must both commit under AC-CU13 and reject its commit under CU18/T11. This acceptance criterion cannot pass as written. This is distinct from a query's spill I/O failure, which CU17 deliberately isolates.

**Suggestion:** Separate query-local failures from store-read failures and state the corresponding commit outcome consistently with CU18/T11.

<a id="R2"></a>
### R2 — major — Normalization does not define a total order for compound expressions

**Section / IDs:** Product decisions / CU7; AC-CU3.

**Evidence:** CU7, line 30, orders compound expressions of the same operation “por su primer argumento ya ordenado”. It gives no further comparison when their first arguments match. AC-CU3, lines 288–292, requires identical normalized bytes for predicates equivalent under these reordering rules.

For example, the two children of the following `OR` tie under the specified comparison:

```text
OR(AND(eq(a,p0), eq(b,p1)), AND(eq(a,p0), eq(c,p2)))
```

**Allowed readings:** Preserve their input order on a tie, or compare subsequent arguments recursively. Reversing the input children can therefore produce different normalized bytes. The referenced design's canonical-order requirement does not supply the missing tie breaker.

**Suggestion:** Complete the comparison of compound expressions, including equal prefixes and different argument counts.

<a id="R3"></a>
### R3 — major — The subnormal rule conflicts with nearest-even rounding

**Section / IDs:** Value forms / floating-point row; CU6; AC-CU2.

**Evidence:** Line 56 accepts numbers “redondeado al tipo con empates al par”, but also says “lo que queda por debajo del menor subnormal es cero”. A JSON `1e-45` bound as `f32` is below the smallest positive subnormal, approximately `1.401298464324817e-45`, yet nearest-even rounding produces that subnormal, not zero. The threshold for rounding to zero is half the smallest subnormal, with the stated tie rule. The referenced design repeats the wording and does not settle it.

**Allowed readings:** Flush an input below the minimum subnormal to zero, or apply the required nearest-even rounding. These yield different bound values and potentially different matching rows.

**Suggestion:** Specify the rounding-to-zero threshold consistently with nearest-even rounding.

<a id="R4"></a>
### R4 — major — Floating-point aggregate admissibility lacks a usable accuracy contract

**Section / IDs:** Product decisions / CU12, CU23; AC-CU7; inherited AC-CS1.

**Evidence:** CU12, line 35, allows IEEE 754 sums and plan-dependent changes “en sus últimos bits”; CU23, line 46, specifies relative tolerance `10⁻⁹`. Ordinary reductions of the same finite inputs can differ much more:

```text
(1e20 + -1e20) + 1 = 1
(1e20 + 1) + -1e20 = 0
```

An intermediate overflow can also make one order return infinity while another returns a finite value. Relative tolerance alone does not define comparison against zero, NaN or infinities. The inherited differential test compares plans against a reference plan, so it needs a defined admissibility rule for these cases.

**Allowed readings:** Accept ordinary order-dependent IEEE reductions even when they exceed the tolerance, or require sufficient accuracy to satisfy a reference-based bound. These readings change both accepted implementation behavior and test results.

**Suggestion:** Define aggregate admissibility, its reference and exceptional cases without prescribing an implementation algorithm.

<a id="R5"></a>
### R5 — major — Canonical output leaves the order of bind.columns unspecified

**Section / IDs:** CU5, CU20; Output; AC-CU1, AC-CU14.

**Evidence:** CU5, line 28, defines `bind.columns` as an object mapping names to identities. CU20 makes validation emit it. Output, lines 214–218, fixes surrounding member order but never orders the members of this map. The parent explicitly leaves exact output to this child (`docs/prd/krummi/queries/queries.prd.md:162`). This point is absent from Left to the implementation.

**Allowed readings:** Emit bindings in schema order, name-byte order or first-use order. For a schema ordered `z, a`, the first two readings emit different bytes for the same bindings. Each writer could be deterministic individually, but the PRD does not select the public canonical form needed for the reference documents.

**Suggestion:** Fix the ordering of `bind.columns` and include it in the reference-document checks.

<a id="R6"></a>
### R6 — major — store/1 column descriptors leave existing type attributes unresolved

**Section / IDs:** Product decisions / CU20, CU5; AC-CU14.

**Evidence:** CU20, line 43, reuses CU5's parameter descriptor for column types. Its UUID example is `{"type":"uuid"}`, suitable for a parameter that matches either ordering, but it does not describe whether a column uses RFC or SQL Server order. CU8 and N5 assign those columns different comparisons. The existing catalog preserves the distinction through `ColumnType::Uuid(UuidOrder)` (`crates/krummi/src/table/value.rs:69`, `:78`) and exposes the column type in `SchemaColumn` (`crates/krummi/src/table/schema.rs:123`).

CU20 also lists `"metric": ...` for vector column types without specifying the representation when a column does not declare cosine. Such columns already exist: `VectorType` contains a `cosine: bool` (`crates/krummi/src/table/value.rs:98`).

**Allowed readings:** Describe UUID columns generically, losing their ordering attribute, or extend the column descriptor to preserve it. For vectors without cosine, omit `metric`, emit `null` or emit another value. The latter choices produce different public documents and JSON Schema; the former omission prevents tools from determining UUID comparison semantics from the description.

**Suggestion:** Complete column-specific descriptors for `store/1`, distinguishing them from parameter descriptors where necessary.

<a id="R7"></a>
### R7 — minor — The starting-state description implies a nonexistent temporary-sort cap

**Section / IDs:** Starting state / spill sorting, line 154.

**Evidence:** The row links the existing 64 MiB sorting memory to “en modo temporal solo ordena en memoria y falla con memoria agotada al pasar de ella”. This suggests that crossing 64 MiB also fails in temporary mode. In `crates/krummi/src/table/sort.rs:80`, the budget triggers spilling only when files exist; lines 83–85 otherwise continue reserving and adding entries. The module documentation at line 8 and IX2 in `docs/prd/krummi/tables/tables-indexes.prd.md:47` say temporary index creation fails if the system cannot provide memory.

**Suggestion:** Distinguish the existing disk-spill threshold and system-allocation failure from the new temporary query budget in CU17.
