### R4 — major — Floating-point aggregate admissibility lacks a usable accuracy contract

**Status:** still open, partially resolved. This preserves the identity of [the original R4](2026-11-28-prd.md#R4), also open in [the preceding verification](2026-11-28-prd-02.md#R4). The remaining issue is the rounding tie breaker for `avg`.

**Section / IDs:** Product decisions / CU12; Acceptance criteria / AC-CU7; inherited AC-CS1.

**Problem and evidence:** `docs/prd/krummi/queries/queries-single-table.prd.md:35` specifies floating-point `sum` as rounded once to the nearest `f64`, explicitly “con empates al par”. For `avg`, the same line instead says “redondeada una sola vez al `f64` más cercano, con las mismas reglas para NaN y los infinitos”. The latter reference carries the exceptional-value rules, but does not settle a tie between two finite results. CU6's nearest-even rule at line 56 governs reading parameter values, not rounding an aggregate result. Neither ancestor supplies a general tie breaker for binary floating-point aggregate results; E8's tie rule concerns decimal and temporal values.

**Reproduction:** take two stored `f64` values, `1.0` and `1.0000000000000002`, the adjacent representable value above `1.0`. Their exact average is:

```text
9007199254740993 / 9007199254740992
```

Its distance to either input is exactly `1 / 9007199254740992`. A file-free Python `Fraction` probe verified those distances and the adjacent binary64 encodings:

```text
lower: 0x1.0000000000000p+0
upper: 0x1.0000000000001p+0
ties to even:       1.0
ties away from zero: 1.0000000000000002
```

**Allowed readings and impact:** use ties to even, as explicitly required for `sum`, or another nearest-value tie rule for `avg`. Both can compute the exact rational average and return a plan-independent result while producing different observable values. AC-CU7 (`queries-single-table.prd.md:302`) and inherited AC-CS1 (`docs/prd/krummi/queries/queries.prd.md:215`) therefore still lack a unique expected result for this case. This is a finite-value boundary of R4's corrected contract, not a request to reconsider the user's exact, plan-independent arithmetic decision.

**Suggestion:** Specify the tie breaker for `avg` in CU12 and cover a halfway result in AC-CU7.

## Verified portions of the R4 correction

The latest resolution records the user's decision verbatim: “Exacta y sin depender del plan (Recomendado)”. The current PRD now defines exact floating-point summation followed by one rounding, and exact division before rounding an average. CU23 no longer imposes a relative tolerance. The plan-dependent aggregate exception and its parent annotation are removed; AC-CU7 explicitly covers numerical cancellation, intermediate overflow, NaN and infinities with equal results under every plan. These portions resolve the original counterexamples and the former zero/non-finite tolerance problem.

The coordinator reproduced both original order-dependent failures and calculated an exact rational oracle from the binary64 input values, rounding only the final result. Every permutation of each finite input set produced the same oracle result:

| Inputs | Ordinary reduction counterexample | Exact `sum` | Exact `avg`, rounded once |
|---|---|---|---|
| `[1e20, -1e20, 1]` | `1` versus `0` | `1` | `0.3333333333333333` |
| `[1e308, 1e308, -1e308]` | infinity versus `1e308` | `1e308` | `3.333333333333333e307` |
| `[f64::MAX, f64::MAX]` | Floating sum overflows | positive infinity | `f64::MAX` |

The probes also exercised a NaN input, opposite infinities, each single infinity sign with a finite value, nearest-even sum ties and a subnormal average tie. Exceptional-value handling in the oracle was explicitly modeled from CU12; it is not execution evidence for a query engine. In particular, averaging two maximum finite values must divide the exact sum before rounding, rather than divide an already infinite rounded sum.
