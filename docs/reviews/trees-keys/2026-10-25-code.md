## Findings

<a id="R1"></a>
### R1 — major: listing trees aborts on allocation failure instead of returning OutOfMemory

- Location: `crates/krummi-tree/src/catalog.rs:96` (also the vector growth at line 98).
- Requirements: trees B11, inherited memory-error contract P13 and the transactions PRD's validation row
  "Falta memoria al abrir una transacción o durante ella" / "La operación falla; el almacén sigue utilizable
  (T7, P13)." / "Memoria agotada" (`docs/prd/krummi/transactions.prd.md:151`).
- Scenario: a valid store contains one tree, `t`; a read transaction opens it successfully. The allocator
  then refuses a reservation made while the same transaction calls `list_trees()`.
- Causal chain: `catalog::list` obtains the catalog leaf, converts its name with
  `String::from_utf8_lossy(...).into_owned()` and appends to a growing `Vec`. These allocations have no
  fallible reservation/error conversion. Failure of the first one-byte name allocation invokes the
  allocation-error path and terminates the process; the `Result` never returns an `OutOfMemory` error.
  Other stores in that process also lose availability, and a temporary store cannot survive the process exit.
- Evidence: reproduced on Windows using the current branch's compiled library and the isolated allocator
  probe below. Setup and `open_tree` completed before fault injection; only allocations on the calling
  thread were denied. Output: `memory allocation of 1 bytes failed`; exit code `-1073740791`
  (`0xC0000409`). The line printing the result was never reached. This is a demonstrated failure, not a
  hypothetical risk. No persistent corruption or memory unsafety was demonstrated.
- Regression boundary: this public catalog/list operation is new in the branch. Similar infallible
  allocations in pre-existing transaction machinery are not reported as additional branch regressions.
- Suggestion: use fallible reservations/conversions for the new catalog-result allocations and verify the
  public operation returns `OutOfMemory` while the store remains usable, recording write failures under T11.

## Allocator reproduction

The following source was passed through standard input to `rustc`, linked against the current debug
`libkrummi-*.rlib`, using `-L dependency=target/debug/deps`. The executable was generated only at
`target/review-oom-probe.exe`; no source file was created or modified. It opens only an in-memory store.

```rust
use std::alloc::{GlobalAlloc, Layout, System};
use std::cell::Cell;
thread_local! { static DENY: Cell<bool> = const { Cell::new(false) }; }
struct Allocator;
unsafe impl GlobalAlloc for Allocator {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        if DENY.try_with(|deny| deny.get()).unwrap_or(false) { std::ptr::null_mut() }
        else { unsafe { System.alloc(layout) } }
    }
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) { unsafe { System.dealloc(ptr, layout) } }
}
#[global_allocator] static ALLOC: Allocator = Allocator;
fn main() {
    let store = krummi::Store::open_temporary(&krummi::StoreOptions::default()).unwrap();
    let mut write = store.write().unwrap();
    write.open_tree_with("t", krummi::TreeKind::Normal, krummi::OpenMode::CreateNew).unwrap();
    write.commit().unwrap();
    let read = store.read().unwrap();
    read.open_tree("t", krummi::TreeKind::Normal).unwrap();
    eprintln!("probe: setup complete; calling list_trees with calling-thread allocations denied");
    DENY.with(|deny| deny.set(true));
    let result = read.list_trees();
    DENY.with(|deny| deny.set(false));
    eprintln!("probe: list_trees returned: {result:?}");
}
```

Observed output:

```text
probe: setup complete; calling list_trees with calling-thread allocations denied
memory allocation of 1 bytes failed
memory allocation of 30 bytes failed
skipping backtrace printing to avoid potential recursion
probe exit code: -1073740791
```
