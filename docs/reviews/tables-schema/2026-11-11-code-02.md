### R1 — major — Valid large defaults are still rejected by an undeclared catalog limit

**Location:** `crates/krummi/src/table/schema.rs:294`–`:295`, called from `:274`; creation through `crates/krummi/src/table/catalog.rs:344`. The same restriction applies when adding a column (`schema.rs:447`) or lengthening a column name (`:484`).

**Status:** still open, partially remediated. This retains [the original R1](2026-11-11-code.md#R1); it is not an additional finding.

**Failure scenario:** the original permitted schema has `id: I64 NOT NULL` as its primary key and `b: Bytes NOT NULL DEFAULT` with 268,435,453 bytes. The key is omitted from the row and the three-byte header makes the stored row exactly 268,435,456 bytes, the E18 maximum. `check_general` now counts the serialized catalog metadata and returns `InvalidSchema / InvalidDefault` when that metadata exceeds `MAX_EXTRA`. The table is still not created, even though its schema and default satisfy the specified rules.

**Evidence: independent public-API reproduction and source tracing.** A Rust program compiled from stdin against the rebuilt head library computed the row length through `RowLayout::encoded_len`, then invoked `open_table_with("large", TableMode::CreateNew(&schema))` under `catch_unwind`:

```text
R1: permitted row bytes=268435456; creation returns InvalidSchema { folder: None, table: "large", column: Some("b"), rule: InvalidDefault }
```

No panic occurred. The reproduction also asserted that the table was absent and successfully committed the transaction. Independently rerun integration tests `ac15_a_default_too_large_for_the_catalog_fails` and `ac15_a_schema_that_fills_the_catalog_entry` passed: they cover all three creation modes, adding an oversized default, an exactly full catalog entry and a rejected longer column name, with no effects on failed validation. These demonstrate the safe error path, but deliberately assert the provisional rejection.

**Requirement:** E1/E4 and S1/AC1 require creation of allowed schemas; E5 enumerates invalid-schema rules without an aggregate catalog-size limit; E18/S15/AC15 allow this stored row size. E4 permits «una constante de su tipo» as the default. The resolutions explicitly acknowledge that the additional limit and error class await the user's decision. Replacing the panic with an error fixes the failure mechanism but does not satisfy the original permitted-schema requirement. No unsafe access or atomicity failure is claimed.

**Suggestion:** support the permitted schema, or obtain an explicit product decision for the additional limit and its public error before closing R1.

<a id="R2"></a>
### R2 — verified resolved — Old-row defaults now borrow the catalog payload

`crates/krummi/src/table/rows.rs:465`–`:471` resolves reference-valued missing columns through `stored_defaults`, which uses `decode_defaults` (`schema.rs:788`–`:841`) to borrow the catalog bytes. Cloning those `Cow::Borrowed` values preserves the underlying pointer. `Versions<'t>` caches defaults once per scan, and the returned lifetime follows the transaction's `PageSource`, not the temporary decoding cache. The original per-row owned payload copy is removed.

**Independent verification:** `e11_old_rows_borrow_the_defaults_of_added_columns` passed for bytes, text and vectors, with point reads and scans in the schema-changing write and a later read. A supplemental public-API reproduction held two old rows and reverse-scan results simultaneously with a 1 MiB default and verified shared borrowed pointers after both table and column renames. It then dropped and re-added the column with a different default, verified the new value, committed, and verified the newer snapshot while an earlier snapshot still exposed its earlier schema. Another reproduction changed a separate scalar column in an old row, forcing actual row re-encoding, and verified that the added default survived as the correct borrowed value before and after commit. A key-only no-op update also passed.

**Dependent invariants:** table rename updates the live state's name before subsequent row reads; schema changes publish catalog metadata and history in the same write; drop/re-add uses distinct column identities. Row updates encode merged borrowed values into an owned row buffer before mutating pages (`rows.rs:842`–`:863`). Mutators require `&mut self`, preventing live row/scan references from crossing writes; independent compile-fail doctests passed. Catalog lookup failures propagate transaction error handling, and scans remain stopped after an error. No new regression was demonstrated in these paths. The inherited D11/AC20 requirement and E11/S25 are met for the reviewed defaults path.

<a id="R3"></a>
### R3 — verified resolved — Vector norm tails follow the specified reduction order

`crates/krummi/src/table/value.rs:585`–`:600` accumulates complete blocks into 16 lanes, reduces the fixed tree, then folds each tail square into the result in order before the square root. F32 and F16 share this kernel; the unchanged exact-integer I8 path is unaffected. `crates/krummi/src/table/row.rs:274` persists the resulting norm, so the corrected order reaches stored rows.

**Independent verification:** the original F32 vector (`2^27`, fifteen zeros, seven ones) now produces exactly `41a0000000000000`, independently reproduced through `vector_norm`. The rerun `vector_norm_adds_the_tail_after_the_lanes_in_order` pins that result and the rounding-sensitive F16 case; the other vector encoding tests also passed. The implementation matches design document 05's requirement that “the tail elements are added after, in order.” No new regression was demonstrated.
