## Findings

All six findings are open. They are ordered by severity; IDs are local to this report.

<a id="R1"></a>
### R1 — blocker — Bulk-load rollback promises extend beyond the commit point of no return

**Location:** Decisions / E13; acceptance / AC10. `docs/prd/krummi/tables-schema.prd.md:48`, `:230`.

**Problem and evidence:** E13 says «Si una fila falla, si la secuencia falla, si la aplicación cancela o si hay un pánico, la carga aborta entera» and «Si el proceso termina de golpe, la carga nunca se confirmó y la recuperación del almacén la descarta (G5)». Neither statement distinguishes loading rows from committing the load's transaction.

The inherited protocol explicitly has a point after which the commit cannot be undone, including by a panic (`docs/prd/krummi/journal-group-commit.prd.md:42`, E2), and its durability wait cannot be cancelled (`:44`, E4). Root G1 allows all or none when a crash interrupts confirmation (`docs/prd/krummi/krummi.prd.md:155`); G2/G5 preserve what has become durable. The implementation publishes the commit, releases the writer turn and then waits for durability before returning (`crates/krummi-tx/src/transaction.rs:515`).

A crash after the journal group becomes durable but before the bulk-load call returns can therefore recover the complete load. E13's unconditional discard/rollback requirement cannot coexist with that protocol. AC10's panic/cancellation cases also need a phase boundary to have a valid oracle.

**Suggestion:** Bound rollback, cancellation and panic guarantees by phase and explicitly retain the inherited commit/recovery rules after the point of no return.

<a id="R2"></a>
### R2 — blocker — AC10 requires secondary indexes before they can be created

**Location:** Acceptance / AC10; Out of scope. `docs/prd/krummi/tables-schema.prd.md:230`, `:155`.

**Problem and evidence:** AC10 starts «Dada una tabla con filas e índices» and requires failed bulk loads to preserve both. However, Out of scope excludes «Índices secundarios (7.2), estadísticas (7.3) y columnas JSON (7.5), salvo lo que E3, E5 y E17 dicen de ellos». Neither AC10 nor E13 is included in that exception.

Parent N2 requires building the children in order (`docs/prd/krummi/tables.prd.md:44`), and 7.2 introduces index creation (`:92`). There is no existing table/index API in the starting code. Consequently, the public interface cannot prepare AC10's required fixture when closing 7.1; implementing indexes early or fabricating internal state would bypass the stated scope or public-interface test rule.

**Suggestion:** Require the no-index bulk-load cases in 7.1 and explicitly assign the indexed extension to 7.2.

<a id="R3"></a>
### R3 — major — Adding a nonnullable column to an empty table has two readings

**Location:** Decisions / E4–E5; acceptance / AC4. `docs/prd/krummi/tables-schema.prd.md:39`, `:40`, `:202`.

**Problem and evidence:** E4 states «Añadir a una tabla con filas una columna que no admite nulos exige un valor por defecto». E5 rejects «una columna añadida que no admite nulos sin valor por defecto», without a condition on whether the table has rows.

**Allowed readings:** The restriction applies only to a populated table, permitting the addition to an empty table; or E5 applies unconditionally, rejecting it even when the table is empty. The observable results differ: success with a new schema version versus an invalid-schema error without changes. AC4 inherits that unresolved difference.

**Suggestion:** Specify one rule for empty tables and use it consistently in E4, E5 and AC4.

<a id="R4"></a>
### R4 — major — Error precedence does not break ties within one column

**Location:** Decisions / E17; acceptance / AC14. `docs/prd/krummi/tables-schema.prd.md:52`, `:260`.

**Problem and evidence:** E17 says «si una fila incumple varias, se informa la primera columna en el orden del esquema». It does not specify precedence among rules violated by that same column. Unlike E5, it does not declare the rule list to be ordered. AC14 nevertheless requires the error specified by E17 when a row violates two rules.

For example, insert `[(id, 1), (n, NULL), (n, 5)]` with `n` nonnullable. The same first invalid column violates both «nulo no admitido» and «columna repetida».

**Allowed readings:** Detect duplicate column names before validating values and report the duplicate; or validate the first occurrence and report its forbidden null. Both satisfy the first-column rule, but return different public `rule violated` data.

**Suggestion:** Specify the tie-breaker among rules for one column and cover it in AC14.

<a id="R5"></a>
### R5 — minor — Promised annotations have not been added to the affected documents

**Location:** Annotations to other PRDs. `docs/prd/krummi/tables-schema.prd.md:283`–`:305`.

**Problem and evidence:** The section states that the affected documents «llevan la anotación del 2026-11-10 (en sus traducciones también)». The Spanish and English versions of `tables`, `trees`, `trees-keys` and `benchmark` lack this child's promised annotations. Existing annotations from the parent tables PRD do not record the child's sequence and precedence changes.

For example, `docs/prd/krummi/tables.prd.md:46` and `:48` still describe autonumeric columns and whole-row replacement, as do `tables.prd.en.md:49` and `:51`, without a child annotation. Design document `01-row-format-and-types.md:72` retains the former timestamp range, and `02-row-storage.md:195` retains the autonumeric counter, although the child says these design documents have been reconciled.

The child **does declare its overrides**. This finding is about the incorrect completion claim and missing required annotations, not an undeclared product override.

**Suggestion:** Add the promised annotations and design reconciliation while preserving the history of the earlier PRDs.

<a id="R6"></a>
### R6 — minor — Reuse lists an operating-system random function that does not yet exist

**Location:** Reuse; Starting state. `docs/prd/krummi/tables-schema.prd.md:150`, `:97`.

**Problem and evidence:** Reuse lists «La función del pager que lee el generador aleatorio del sistema operativo», while Starting state correctly says «No hay generadores de `ulid` ni `uuid`, ni una función que lea el generador aleatorio del sistema operativo».

Static source searches found no such engine function or Pager export. `crates/krummi-pager/Cargo.toml` currently enables `rustix` filesystem/memory features and Windows filesystem/Foundation/memory features, without the random facilities proposed by design decision P20. That decision describes functionality to add, rather than an existing reuse dependency.

**Suggestion:** Identify the Pager random function as functionality introduced by 7.1 and then shared by generators and catalog tokens.
