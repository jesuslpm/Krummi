## Findings

<a id="R1"></a>
### R1 — major — A valid large default panics while creating the table

**Location:** `crates/krummi/src/table/catalog.rs:549`; supporting paths: `crates/krummi/src/table/schema.rs:267`, `:786`, and `crates/krummi-tree/src/lib.rs:702`.

**Failure scenario:** create a schema with `id: I64 NOT NULL` as the primary key and `b: Bytes NOT NULL` with a default containing 268,435,453 bytes (`MAX_ROW - 3`). The fixed-width primary key is omitted from the stored row; the three-byte header and the default therefore make a row of exactly 268,435,456 bytes, the permitted 256 MiB maximum. The schema satisfies E4/E5. Validation normalizes the default without restricting the encoded catalog size. Creation then allocates the rows/history roots and serializes the whole schema, including the default, into a single catalog value. The additional schema/catalog metadata pushes that value over `MAX_VALUE`; `krummi_tree::set` panics at its size assertion instead of creating the permitted table or returning a typed failure.

**Evidence: reproduced through the public API**, with a standalone Rust program compiled from stdin against the reviewed checkout's debug library. The essential input was:

```rust
let schema = Schema::new(vec![
    Column::new("id", ColumnType::I64).not_null(),
    Column::new("b", ColumnType::Bytes).not_null()
        .with_default(Value::Bytes(Cow::Owned(vec![42; MAX_ROW - 3]))),
], &["id"]);
// In a temporary store's write transaction:
write.open_table_with("t", TableMode::CreateNew(&schema));
```

Observed output:

```text
default bytes: 268435453; stored row bytes: 268435456
a value has up to 268435456 bytes
create panicked: true
```

The program independently checked the row size with `RowLayout::encoded_len`, caught the panic while allowing the transaction to drop, then verified that another writer acquired its turn and the aborted table was absent. No loss of atomicity was demonstrated. The schema-change path also passes the serialized schema to the same catalog writer (`catalog.rs:643`); that variant was established by source tracing, not separately reproduced.

**Requirement:** E1/E4 and S1/AC1 require creation of allowed schemas; E18/S15 permit this row size. The catalog representation introduces an undeclared lower limit and a public panic. Existing maximum-row tests do not cover maximum-sized defaults in schema metadata.

**Suggestion:** store permitted defaults without overflowing a catalog value; any additional public schema limit needs an explicit product decision.

**Status:** open.

<a id="R2"></a>
### R2 — major — Reading added-column defaults copies their payload for every old row

**Location:** `crates/krummi/src/table/rows.rs:463`; supporting paths: `crates/krummi/src/table/schema.rs:823` and `crates/krummi/src/table/rows.rs:260`.

**Failure scenario:** create rows, add a `bytes`, `string` or vector column with a nonempty default, commit, and read rows written before that schema change. Schema decoding converts the default to an owned value, and `Reader::new` retains an owned clone. In `Reader::decode`, an added column absent from the old layout takes `column.default.clone()`. For `Cow::Owned`, this copies the entire payload into each returned row. Both point reads and scans use this path. Retaining N old rows with a B-byte default consequently retains N separate B-byte allocations, although all rows obtain the same stored default.

**Evidence: reproduced through the public API.** In a temporary store, the coordinator inserted two rows into an `id: I64` table, added `b: Bytes DEFAULT` containing 1 MiB, committed, and read both rows in a new read transaction. Both results were `Value::Bytes(Cow::Owned(...))`, and their simultaneously live payload pointers differed:

```text
old-row defaults: Owned/Owned, 1048576 bytes each, distinct allocations: true
```

The point-read reproduction demonstrates the per-row copy; the scan impact follows from the shared decoder. The existing borrowing test at `crates/krummi/tests/table_rows.rs:478` covers values physically present in the row, not defaults synthesized for older versions.

**Requirement:** inherited D11/AC20 explicitly retain the reference contract for these column types. The root annotation at `docs/prd/krummi/krummi.prd.md:116` says they «siguen siendo referencias sin copia»; AC20 at `:477` requires «no a una copia hecha para esa lectura». This applies to E11 and S25/AC-N6, including rows read after adding a column with a default. The returned values are semantically correct, but the explicit read contract is violated.

**Suggestion:** share the engine's retained default payload and cover old-version point reads and scans with borrowing tests.

**Status:** open.

<a id="R3"></a>
### R3 — minor — Stored vector norms use a different tail reduction order

**Location:** `crates/krummi/src/table/value.rs:592`, with the final addition at `:602`.

**Failure scenario:** store a cosine `f32` vector of dimension 23 whose elements are `2^27`, fifteen zeros, and seven ones. The implementation accumulates the seven tail squares into a separate subtotal, then adds that subtotal once to the reduced lanes. The approved design instead reduces the lanes first and adds each tail square individually, in order. Floating-point addition is not associative, so these produce different persisted `f64` norm bits.

**Evidence: reproduced** by calling the public `vector_norm` with that vector and comparing with the prescribed scalar order:

```text
norm bits: actual=41a0000000000001, prescribed=41a0000000000000
```

The reduced lanes equal `2^54`. Each subsequent `+1` rounds away under the prescribed order, while the implementation's combined `+7` rounds to `2^54 + 8` before the square root. `row.rs` persists the output of `vector_norm` for a cosine column. The existing tail test with equal small values does not distinguish these reduction orders.

**Requirement:** `docs/design/tables/05-vectors.md:111` applies the fixed-order kernel to the stored norm, and `:163` prescribes “the tail elements are added after, in order.” The execution document at `odd/tasks/tables-schema.md:56` explicitly includes that document's stored cosine norm in 7.1. No deviation was recorded. This is a persisted numeric-format discrepancy; no current vector-query failure is claimed, since query kernels are outside this range's scope.

**Suggestion:** follow the approved reduction order and pin a rounding-sensitive tail vector's exact norm bits.

**Status:** open.

## Open product question
