### R1 — verified resolved — Aggregate schema size has an approved limit and its own final validation rule

**Original severity:** major. **Lineage:** [original R1](2026-11-11-code.md#R1), [previous follow-up R1](2026-11-11-code-02.md#R1), and the R1 entries in the resolutions. Both earlier reports, their reproductions and all R1 dispositions were consulted.

**Reviewed fixes:** code `6e4a04ad700053fa75520abcf29bdec7b6e3125f`, requirements `461bcccc39b5bda1828e988729d560846f9ca2d0`, and explanatory comment `ed4a2bce270cb96e4d7ebe7512fc02b77d7ac675`.

The original failure was a public panic when a permitted row default made the catalog entry exceed its value limit. The previous follow-up verified removal of the panic but left the undeclared aggregate limit open. The reviewed resolutions now record the user's answer «Aceptar el límite», and the authoritative Spanish PRD annotates E5 accordingly:

> se añade un caso al final de su lista: un esquema que, guardado con los nombres y los valores por defecto de sus columnas, pasa de 256 MiB, el máximo de una entrada del catálogo, falla sin efecto con esquema no válido y la regla «esquema demasiado grande», nombrando la columna con la que lo pasa, también al añadir una columna o al renombrarla a un nombre más largo (la columna del cambio).

**Source verification:**

- `crates/krummi-pager/src/error.rs:166` appends `SchemaTooLarge` after `VersionExhausted`, and its display mapping describes the aggregate limit.
- `crates/krummi/src/table/schema.rs:281` counts the actual encoded schema in column order and reports the column where it exceeds `MAX_EXTRA`. `check_new` at `:296` applies this after the other general E5 rules. Opening modes still perform catalog errors before schema validation and schema validation before compatibility (`table/catalog.rs:320`).
- `TableSchema::plan` checks the change-specific rules, then version exhaustion at `schema.rs:506`, then the aggregate size at `:511`. Adding or renaming reports the changed column; a rename uses its destination name. Failure occurs before drawing identities, recording history or publishing the schema (`table/catalog.rs:628`, `:638`, `:651`). Creation likewise validates before allocating table/history trees (`:344`, `:560`).
- `encoded_column_len` at `schema.rs:861` accounts for the same type, name, flags and default-row bytes written by `encode` at `:888`. `MAX_EXTRA` is the tree value limit minus the catalog entry's fixed 25 bytes (`crates/krummi-tree/src/catalog.rs:27`). Thus the whole entry, including fixed metadata, remains at most 256 MiB.
- Dropping a column reduces size; the supported Modify only changes the fixed-size nullability flag. Table renaming and commit-time root/count updates retain the already-validated schema size (`table/catalog.rs:437`, `:697`). These dependent paths do not bypass the limit through a size increase.

**Independent reproduction and checks:** the original `MAX_VALUE - 3` bytes-default scenario now passes the integration test asserting `InvalidSchema / SchemaTooLarge`, the column `b`, no created table, unchanged schema after a rejected addition, and a usable transaction that commits other changes. The exact-limit integration test creates and commits a catalog entry whose schema occupies exactly `MAX_EXTRA`; growing its column name fails without effect.

A supplemental program, compiled from stdin against the rebuilt head library, additionally exercised the public API:

1. Measured the encoded schema overhead with a one-byte default, then constructed `id I64 NOT NULL`, `b Bytes DEFAULT`, `tail I32` so the whole catalog entry exceeded its maximum by one byte. The default column alone fitted; the final column had no default. All three creation modes returned `SchemaTooLarge` naming `tail`, and created nothing.
2. Removed `tail` and successfully created that near-full schema. Adding `tail NOT NULL` without a default returned `NotNullWithoutDefault`; adding nullable `tail` returned `SchemaTooLarge`. Lengthening the earlier primary-key column name returned `SchemaTooLarge` naming the new name, although size accumulation crossed the maximum at the later bytes column. All failures preserved the original version, schema state, key and column count.
3. Allowed nulls on the bytes column, dropped it, added a small column and inserted a row. These subsequent operations committed successfully; a new read verified the row and resulting schema.
4. Advanced a separate minimal table through 65,534 renames. At version 65,535 an oversized bytes-default addition returned `VersionExhausted`, while an incorrectly typed default returned `InvalidDefault`. Neither changed its version; the transaction committed successfully.
