## Findings

<a id="R1"></a>
### R1 — major — A thread panic does not guarantee process termination

**Section / IDs:** Objective and context; Product decisions / L2 (`docs/prd/krummi/tables/tables-row-reads.prd.md:18`, `:29`).

**Problem:** The PRD records the user's selection «Pánico del proceso», but describes an ordinary thread panic as automatically terminating the process unless captured. These are different observable guarantees.

**Evidence:** L2 says «un pánico del hilo que la lee, que termina el proceso si la aplicación no lo captura». Under Rust's unwinding strategy, an uncaught panic on a secondary thread terminates that thread; other threads can continue. An uncaught main-thread panic ends the application. See the official [Rust threading model](https://doc.rust-lang.org/std/thread/index.html#the-threading-model). The repository already exercises the distinction: `crates/krummi-tx/tests/commit.rs:78` spawns a writer that panics, observes the failed join at line 83, and continues using the store. This test was inspected, not executed.

**Allowed readings:** Ordinary Rust panic, potentially losing only the reader thread; or mandatory process termination, matching the recorded choice. Also, «Igual en todas las compilaciones del motor» needs a scope for the promised recovery: [`catch_unwind`](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html) cannot capture a panic compiled to abort the process.

**Suggestion:** Specify thread versus process termination and the panic strategy under which the capture/recovery contract applies.

<a id="R2"></a>
### R2 — major — The fate of a write retained across panic capture is unspecified

**Section / IDs:** Product decisions / L2; Acceptance criteria / AC-L5 (`docs/prd/krummi/tables/tables-row-reads.prd.md:29`, `:116`).

**Problem:** The PRD attributes automatic write abortion to T10 without specifying whether the panic must unwind through the transaction's lifetime. Capturing only the column access can leave the transaction alive, which requires a separate observable contract.

**Evidence:** L2 states «durante una transacción de escritura, la aborta como dice T10». AC-L5 explicitly describes a panic «capturado por la aplicación» and requires «la escritura se aborta sin aplicar nada». T10 (`docs/prd/krummi/transactions/transactions.prd.md:39`) describes an aborted transaction or one abandoned without committing. Current source implements that through transaction lifetime: `crates/krummi-tx/src/transaction.rs:942` releases the write turn on destruction; commit checks recorded errors at `:516`. A `TableRow` holds its reader and stored data (`crates/krummi/src/table/rows.rs:889`, `:917`), without a link to the write's failure latch, and its text accessor can panic directly at `:1140`.

**Allowed readings:** Capture outside the whole transaction lifetime, allowing unwinding to destroy and abort it; or capture around `row.text(...)` while retaining the write, with the engine automatically invalidating that surviving transaction. In the latter case, the PRD does not specify the result of a later commit or when the write turn becomes available. The existing panic test at `crates/krummi-tx/tests/commit.rs:63` covers destruction during unwinding, not this retained-write case.

**Suggestion:** Define both capture boundaries and add the retained transaction's commit and write-turn outcomes to AC-L5.

<a id="R3"></a>
### R3 — minor — The claimed unchanged error-page attribution is inaccurate

**Section / IDs:** Product decisions / L1; Acceptance criteria / AC-L3 (`docs/prd/krummi/tables/tables-row-reads.prd.md:28`, `:109`).

**Problem:** AC-L3 specifies an implementable error result, but incorrectly calls that result the existing behavior when a schema version is missing from history. Applying it would change a public error datum.

**Evidence:** AC-L3 includes «una de una versión que falta en su historial» and requires «la clase de daño y el número de la página de la fila, como hoy». Currently, `crates/krummi/src/table/rows.rs:688` resolves an older schema version from the history tree; lines 695–700 report its history leaf as damaged when that version is absent. The row reader propagates that error at `:530`. This differs from identifying the row's page.

**Suggestion:** Declare the diagnostic change and remove the unchanged-behavior claim, or correct the specified page to preserve current behavior.

<a id="R4"></a>
### R4 — minor — Starting state presents future operations as implemented behavior

**Section / IDs:** Objective and context / Starting state, fourth bullet (`docs/prd/krummi/tables/tables-row-reads.prd.md:43`).

**Problem:** A planned, inherited requirement is presented as existing behavior verified against code.

**Evidence:** The bullet says «El backup, la compactación, la migración y la verificación tratan las páginas de las tablas como las de los árboles y no leen el contenido de las filas». N1 (`docs/prd/krummi/tables/tables.prd.md:43`) assigns whole-store operations to future modules; the root lists backup, compaction and operational tooling as modules 10–12 (`docs/prd/krummi/krummi.prd.md:251`). `README.md:7` describes the implemented modules, and inspection of `crates/` found no corresponding whole-store operation APIs. Internal page/run checksum functions are not a store verification tool.

**Suggestion:** Label this bullet as the inherited contract for future modules rather than an implemented starting-state fact.

## Open product questions

1. Must a malformed-column panic terminate the process even on a secondary thread, or should it follow ordinary Rust thread-panic behavior? Under which panic strategy does the recovery guarantee apply? (R1)
2. If the application catches only the column-access panic and retains its write transaction, must that transaction become unusable for commit, and when must its write turn be released? (R2)

These questions require product decisions; this review does not select the answers.
