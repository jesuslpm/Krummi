## Findings

### R1 — Major: AC-IC4 contradicts IC6 about primary-key spelling in an update error

<a id="R1"></a>

- **Section / IDs:** Acceptance criteria / AC-IC4; Product decisions / IC4, IC6.
- **Location:** `docs/prd/krummi/tables/tables-collation.prd.md:220`, particularly lines 221–222; IC6 at line 51 and IC4 at line 49.
- **Problem:** AC-IC4 requires duplicate-key errors, including update failures, to return “los textos tal como los dio la aplicación”. IC6 instead requires “los textos de la fila que choca tal como quedarían guardados”, expressly including “al actualizar, los que la fila conserva”. These differ when an update locates a row through an equivalent primary-key spelling.
- **Evidence:** A stored row has primary key `Ana` in a `ci` column. The application updates it through `ANA`, assigning a unique indexed column a value that conflicts with another row. IC4 preserves the stored primary key as `Ana`. Under IC6 the error's primary-key data must therefore contain `Ana`; AC-IC4's literal wording instead requires `ANA`. The primary key is part of the public duplicate-key error data under `tables-schema.prd.md:52` (E17) and `tables-indexes.prd.md:55` (IX10), so this is not limited to the spelling of the conflicting index value.
- **Observable readings:** report the retained primary key (`Ana`), or echo the update's supplied lookup key (`ANA`). The acceptance criterion and decision do not provide the same oracle for that public error field.
- **Suggestion:** Align AC-IC4 with IC6 and cover an update through an equivalent but differently spelled primary key.
- **Status:** Open. IC6 already settles the intended behavior; no new product decision is needed to make the criterion consistent.
