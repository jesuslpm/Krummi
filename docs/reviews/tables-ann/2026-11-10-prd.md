## Findings

<a id="R1"></a>
### R1 — Major: JSON reads conflict with the common ownership contract

- **Location:** Reparto en PRD hijos / 7.5; Salida; inherited D11 and AC20.
- **Evidence:** `docs/prd/krummi/tables.prd.md:110` requires JSON stored in “un formato binario que se lee sin copiar ni analizar el texto”. However, `docs/prd/krummi/tables.prd.md:166` reserves zero-copy reads for `string`, `bytes` and vector, requiring the other types to be returned “decodificados en una copia propia de la aplicación”. The root repeats that exception explicitly for D11 and AC20 at `docs/prd/krummi/krummi.prd.md:116–118`. The 7.5 annotation updates N2 and the scope exclusion, but does not declare an exception to this ownership rule. The English translation reproduces both requirements at `docs/prd/krummi/tables.prd.en.md:112–113` and `:165–168`.
- **Problem and allowed readings:** an implementer following 7.5 returns a borrowed JSON view tied to the transaction; an implementer following the common output rule returns an application-owned decoded copy. These differ in allocation, lifetime and whether the application can retain the value after the transaction ends. AC20 also has different expected outcomes under those readings. The umbrella does not consistently state the already selected zero-copy behavior for this new type.
- **Suggestion:** explicitly extend the zero-copy rule to JSON in the umbrella output contract and the root D11/AC20 annotation, including the translations.
- **Status:** open.

<a id="R2"></a>
### R2 — Minor: starting state generalizes normal-tree limits to all tree kinds

- **Location:** Estado de partida / Datos, `docs/prd/krummi/tables.prd.md:72`.
- **Evidence:** the row names “normales, multivalor y de tamaño fijo”, then says “Las claves son bytes de 1 a 2.048, ordenados byte a byte” and “los valores, de 0 a 256 MiB”. Fixed-size trees instead accept numeric `u64` keys (`crates/krummi/src/lib.rs:633`) and values of a fixed length no greater than 2,048 bytes (`crates/krummi-tree/src/fixed.rs:1–2`, `:46`). Multi-value entries also cap each value at 2,048 bytes (`crates/krummi/src/lib.rs:69`, `:1445–1447`). The inherited B5/B6 distinguish these cases (`docs/prd/krummi/trees.prd.md:45–46`).
- **Problem:** the starting-state summary attributes the normal-tree limits and ordering to all three existing kinds. This is a documentation precision defect; the detailed inherited contracts and source already settle the behavior.
- **Suggestion:** qualify the normal-tree limits and separately summarize the existing fixed-size and multi-value exceptions.
- **Status:** open.
