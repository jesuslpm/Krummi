# Tables, queries and bindings: technical design

Design documents written before the PRDs of module 7 (tables) and of the modules that follow it (queries, C interface
and C# binding). Each document compares Voron with other structured storage systems on one topic, measures or cites
the costs that matter, and ends with a recommended design and the product questions it leaves for the user. The PRDs
take the chosen designs as their starting state, so that performance does not force the code and the PRDs to change
later, as it did with the journal (O8 of the [performance plan](../../performance/plan.md)).

Decisions taken with the user after the first drafts:

- Rows are stored clustered by primary key, as in SQL Server: the row is the value of the primary key's tree, and
  secondary indexes point to the primary key. User: "Las claves primarias rara vez cambian y suelen ser artificiales
  como autonuméricos o ULID o GUID. Así que quizá mejor tener índices agrupados para la clave primaria como en SQL
  Server". This replaces the heap of [02-row-storage.md](02-row-storage.md).
- The primary key is mandatory. User: "Hacemos la clave primaria obligatoria."
- One `uuid` type, ordered by its RFC 9562 bytes by default, with a per-column option to order like SQL Server's
  `uniqueidentifier` (groups of bytes 10–15, 8–9, 6–7, 4–5, 0–3), for data generated by `NEWSEQUENTIALID()` or by the
  user's sequential GUID generator; `ulid` is its own type, 16 bytes with the time first, generated monotonically as
  that generator does (48 bits of Unix milliseconds, 80 random bits incremented within a millisecond). User: "Sí, me
  sirve". Evidence from the user, who tested the generator on SQL Server: "ordena perfectamente bien por tiempo, no
  solo eso sino que cuando se usa "por proceso" quedan casi casi en el orden de inserción", and "Incluso en el mismo
  milisegundo" (the increment of the random part keeps them strictly increasing). Test vectors need no SQL
  Server: .NET's `SqlGuid` implements its order (`rgiGuidOrder` in `CompareTo`), so a C# test can order generated GUIDs
  with `SqlGuid` and check that Krummi's permuted keys give the same order under `memcmp`.
- The planner works on estimates, not exact range counts: no counts in branch nodes. Statistics with histograms exist
  per column, also for columns without an index, like SQL Server's statistics, and need be neither exact nor always up
  to date. User: "Estimaciones, los histogramas no necesitan ser exactos ni estar siempre al día, pero tienen que
  existir incluso si no hay índices para las columnas, algo como hace SQL Server con las estadísticas."
- Statistics are created and refreshed automatically in the background, like SQL Server's asynchronous mode: a
  modification counter per table is kept with each commit; a query that finds a column's statistics missing or stale
  plans with a default estimate and asks a thread of the store to build them from a sample with a read transaction
  and store them with a short write; an explicit `analyze` forces it. No query waits for sampling. User: "Sí".
- Column types of the first version: `bool`; `i8`–`i64` and `u8`–`u64`; `f32` and `f64` (`-0` stored as `+0`, one
  canonical NaN sorting after +∞); `decimal(p, s)` as 128-bit fixed point up to 38 digits; `string` (UTF-8, binary
  order, no collation); `bytes`; `date`, `time`, `timestamp` (a UTC instant in microseconds, no stored time zone) and
  `duration`; `uuid` (RFC or SQL Server order per column); `ulid`; `vector(element, dimension)` with `f32`, `f16`, `i8`
  or `bit` elements and a fixed dimension per column. Every column is nullable unless declared `NOT NULL`; primary
  key columns never are. Out of the first version: arrays, enums, JSON, stored time zones, scalar `f16` and
  case-insensitive collation. User: "Sí".
- Vectors: at most 4,096 dimensions; L2, cosine, dot product and Hamming (for `bit`) distances; distances bit-identical
  on every platform, so that a distance filter returns the same rows under any plan; the norm stored beside a vector
  of a cosine column; NaN and infinities rejected on write and in queries, and zero vectors in cosine columns; the
  caller quantizes `i8` and `bit` vectors; top-k by an exact scan with a bounded heap, ties broken by primary key, `k`
  up to 10,000; one thread per query in the first version; a vector is never a primary or index key. User: "Me valen".
- The query tree of the first version: one table per query; filters (`=`, `<`, `≤`, `>`, `≥`, between, `IN`,
  prefix, is null, `AND`/`OR`/`NOT`); vector distance as a threshold and as top-k nearest; projection; `ORDER BY`
  columns, `LIMIT`, `OFFSET`; aggregates over the whole filtered table (`count`, `min`, `max`, `sum`, `avg`). Out:
  joins, `GROUP BY`, subqueries, functions over columns, writes inside the tree. Values always travel as separate
  parameters; tags for joins and `GROUP BY` are reserved in the format. User: "Me sirve".
- C interface and C# binding: a `krummi-capi` crate is the only place with `unsafe` besides the pager (D12 annotated);
  a first C surface of store, transactions and queries by serialized tree; a status code per error class with the
  message asked for separately; zero-copy reads valid until the transaction ends, with a copying twin of each method
  in C#; a cursor that returns batches of rows; the write transaction checks its thread and panics never cross the
  boundary; .NET 8 or later with `LibraryImport`, `SafeHandle` and a `ref struct` so that spans cannot outlive the
  transaction; a typed method chain as the fluent API; no async in the first version. Platforms: only those that CI
  builds and tests, today win-x64 and linux-x64 (`.github/workflows/ci.yml`: `windows-latest`, `ubuntu-latest`).
  User, to the platforms: "de momento no tenemos compilación ni pruebas en arm64."
- Compression of values by dictionary is deferred out of the first children, with its hooks reserved in the format
  now (a compressed flag and a dictionary id in the row header, a tree reserved for dictionaries). When built: LZ4 with
  a dictionary, opt-in per table, whole row; first confirm that enabling `lz4_flex`'s dictionary feature does not
  switch the journal's encoder to its slower safe one. User: "Sí".
- Secondary indexes: one normal tree per index, keyed by `columns ‖ primary key`; nulls first by default, first or
  last per index column; in a unique index, nulls are distinct from each other, as in standard SQL (not SQL Server);
  an index key over the tree's 2,048-byte limit is rejected with a typed error before anything changes; included
  (covering) columns from the first version; partial indexes reserved in the definition, built once the query tree
  exists; descending order per index column. User: "Sí".
- Split: module 7 (tables) is an umbrella PRD without an execution of its own, with children 7.1 tables with a schema
  (column types, row format, mandatory clustered primary key, insert, update, delete and read by key, scans by primary
  key range, schema changes without rewriting rows), 7.2 secondary indexes, 7.3 statistics, 7.4 compression by
  dictionary (deferred; its hooks in 7.1). Two new modules in the root PRD, built right after module 7 and numbered
  17 and 18 so that no existing number moves: 17 queries (query tree, validation, cost-based planner, execution by
  cursor in batches, vector distance filters and top-k, the Rust fluent API) and 18 the C interface and the C# binding
  (`krummi-capi`, the C header, the .NET 8 binding with its fluent API, the NuGet package); 18 depends on 17. User:
  "Sí".
- Keys of tables and index entries use FoundationDB's tuple encoding (https://github.com/apple/foundationdb/blob/main/design/tuple.md),
  not a format of Krummi's own: a standard, self-describing, with existing implementations (C# among them), compared
  with `memcmp` as today. Extensions within the specification: `ulid` with the UUID code (16 raw bytes, time first);
  `uuid` in SQL Server order by permuting its 16 bytes before encoding; `timestamp`, `date`, `time` and `duration` as
  integers; `decimal` with a user type code (`0x40`–`0x4F`); a descending column by inverting the bytes of its
  element (the only place a key is not self-describing; the schema says which). The row format stays the one of
  [01-row-format-and-types.md](01-row-format-and-types.md) (O(1) column access); a tuple is read sequentially. User,
  after "¿Tú que opinas?": "Sí".
- Execution plans are a representation of their own: the planner turns the query tree into a tree of physical
  operators (for example primary key range, index seek, full scan, filter, fetch by primary key, project, sort, top-k,
  limit, aggregate), and the executor only runs plans; `explain`, the plan cache and the tests use them. The public
  interface accepts plans as well as query trees from the first version of module 17, validated strictly (a bad plan
  is an error, never a panic or a silent wrong result), with resource limits and checked against the schema version.
  Plans grow later towards most of standard SQL by adding operators. User: "Una cosa que tengo en mente es el plan de
  ejecución. [...] Quizá podríamos permitir que el interfaz público admitiera planes de ejecución. Con la IA se podrían
  construir planes de ejecución para consultas complejas sin necesidad de un procesador de consultas." and, to
  accepting plans from the first version: "Sí".
- The executor builds its own data structures outside the store's journal: table spools, index spools, hash tables
  and temporary indexes, for example on Krummi's temporary mode (no journal, no durability, no file). User: "estaba
  pensando en otras operaciones como table spool, index spool. El ejecutor podría formar estructuras de datos como
  hash tables e índices temporales no sujetos a toda la parafernalia de Krummi como el diario." Document 8 compares
  plan representations (Substrait, DataFusion and DuckDB physical plans, SQLite's VDBE, PostgreSQL's plan nodes) and
  fixes the memory budget per query, spilling, and the lifetime of these structures.
- Encryption at rest of a store in use leaves the scope; it is delegated to the file system's encryption. Only
  backups are encrypted, on request, in module 10; module 9 leaves the split; G8 holds only for backups (root PRD
  annotated, 2026-11-09). So the executor's spill files go unencrypted to a subfolder of the store's folder, which the
  file system's encryption covers when there is one. User: "no estoy muy seguro de implementar el cifrado, puede que
  lo deje fuera de alcance. [...] la clave de cifrado es muy difícil de proteger y tiene que estar a mano para usarla.
  Ya existen mecanismos de cifrado a nivel del sistema de archivos." and "Podríamos cifrar los backups, eso es barato,
  mientras que cifrar los archivos de datos es muy caro." and, to annotating the root PRD so: "Sí".
- Plans ([08-execution-plans.md](08-execution-plans.md)): a format of Krummi's own, in the query tree's binary
  envelope, with operator names aligned with Substrait (a Substrait translator later); a plan built against another
  schema version is rejected, naming the table and both versions; applications may store plan bytes; default limits
  per query of 64 MiB of memory and 1 GiB of spill, configurable, no store-wide cap in the first version;
  three-valued logic for `NULL` in comparisons, a filter passing only what is true; row order without `Sort`
  unspecified; `explain` statistics (estimated and actual rows, time, memory, spill per operator) in the C interface.
  User: "Me sirven".
- Dependencies with `unsafe` inside: D12 governs Krummi's own code; a dependency that uses `unsafe` is admitted case
  by case when it is widely used and maintained, pure Rust (no C), without a reasonable safe alternative, and annotated
  with its reason in the PRD that introduces it (the pager already depends on `memmap2`, `zerocopy` and `windows-sys`).
  Dependencies with C code (for example `zstd`, `simsimd`) stay out unless expressly decided. User: "Sí".
- Closing a store through the C interface while transactions or cursors are open fails with the misuse class and
  leaves the store open until they are released, so no pointer dangles; the C# binding's `Dispose` of a store may
  first abort the transactions it knows are open, then close. User: "Sí".
- Generators of primary key values: monotonic `ulid`; sequential `uuid` in SQL Server order (the user's algorithm),
  for `uuid` columns with that order; `uuid` version 7, for `uuid` columns in RFC order; and auto-increment
  (`identity`) 64-bit integer columns that Krummi assigns on insert, increasing and never reused, with a counter per
  table kept with each commit that inserts. User: "Si todos". Their random bits come straight from the operating
  system through the pager at each new millisecond, with no pseudo-random generator in between (document 11, P20,
  decided 2026-11-10).
- Writing rows by primary key: three operations. Insert fails with duplicate key, without effect, when the key
  exists; update replaces the row when it exists and does nothing, reporting that it did not find it, when it does
  not; insert-or-update (upsert) replaces or inserts. User: "Sí".
- Schema changes of the first version, each a new schema version that rewrites no row: add a nullable column (old
  rows read `NULL`); add a column with a default, a constant fixed when the column is added, which old rows read; drop
  a column that is in neither the primary key nor an index; rename a column; allow nulls in a column that did not.
  Refused: changing a column's type, changing the primary key, forbidding nulls in an existing column. User: "sí".
- Tables and trees in the catalog: listing shows both, each with its kind; opening, deleting, renaming or emptying as
  a tree something that is a table, or the other way round, fails without effect with the existing class of a
  different type (B3, annotated: tree operations never destroy a table); the trees inside a table (rows, indexes,
  statistics) are invisible, neither listed nor openable as trees, and take no name of the user's, so B4 ("no name is
  reserved") still holds. User: "Sí".
- The background statistics write takes the single writer turn (G4) for a short write: sampling runs in a read
  transaction and blocks nobody; an application write may wait for the statistics write as for any other writer, and
  that wait counts towards its time limit (T4). The rule is "no operation waits for sampling". User: "Sí".
- Raw data sections leave module 7 (root PRD annotated): the clustered table needs no row ids, and storing bytes under
  an id is what the containers of module 13 cover. User: "Sí".
- Performance of tables: new bench loads, in 7.1 insert with a `ulid` key in order and with a random `uuid`, read by
  primary key, scan a primary key range, update and delete; in 7.2 insert with two indexes, look up by an index, scan
  an index range; compared with Voron's tables (`Table` with `TableSchema` and indexes), since the other engines of
  the bench are key-value stores; threshold Krummi ≥ 0.80 × Voron, as K7; single-load measurements before and after
  are mandatory in every child, on Windows and Linux with the bench power plan. User: "Sí".
- Module 7 is closed when 7.1, 7.2 and 7.3 are; compression by dictionary (7.4) is left out of the root PRD's
  objective 2, as leaf page compression was for module 5 (annotation of 2026-11-03); objective 2 is annotated also
  with modules 17 and 18 added and module 9 removed. User: "Sí".
- A `vector` column may declare the `cosine` metric: Krummi then stores the norm beside each vector on write and
  rejects zero vectors. Without it no norm is stored; a query may still ask for cosine distance on such a column, which
  computes the norms on every row. L2, dot product and Hamming apply to any column of their type. `bit` vectors have a
  dimension that is a multiple of 8. User: "Sí".
- Error classes of module 7: a new class **invalid value** for a value that breaks its column's rules (NaN in a float
  column, a vector of the wrong dimension or a zero vector under `cosine`, a decimal beyond its precision, a null in a
  NOT NULL column), instead of misuse; and **duplicate key** also for a unique index, with the error naming the index,
  as SQL Server reports both cases as duplicate keys (errors 2627 and 2601). User: "Sí".
- After the third PRD review: a NaN in an `f32` or `f64` column is stored as the one canonical NaN (the type entry
  holds; the "NaN in a float column" example of the error classes means a NaN inside a vector); a `bit` vector column
  cannot declare the cosine metric (Hamming is its metric), an `i8` one can; the four generators are increasing also
  within the same millisecond, `uuid` version 7 through the counter RFC 9562 allows. User: "Sí".
- Scope points the PRD had not named: in 7.1, the number of rows of a table, reported at once by a handle for what
  its transaction sees, as a tree's number of entries (A5); in 7.1, deleting a range of the primary key, as a tree's
  range removal, keeping the indexes as row-by-row deletes would; out of scope, resetting or setting the
  auto-increment counter, renaming or redefining an index (drop and create again), statistics over several columns
  together. User: "Sí, pero lo de importar y exportar filas en masa me parece importante."
- Bulk rows: in 7.1, a bulk load from the application, a sequence of rows inserted at once with a fast path when they
  come in primary key order (leaves filled directly), with its own bench load against Voron; load first and create the
  indexes after, since 7.2 builds an index over existing rows; exporting from the application is a scan. Importing and
  exporting files (CSV, JSON lines, Parquet) is a new module 19, after module 18. User: "Sí".
- After the fourth PRD review: renaming to a name of the other kind fails with already exists without overwrite, as
  between trees of different types (A3), and with type mismatch with overwrite, so a tree operation never destroys a
  table; the three new error classes follow B7's rule (the operation fails without effect, the transaction can still
  commit); emptying a table does not reset its auto-increment counter, unlike SQL Server's `TRUNCATE TABLE`, so "never
  reused" holds. User: "Sí".
- Exclusions of module 7: foreign keys and `CHECK` constraints stay out (only the foreign key is a constraint between
  tables); changing a column's default or the order of the columns stays out; updating part of a row stays out with no
  exception, an update replaces the whole row; the exclusion of the command-line tool is removed, because its
  verification and rescue cover the whole store (root PRD D9) and the trees inside a table are checked and rescued as
  trees; showing rows decoded by their schema stays out (module 12). User: "Sí".
- What triggers statistics in module 7, which has no queries: 7.3 offers a public estimate operation (for example the
  rows in a range of a column, or the fraction holding a value), the one module 17's planner will call; when it finds
  a column's statistics missing or stale it answers with the default estimate and asks for them to be built in the
  background, as a query will; `analyze` forces them. Statistics are stale when the modifications since they were
  built exceed SQL Server's dynamic threshold, the lesser of 500 + 20 % of the rows and √(1000 × rows). User: "Sí".
  (Correction of 2026-11-09 after the PRD review: SQL Server applies that formula to tables of more than 500 rows and
  a flat 500 modifications to smaller ones, so the PRD states both, as the threshold "of SQL Server" agreed. Source,
  fetched on 2026-11-09: https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics, the
  table for compatibility level 130 and later: "Permanent | n <= 500 | 500" and "n > 500 | MIN ( 500 + (0.20 * n),
  SQRT(1,000 * n) )".)

Corrections after an external review of the PRD and documents 1 to 8 (2026-11-10), each checked against the
documents before it was applied:

- Doc 3, key encoding: the rejected combination of directions and null orders broke N5, and a second combination broke
  too. Descending strings and byte strings now end with `FF FE`, a descending null that sorts last is `FE FF FF`, and
  every combination keeps the typed order (checked by brute force). A descending column's default puts nulls first,
  as N5 says, not last.
- Doc 3, range bounds: an inclusive upper bound lost the entries equal to it, and the successor of a string prefix
  matched longer strings. Bounds are now `P ‖ enc(v)` and `P ‖ enc(v) ‖ FF`, per direction, for indexes and for the
  primary key of 7.1.
- Doc 3, unique indexes: the uniqueness probe tests the range `[tuple(columns), tuple(columns) ‖ FF)`, not a byte
  prefix, which would report "a" as a duplicate of "a\0". The layout stays the same as for non-unique indexes; SQL
  Server's unique layout (primary key only in the leaves) is recorded as an optimization to measure with 7.2. User,
  to keeping one layout and fixing the probe: "Sí".
- Doc 2, writes: every check (values, sizes, the primary key and each unique index whose key changes) runs before the
  first change, for updates as well as inserts.
- Doc 3, statistics: they keep the modification counter and schema version of the snapshot they were sampled from,
  and never replace statistics sampled from a later snapshot.
- Doc 5, distances: a test pins the expected bits of each kernel, run on every platform in CI. Doc 6, C#: a span read
  after an explicit `Dispose` of its scope is a residual risk, like `unsafe` code.
- PRD: N8 states the snapshot rule, N9 no longer promises that adding compression keeps the format (B12 decides
  then), and AC-N7 requires each index of a table with several, in turn, to be the one that fails.

After the reviewer's follow-up (2026-11-10), and from looking for counterexamples to these corrections:

- Doc 3: the user codes are fixed: `40` `decimal`, `41`–`4E` reserved for future types, `4F` only the null of an
  ascending column with nulls last. The key-size rule counts the extra bytes of descending strings and nulls.
- Doc 3: the encoding check now covers every indexable type, all pairs of consecutive columns exhaustively, longer
  random keys, decoding, ranges, the uniqueness probe and `LIKE`, and it was validated with 8 mutants. AC-N1 and
  AC-N7 require property tests in Rust against a reference model.
- Doc 3, statistics: the first fix ordered builds by the modification counter, which breaks when the counter
  restarts (the in-memory fallback); builds of a table now run one at a time, and the save checks the table's
  identity and the column id. The staleness line still gave the first draft's threshold; it now follows N8.
- Doc 2: operations over many rows (a bulk load that fails whole, creating a unique index over duplicates) cannot
  check row by row; the document says how each one stays without effect.
- Doc 6: R2 no longer promises that safe C# code can never use a span after its transaction; it states the cases
  the binding cannot stop, with the copying twins as the full guarantee.
- PRD: AC-N7 also requires that the transaction can commit its other changes after each failure.
- New documents 9 (query serialization format) and 10 (tools for AI agents), evaluations requested by the user,
  with their own product questions; no decision recorded yet.

Third review round (2026-11-10, findings H7 to H14 of the external review), each examined against the documents and
for counterexamples before applying it:

- H7, accepted: a counter that restarts at zero cannot measure staleness (600 at build, 0 after a restart, 601
  modifications read as 1). Doc 3: the modification counter is table data in the `meta` tree, versioned with the
  rows, never decreasing, surviving close; the in-memory fallback is withdrawn. N8 states it; AC-N8 covers a reopen.
  Found while fixing it: emptying a table or a range delete must add the rows removed, or a table that lost all its
  rows keeps fresh statistics; and a counter that counts only at commit would let an older background build replace
  the statistics an `analyze` built inside a write transaction. Doc 3 counts per operation in the transaction's view.
- H8, accepted: serializing builds deadlocks an `analyze` that waits for a build while holding the write turn. Doc 3:
  no build waits for another; newer statistics win by comparing counters, sound again with H7's counter; one lock
  order, the write turn last; `analyze` inside a write transaction stores within it.
- H9, accepted: doc 2's bulk load that fails whole is a write transaction of its own, read once, written row by row
  with each insert's two phases; any failure aborts it. AC-N3 covers the last row, generated against explicit keys and
  the counter exhausted.
- H10, accepted in part: building into an invisible tree already keeps the data unchanged; doc 2 now states what B7's
  "without effect" covers (everything public operations read, and the ability to commit) and that freed pages are
  free, not lost. AC-N7 checks that every page is in use or free after a failed unique index creation.
- H11, accepted: the scripts canonicalize `-0` and NaN before encoding, so they cannot catch an encoder that skips
  it. AC-N1's property test now names `-0`/`+0`, NaN payloads, both `uuid` orders, the temporal types and `ulid`,
  with a model that compares typed values without the encoding.
- H12, accepted: doc 10's A3 put `TopK(created)` below `KeyLookup`, over an index that lacks `created`. The plan is
  corrected, the fixture's distribution is fixed so the planner's choice follows from statistics, and A9 uses it.
- H13, accepted: `--write` and `--destructive` express intent and authorize nothing. Doc 10 lists the barriers that
  hold against the agent (reach and file permissions, the host's approval rules, MCP launch configuration, backups)
  and adds an injection scenario to A6.
- H14, accepted: doc 10's comparison is now against a reference logical query with the same parameters and snapshot,
  with three outcomes: equal, candidate differs, executor defect (only when two plans Krummi derived from the query
  disagree). (Refined in the fourth round, H17: admissible, not admissible, engine defect.)
- Found reviewing these corrections: a thread that holds the write transaction and calls `analyze` outside it, or
  starts a bulk load, gets T5's misuse error at once (a first wording said T4's time limit, but T4 waits forever by
  default); and an aborted write keeps a grown `krummi.data` (T10, P11), so "as before" after an abort covers the data
  and the free pages, not the file size.

Fourth review round (2026-11-10, H15 to H19):

- H15, confirmed defect: building a unique index into a tree and deleting it on a duplicate allocates pages before
  the duplicate is known, against N10's "detected before the operation changes anything". Doc 2: the build sorts the
  entries first (the sorted bulk load doc 3 already planned), finds a duplicate as equal column parts of neighbours
  before allocating any page of the tree, and only then writes it. No savepoint. AC-N7 checks the store's
  information is as without the attempt; 7.2 also fixes where a large build sorts.
- H16, confirmed defect, and it also hit the third round's fix: `TopK` emits keys and locators only, so the plan
  `TopK → KeyLookup → IndexScan` lost the requested columns, and so did the candidate `TopK → Filter → TableScan`.
  Doc 8 lists each operator's output columns. Doc 10: the fixture's `ix_country` includes `created`, the expected plan
  is `KeyLookup → TopK → IndexScan`, as doc 8's own explain example, and the candidate is `Limit → Sort → Filter →
  TableScan`.
- H17, confirmed defect: with `LIMIT` or `OFFSET` over an order that is not total, two correct plans can return
  different rows. Doc 10's comparison checks admissibility against the full result of Q without its window, adds no
  order Q does not ask for, and names an engine defect only when the planner's own result is not admissible.
- H18, insufficient tests: AC-N8 and doc 3's test list add `analyze` in a write transaction that aborts, more changes
  after `analyze` before a commit, and a failed bulk load during a background build; the reopen case was already in
  AC-N8.
- H19, insufficient specification: doc 2 states that the load's source is a fallible sequence, that an error from it
  is how the application cancels or bounds a load, that a panic or a dropped load aborts and frees the turn (T10),
  and that tools add their own limits; AC-N3 covers a failing source and a cancellation.
